# Sprint 1 — Acceptance Criteria

Документ фиксирует критерии QA / Product Acceptance только для тех Foundation-задач Sprint 1, в проверке которых участвует Product Owner / Analyst / QA.

Для текущего Foundation scope:

- `F-06` — QA / Product Acceptance;
- `F-07` — Product Review;
- `F-08` — QA.

Критерии реализации остальных Foundation-задач находятся в зоне ответственности их owners и reviewers и этим документом не определяются.

# 1. Граница ответственности

Product Owner / Analyst определяет:

- что должно быть реализовано;
- ожидаемое пользовательское и бизнес-поведение;
- обязательные ограничения;
- внешние контракты там, где они необходимы для однозначного взаимодействия компонентов;
- Acceptance Criteria.

QA проверяет фактическое поведение относительно согласованных требований, контрактов и Acceptance Criteria.

Product Acceptance подтверждает, что переданный результат соответствует согласованному продуктовому scope.

Ответственные разработчики и Code Review отвечают за:

- внутреннюю архитектуру;
- структуру кода;
- структуру БД;
- ORM и persistence implementation;
- migrations implementation;
- hashing / token implementation;
- выбор библиотек;
- алгоритмы;
- техническую декомпозицию;
- качество и корректность внутренней реализации;
- устранение конфликтов и дефектов, возникших вследствие выбранных технических решений.

QA / Product Acceptance не заменяет Code Review и не подтверждает корректность внутренней архитектуры.

Если внутреннее техническое решение приводит к невыполнению согласованного требования, внешнего контракта или Acceptance Criterion, это является проблемой реализации и не изменяет требование автоматически.

Если само требование неоднозначно, противоречиво или технически невыполнимо в согласованном виде, это должно быть поднято командой на уточнение. В таком случае проверка может получить статус `BLOCKED` до принятия решения.

# 2. Общие правила приёмки

Результат проверки фиксируется одним из статусов:

- `PASS` — все применимые обязательные Acceptance Criteria выполнены;
- `FAIL` — хотя бы один применимый обязательный Acceptance Criterion не выполнен;
- `BLOCKED` — проверку невозможно завершить из-за внешнего blocker, отсутствующего результата, окружения, данных либо противоречия в требованиях.

Дополнительная функциональность не заменяет обязательную.

Наличие Dashboard, Invitations, Connections либо любой другой функциональности сверх согласованного scope не компенсирует невыполнение Acceptance Criteria проверяемой задачи.

Approve относится только к конкретной проверенной версии / commit / build.

Если после проверки изменяется поведение, затронутое Acceptance Criteria, соответствующая проверка выполняется повторно.

Изменение внутренней реализации, не меняющее наблюдаемое поведение и внешний контракт, само по себе не требует повторного Product Acceptance.

# 3. Передача задачи на проверку

Перед QA / Product Acceptance исполнитель предоставляет по применимости:

- ссылку на задачу;
- Pull Request / commit / build, который необходимо проверять;
- рабочее окружение или воспроизводимую инструкцию запуска;
- необходимые demo / test data;
- информацию о применимых автоматизированных проверках;
- результат Code Review, если он предусмотрен workflow;
- известные ограничения, способные повлиять на проверку.

Технические доказательства, относящиеся к внутренней реализации, проверяются owner / Code Reviewer. QA может использовать их как prerequisite или evidence, но не обязан проводить повторный аудит внутренней реализации.

Задача может быть возвращена без Product / QA Acceptance, если переданный результат невозможно воспроизвести или однозначно проверить.

# 4. F-06 — Teacher / Student / Authentication

## 4.1. Что должно быть передано

Для проверки F-06 должен существовать работоспособный результат, позволяющий проверить:

- регистрацию Teacher;
- регистрацию Student;
- login;
- получение текущего пользовательского контекста;
- разграничение ролей `TEACHER` / `STUDENT`;
- demo data для дальнейших сценариев Sprint 1.

До передачи разработчик / Code Reviewer подтверждает технические prerequisites:

- password не хранится в открытом виде;
- необходимые структуры хранения данных воспроизводимо создаются на чистом окружении;
- demo data воспроизводимо создаются;
- автоматизированные positive / negative tests, предусмотренные задачей, проходят;
- критические Code Review comments закрыты.

QA / Product Reviewer не обязан повторно ревьюить hashing implementation, migrations, ORM-модели, структуру таблиц или Backend architecture.

## 4.2. Acceptance Criteria

### AC-F06-01 — Регистрация Teacher

**Given:** используется новый корректный email.

**When:** пользователь регистрируется с ролью `TEACHER` и корректными обязательными данными.

**Then:**

- регистрация завершается успешно;
- созданный пользователь имеет роль `TEACHER`;
- возвращаются корректные данные пользователя;
- password не возвращается в response.

### AC-F06-02 — Регистрация Student

**Given:** используется новый корректный email.

**When:** пользователь регистрируется с ролью `STUDENT` и корректными обязательными данными.

**Then:**

- регистрация завершается успешно;
- созданный пользователь имеет роль `STUDENT`;
- возвращаются корректные данные пользователя;
- password не возвращается в response.

### AC-F06-03 — Валидация регистрационных данных

Регистрация должна отклоняться при нарушении обязательных правил, включая применимые случаи:

- отсутствует обязательное поле;
- email имеет некорректный формат;
- роль отличается от `TEACHER` / `STUDENT`;
- `first_name` либо `last_name` после trim пусты;
- password короче 8 символов;
- password длиннее 128 символов.

Ошибка должна соответствовать согласованному API contract.

### AC-F06-04 — Уникальность email

**Given:** пользователь с email уже зарегистрирован.

**When:** выполняется повторная регистрация с тем же email, включая эквивалентный вариант с другим регистром или внешними пробелами.

**Then:**

- второй пользователь не создаётся;
- API возвращает согласованный conflict response.

### AC-F06-05 — Login

**Given:** существует зарегистрированный пользователь.

**When:** переданы корректные email и password.

**Then:**

- login завершается успешно;
- Frontend / API получает действующий access credential согласно контракту.

### AC-F06-06 — Неверные credentials

При неизвестном email или неверном password:

- login отклоняется;
- публичный response не раскрывает, существует ли пользователь с указанным email;
- оба случая имеют одинаковую публичную семантику `invalid_credentials`.

### AC-F06-07 — Current User

**Given:** пользователь успешно аутентифицирован.

**When:** выполняется `GET /api/v1/me`.

**Then:**

- Backend определяет текущего пользователя из authentication context;
- возвращается корректный `id`;
- возвращается корректный `email`;
- возвращается корректная роль;
- возвращаются `first_name`, `last_name`, `middle_name`;
- клиент не выбирает текущего пользователя передачей произвольного user ID.

### AC-F06-08 — Защищённый контекст

Защищённый запрос без действующей authentication не должен считаться выполненным от имени какого-либо пользователя.

API возвращает согласованную authentication error.

### AC-F06-09 — Demo data

В воспроизводимом demo / test environment доступны:

- минимум 1 Teacher;
- минимум 3 Students;
- данные, позволяющие в последующих User Story проверить связанную пару Teacher–Student;
- данные, позволяющие проверить недоступного текущему Teacher Student.

Конкретный внутренний способ хранения relation не является предметом Product / QA Acceptance.

## 4.3. PASS / FAIL

`F-06 = PASS`, если:

- `AC-F06-01–AC-F06-09` выполнены;
- обязательный внешний контракт F-06 соблюдается;
- нет дефектов, нарушающих обязательные Acceptance Criteria, согласованный внешний контракт, безопасность или целостность данных;
- передача результата воспроизводима.

`F-06 = FAIL`, если хотя бы один обязательный AC не выполнен.

Наличие дополнительной auth / profile / invitation / connection функциональности не компенсирует невыполнение F-06.

# 5. F-07 — Минимальная UI/UX-база

## 5.1. Что должно быть передано

Для Product Review должен быть доступен согласованный UI/UX artifact, достаточный для реализации пользовательских сценариев Sprint 1.

Это может быть Figma либо другой согласованный design artifact.

До Product Review ответственный за реализацию / Frontend owner подтверждает, что предложенные решения технически реализуемы в рамках Sprint 1.

Product Reviewer не отвечает за способ реализации UI-компонентов во Frontend.

## 5.2. Acceptance Criteria

### AC-F07-01 — Базовая структура

Определены:

- базовая grid / layout;
- основные spacing rules;
- типографика;
- базовые визуальные правила.

Решения должны быть достаточно однозначны для дальнейшей Frontend-реализации.

### AC-F07-02 — Базовые компоненты

Определены необходимые для Sprint 1 состояния и внешний вид минимум следующих элементов:

- button;
- input;
- select;
- date/time input.

Дополнительные компоненты могут быть добавлены без отдельного Product Acceptance, если они не изменяют согласованное пользовательское поведение.

### AC-F07-03 — UI states

Для применимых пользовательских сценариев определены состояния:

- normal;
- loading;
- error;
- empty;
- success feedback.

Состояния должны быть различимы пользователем и не противоречить требованиям Sprint 1.

### AC-F07-04 — Человекочитаемое представление

Teacher и Student в пользовательском интерфейсе должны быть представлены человекочитаемо.

Технический UUID не используется как единственная подпись пользователя.

### AC-F07-05 — Desktop-first / responsive

Определён desktop-first интерфейс и понятен базовый подход к поведению интерфейса при изменении доступной ширины.

Product Acceptance не требует отдельного pixel-perfect дизайна для всех возможных размеров экрана, если это не определено отдельной задачей.

### AC-F07-06 — Соответствие сценариям Sprint 1

UI/UX base не должен блокировать реализацию обязательных пользовательских сценариев Sprint 1.

Если design требует поведения, отсутствующего в согласованных requirements / contracts, такое поведение сначала уточняется как изменение требований.

### AC-F07-07 — Handoff

Frontend owner имеет доступ к актуальным UI/UX materials и подтвердил, что материалов достаточно для начала / продолжения реализации.

## 5.3. Что не проверяется Product Review

В рамках F-07 Product Reviewer не проверяет:

- React component architecture;
- CSS implementation;
- структуру Frontend-проекта;
- выбор UI library;
- state management implementation;
- техническую адаптивность конкретного кода;
- внутреннюю реализацию design system.

Эти вопросы находятся в зоне Frontend implementation / Code Review.

## 5.4. PASS / FAIL

`F-07 = PASS`, если:

- `AC-F07-01–AC-F07-07` выполнены;
- обязательные пользовательские сценарии имеют достаточную UI/UX-основу;
- критические Product Review comments устранены либо явно согласованы как отдельный change.

`F-07 = FAIL`, если design не покрывает обязательный элемент / состояние либо противоречит согласованному пользовательскому поведению.

# 6. F-08 — Frontend ↔ Backend Integration

## 6.1. Что должно быть передано

Для QA должен быть доступен совместно работающий Frontend + Backend на конкретной проверяемой версии.

Проверка выполняется на реальном HTTP exchange.

Mock-only реализация не считается достаточным результатом F-08.

До передачи исполнители подтверждают:

- Frontend и Backend запускаются воспроизводимо;
- необходимые automated tests проходят;
- взаимный Frontend / Backend Code Review завершён по принятому workflow;
- критические review comments закрыты.

QA не проводит повторный аудит внутренней реализации HTTP-клиента, CORS middleware, token parser или Backend architecture.

## 6.2. Acceptance Criteria

### AC-F08-01 — Реальный HTTP exchange

Frontend выполняет реальный запрос к Backend и получает фактический Backend response.

Mock response не используется как доказательство выполнения критерия.

### AC-F08-02 — Environment configuration

Backend origin может быть задан через environment configuration.

Проверяемая сборка не должна зависеть от случайного локального адреса конкретного разработчика как единственного способа работы.

### AC-F08-03 — API base path

Интеграционный flow использует согласованный `/api/v1` contract.

Frontend и Backend используют совместимые method, path и DTO.

### AC-F08-04 — Authentication flow

Должен воспроизводиться минимальный positive flow:

```text
Frontend
→ login
→ Backend
→ успешный TokenDTO
→ Frontend выполняет защищённый /me request
→ Backend определяет текущего пользователя
→ Frontend получает и отображает корректные данные пользователя
```

### AC-F08-05 — Trusted identity

Frontend не должен выбирать текущего пользователя передачей произвольного идентификатора.

Backend определяет identity защищённого запроса из authentication context.

### AC-F08-06 — Authentication error

Должен воспроизводиться negative flow:

```text
Frontend
→ protected request без действующего credential
→ Backend
→ 401 authentication_required
→ Frontend корректно обрабатывает ошибку
```

Пользователь не должен получать ложное успешное состояние.

### AC-F08-07 — ErrorDTO

Для ожидаемой Backend error Frontend способен обработать согласованный ErrorDTO.

Логика обработки не должна зависеть от точного текста `error.message`, если существует стабильный `error.code`.

### AC-F08-08 — Transport / compatibility failure

Frontend безопасно обрабатывает ситуацию, когда корректный Backend ErrorDTO получить невозможно, например:

- network failure;
- CORS failure;
- non-JSON response;
- несовместимый response DTO.

Такой случай не должен отображаться как успешная операция.

### AC-F08-09 — CORS

При согласованном Frontend origin браузер не блокирует штатный Frontend ↔ Backend flow из-за CORS.

Конкретный способ настройки CORS является ответственностью разработчиков.

### AC-F08-10 — Пользовательский результат

При успешном Foundation smoke flow пользователь видит корректные данные текущего пользователя в интерфейсе.

Технический HTTP `200` без корректной обработки результата Frontend не является достаточным подтверждением F-08.

## 6.3. Что не проверяется QA

В рамках F-08 QA не отвечает за:

- устройство HTTP-клиента;
- структуру Frontend services / hooks;
- Backend layers;
- CORS implementation;
- token parsing implementation;
- конкретную auth library;
- внутренний exception mapping;
- способ организации environment files;
- архитектурные конфликты между Frontend и Backend.

Если выбранные разработчиками технические решения несовместимы между собой и из-за этого Acceptance Criteria не выполняются, результат F-08 получает `FAIL` либо `BLOCKED` по фактической ситуации; устранение технического конфликта находится в зоне ответственности исполнителей.

## 6.4. PASS / FAIL

`F-08 = PASS`, если:

- `AC-F08-01–AC-F08-10` выполнены;
- реальный Frontend ↔ Backend smoke flow воспроизводится;
- positive и обязательный negative flow работают;
- фактический exchange соответствует согласованному внешнему контракту;
- нет дефектов, нарушающих обязательные Acceptance Criteria, согласованный внешний контракт, безопасность или целостность данных.

`F-08 = FAIL`, если хотя бы один обязательный AC не выполнен.

Дополнительные работающие страницы или функции Frontend / Backend не компенсируют сломанную обязательную интеграцию.

# 7. Дефект или изменение требования

Отклонение считается дефектом, если фактический результат не соответствует уже согласованному:

- requirement;
- business rule;
- external contract;
- Acceptance Criterion.

Новое пожелание, которого не было в согласованном scope, не считается дефектом автоматически и оформляется как изменение / новая задача.

Разработчик не обязан угадывать отсутствующее требование.

Product Owner / Analyst, в свою очередь, не обязан принимать реализацию, которая расходится с уже согласованным требованием только потому, что технически она была реализована другим способом.

# 8. Итоговое правило Acceptance

Для задач, описанных этим документом:

`Implemented` не означает `Accepted`.

`Code Review passed` не означает `QA passed`.

`QA passed` не подтверждает внутреннюю архитектуру.

`Additional features implemented` не означает `required scope completed`.

Задача принимается только тогда, когда обязательный результат соответствует согласованным требованиям и всем применимым Acceptance Criteria.
