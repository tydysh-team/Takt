# Соглашения по документированию API

[К документации](../README.md) · [Бизнес-правила](../requirements/business-rules.md)

Документ задаёт стандарт описания контрактов Frontend ↔ Backend. Окончательные endpoints, схемы данных и механизм аутентификации пока не определены. Ниже нет утверждённых маршрутов API.

## Структура контракта

Для каждой операции заполняются все разделы. Если раздел неприменим, указывается «Не применяется» с краткой причиной; нерешённые вопросы отмечаются `TBD / требуется согласование`.

| Раздел | Что фиксировать |
| --- | --- |
| Назначение | Пользовательский результат, связанная US / F-задача и бизнес-правила. |
| HTTP method и path | Метод, полный шаблон пути, статус согласования. |
| Аутентификация | Нужна ли она, допустимые роли, способ передачи данных аутентификации и определения текущего пользователя. |
| Path-параметры | Имя, тип, обязательность, смысл, ограничения и пример каждого параметра пути. |
| Query-параметры | Имя, тип, обязательность, значение по умолчанию, ограничения и пример каждого параметра запроса. |
| Request body | Content-Type, схема, обязательность полей, типы, допустимость null, ограничения и пример. Для отсутствующего тела — явная отметка. |
| Успешный ответ | HTTP-код, заголовки при необходимости, схема тела и смысл результата. |
| Валидация | Проверки формата, обязательности, связей, доступа и бизнес-правил; ссылки на BR и зависимые Q. |
| Ошибки | Для каждого случая: причина, HTTP-код, схема тела, ожидаемая реакция клиента. |
| Пример запроса | Метод, путь, параметры, необходимые заголовки и тело с согласованными полями. |
| Пример ответа | HTTP-код и тело, соответствующие схеме; примеры существенных ошибок. |
| Открытые решения | Что требует согласования и какие части контракта от этого зависят. |

Контракт считается согласованным только после определения всех деталей, необходимых для его реализации и проверки. Примеры используют вымышленные данные и не содержат реальные пароли или токены.

## Именование и JSON

- Использовать термины Teacher, Student и Lesson в значении из [глоссария](../glossary.md).
- Технические имена полей и параметров писать на английском; одинаковое понятие именовать одинаково во всех контрактах.
- Стиль имён полей и параметров (`snake_case` или `camelCase`), правила путей и версионирование API — **TBD / требуется согласование**. Не смешивать варианты после выбора.
- Для JSON-тел указывать `Content-Type: application/json`; JSON-примеры должны быть синтаксически корректными, без комментариев и завершающих запятых.
- Явно различать отсутствие поля, `null`, пустую строку и пустой массив. Допустимость каждого варианта задаётся схемой.
- Документировать тип и формат идентификаторов; не предполагать UUID или числовой тип до согласования.
- Формат коллекций, общая оболочка ответа и единая структура ошибок — **TBD / требуется согласование**. Пагинация не считается обязательной без отдельного требования.

## Даты и время

В контрактах использовать ISO 8601. Календарную дату описывать как `YYYY-MM-DD`, момент времени — строкой с датой, временем и явным смещением либо `Z`. Примеры формата: `2026-10-05`, `2026-10-05T10:00:00+04:00`, `2026-10-05T06:00:00Z`. Смещение в примере не задаёт часовой пояс продукта.

Для каждого поля указывать, является ли оно датой или моментом времени, точность и правила преобразования. Локализованные строки для отображения в интерфейсе не использовать как формат обмена.

Часовой пояс продукта и нормализация — Q-01; сравнение с текущим моментом — Q-02; тип и включение границ календарного периода — Q-03. До их согласования не фиксировать конкретную семантику фильтров. Длительность и время окончания Lesson зависят от Q-04.

## Принципы HTTP-кодов

Код должен отражать результат операции; ошибку нельзя маскировать успешным ответом. В каждом контракте перечисляются фактически используемые коды и условия их возврата.

| Код | Принцип применения |
| --- | --- |
| 200 OK | Успешная операция с телом ответа, включая пустую коллекцию при успешном чтении списка. |
| 201 Created | Успешное создание ресурса. |
| 204 No Content | Успешная операция без тела ответа, если это предусмотрено контрактом. |
| 400 Bad Request / 422 Unprocessable Content | Ошибки входного запроса; распределение случаев между кодами требует согласования. |
| 401 Unauthorized | Отсутствующая или недействительная аутентификация для защищённой операции. |
| 403 Forbidden | Пользователь определён, но операция ему недоступна. |
| 404 Not Found | Запрошенный ресурс не найден. Политика ответа для недоступного чужого ресурса требует согласования. |
| 409 Conflict | Конфликт с состоянием ресурса, только если такой случай предусмотрен согласованным контрактом. Не вводит проверку конфликтов расписания в Sprint 1. |
| 500 Internal Server Error | Непредвиденная ошибка сервера; ответ не раскрывает внутренние данные реализации или секреты. |

Точные коды для ошибок бизнес-проверок, включая недопустимый выбор Student, задаются при согласовании соответствующего контракта.

## Примеры запросов и ответов

В каждом конкретном контракте обязательны парные примеры запроса и успешного ответа, а также примеры предусмотренных ошибок. Пример запроса должен показывать метод, согласованный путь, параметры, заголовки и тело; пример ответа — код, заголовки при необходимости и тело согласно схеме.

Конкретные примеры операций US-01–US-03 — **TBD / требуется согласование** вместе с маршрутами и схемами. Фиктивные endpoints и поля здесь не вводятся. Перед реализацией проверить соответствие примеров валидации, правилам доступа, фильтрации и сортировки из [Sprint 1](../sprints/sprint-01/scope.md).
