# Review

## Виды проверки

| Вид | Вопрос | Результат |
| --- | --- | --- |
| Code Review | Корректны ли изменение и технические границы? | Замечания / принятое техническое ревью |
| Design Review | Соответствует ли дизайн сценариям, данным и состояниям? | Согласованный UI / UX и артефакт |
| QA | Работает ли результат по AC / BR и не сломаны ли затронутые сценарии? | Проверки, дефекты, retest |
| Product Review / Acceptance | Достигнут ли согласованный пользовательский результат? | Решение PO по приёмке |

Они не являются синонимами и не заменяют друг друга, даже если один участник выполняет несколько ролей.

## Обязанности ревьюера

Проверить корректность и scope, архитектурные границы, авторизацию и базовую безопасность, совместимость API / DTO, тесты и evidence, читаемость / именование, обновление документации и отсутствие случайных изменений. Для DB — целостность и влияние миграций, для UI — API-layer и состояния, для docs — каноничность и ссылки.

Не принимать «тесты зелёные» как доказательство выполнения неизвестного критерия. Не требовать новую библиотеку или архитектуру без конкретной необходимости. В замечании указать проблему, последствие и ожидаемый результат; отличать blocking issue от необязательного предложения.

## Работа с замечаниями

Автор отвечает и исправляет, либо согласует альтернативу. Неразрешённые comments блокируют merge по PR workflow. При споре о продукте обратиться к PO, о технической области — к владельцу области; сохранить принятое решение в каноническом документе.

Изменение API после review повторно проверяется участниками Frontend / Backend. Review не отмечается завершённым только потому, что PR открыт или review-thread механически закрыт.
