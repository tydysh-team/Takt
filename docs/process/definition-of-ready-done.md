# Definition of Ready / Definition of Done

[К справочнику](../README.md) · [Workflow](development-workflow.md) · [Technical Task](../templates/technical-task.md) · [Code Review](code-review.md) · [QA / Acceptance](qa-and-acceptance.md)

## Назначение

Definition of Ready (DoR) определяет минимальную готовность задачи к активной разработке.

Definition of Done (DoD) определяет минимальные условия, при которых задача может считаться завершённой.

DoR / DoD применяются с учётом типа работы. Неприменимый пункт помечается `N/A` с краткой причиной. `N/A` означает отсутствие применимости, а не успешно выполненную проверку.

Фактические owner, reviewer, Story Points, зависимости, blockers и состояние задачи подтверждаются в Sprint Planning / Kaiten. Этот документ не назначает их автоматически.

## Definition of Ready

До перевода Technical Task в активную разработку должны быть определены все применимые пункты.

### 1. Идентификация и scope

- Есть ID / название задачи.
- Указан parent: User Story либо Foundation, если применимо.
- Сформулирована цель задачи и ожидаемый результат.
- Scope ограничен и понятен исполнителю.
- Out-of-scope зафиксирован там, где возможна неоднозначность.
- Acceptance Criteria проверяемы и соответствуют parent scope.

Задача не считается Ready, если её ожидаемый результат можно понять только из устного объяснения автора.

### 2. Ответственность и планирование

- Назначен owner.
- Назначен reviewer.
- Определены применимые QA / Product Review.
- Зафиксирована оценка Story Points, если задача оценивается в Sprint Planning.
- Известны зависимости от других задач / артефактов.
- Активные blockers отсутствуют либо задача остаётся не Ready.

Общие зоны ответственности команды не заменяют назначения в конкретной карточке.

### 3. Требования и решения

- Есть ссылки на актуальные BR / AC / scope.
- Все продуктовые решения, без которых нельзя корректно реализовать задачу, приняты.
- Нерешённый product blocker не заменён предположением разработчика.
- Неблокирующий implementation choice I-* либо уже определён, либо явно входит в scope задачи и может быть выбран без изменения согласованного продуктового поведения / внешнего контракта.
- Если выбор становится существенным архитектурным решением, применяется ADR process.

### 4. API и интеграционные границы

Если задача создаёт или изменяет Frontend ↔ Backend обмен:

- определены method / path;
- authentication / role requirements;
- request DTO;
- response DTO;
- success HTTP status;
- ожидаемые error statuses и стабильные `error.code`;
- time semantics;
- sorting / pagination semantics, если применимо;
- согласованный контракт зафиксирован в `docs/api/contracts/`.

Backend и Frontend не начинают параллельную реализацию неизвестных частей контракта независимо друг от друга.

### 5. UI / UX

Если задача затрагивает пользовательский интерфейс:

- определён пользовательский сценарий;
- известны необходимые состояния `loading / empty / error / success`, если применимо;
- согласован design / UX-артефакт там, где он необходим;
- понятны человекочитаемые данные, которые должен видеть пользователь;
- нет требования придумывать отсутствующие DTO или product behavior внутри Frontend.

Отсутствие design блокирует только ту часть реализации, которая действительно зависит от неизвестного UI/UX-решения.

### 6. Данные и persistence

Если задача меняет данные:

- понятны затронутые entities / fields / relations;
- определены необходимые DB constraints;
- понятно, нужна ли Alembic migration;
- определено влияние на seed / demo / test fixtures;
- изменение согласовано с канонической моделью данных.

Persistence model не используется как неявная замена публичному API DTO.

### 7. Проверки

До старта понятно, как будет подтверждаться результат:

- какие unit / API / persistence / integration tests применимы;
- какие ручные проверки необходимы;
- какие временные / permission / validation boundaries нужно проверить;
- какое evidence должно остаться после выполнения.

Задача с неизвестным критерием успеха не считается Ready.

## Что не делает задачу Ready

Само по себе недостаточно:

- создать карточку;
- назначить исполнителя;
- поставить Story Points;
- открыть branch;
- начать писать каркас;
- иметь частично определённый API;
- иметь mock без согласованного DTO;
- договориться устно о критичной детали без обновления канонического источника.

Если независимую подготовительную часть можно выполнять безопасно, она оформляется отдельным ограниченным scope, а не используется как основание считать всю blocked-задачу Ready.

# Definition of Done

Задача может быть переведена в Done только после выполнения всех применимых пунктов.

## 1. Scope и Acceptance Criteria

- Реализован / подготовлен весь согласованный scope задачи.
- Out-of-scope не был незаметно включён в реализацию.
- Все применимые Acceptance Criteria проверены.
- Результат соответствует актуальным BR и утверждённым решениям.
- Если scope был изменён в ходе работы, изменение прошло [change management](change-management.md), а задача и связанные документы синхронизированы.

Частично выполненная задача не становится Done из-за завершения её наиболее простой части.

## 2. Качество реализации

Для кода по применимости:

- локальный запуск / build выполняется;
- применимые automated tests добавлены или обновлены;
- применимые tests проходят;
- error paths обработаны согласно контракту;
- отсутствуют случайные debug artifacts;
- secrets, credentials и private data не добавлены в repository / logs / evidence;
- environment-specific значения не захардкожены там, где должны задаваться config;
- код соответствует согласованным architecture / API boundaries.

Не требуется вводить новую библиотеку, abstraction или automation только ради формального пункта DoD.

## 3. Данные и миграции

Если задача меняет persistence:

- модель данных обновлена;
- Alembic migration добавлена и проверена, если требуется;
- constraints соответствуют бизнес-инвариантам;
- seed / demo / test data обновлены по необходимости;
- rollback / failure не оставляет заведомо частичное состояние для атомарной операции;
- API DTO и persistence model не смешаны.

## 4. API / Frontend ↔ Backend compatibility

Если затронут внешний обмен:

- фактические method / path соответствуют утверждённому контракту;
- request / response DTO совпадают с контрактом;
- HTTP status и `error.code` совпадают с реестром;
- runtime OpenAPI не противоречит утверждённому API-контракту;
- time semantics сохранены;
- Frontend использует централизованный API-layer;
- выполнена реальная integration-проверка, а не только независимые mocks.

Breaking change не может считаться Done, если зависимые потребители и документация не обновлены согласованным образом.

## 5. Review

- Автор выполнил self-review diff.
- Pull Request содержит достаточный context и evidence.
- Назначенный review завершён.
- Все blocking review comments закрыты по существу.
- Значимые изменения после review были повторно проверены.

Механическое закрытие discussion thread не означает устранение проблемы.

## 6. QA

Если QA применима:

- проверены Acceptance Criteria и BR;
- проверены необходимые positive / negative scenarios;
- permissions / authentication проверены там, где применимо;
- временные границы и error cases проверены там, где применимо;
- исправленные дефекты прошли retest;
- выполнена необходимая regression затронутого поведения;
- evidence относится к актуальной версии / commit результата.

Blocker / Critical defect несовместим с Done.

Major defect, нарушающий Acceptance Criteria, также несовместим с Done соответствующей задачи.

## 7. Product Acceptance

Если задача даёт пользовательский результат либо для неё назначена Product Acceptance:

- Product Owner проверил результат в согласованном scope;
- замечания Product Acceptance либо устранены, либо явно классифицированы как новый change request;
- новый запрос не маскируется под дефект старых Acceptance Criteria.

Для чисто технической или служебной задачи Product Acceptance может быть `N/A`, если причина понятна и зафиксирована.

## 8. Документация

- Канонические документы обновлены, если реализация изменила описанное поведение.
- Нет известного расхождения между BR, architecture, API contracts и фактической реализацией в scope задачи.
- Относительные ссылки в изменённых docs корректны.
- Существенное архитектурное решение оформлено через ADR, если критерии ADR применимы.
- Временный implementation detail не превращён в продуктовый requirement без решения PO.

Документация должна описывать фактическое согласованное поведение, а не желаемый будущий статус реализации.

## 9. Evidence и фактический статус

В карточке / связанных артефактах доступны применимые ссылки:

- Pull Request;
- commit / branch либо merged result;
- test results;
- integration evidence;
- QA evidence;
- design;
- обновлённые docs;
- defect / change cards.

Kaiten отражает фактическое состояние работы.

Merge PR сам по себе не является доказательством выполнения QA, Product Acceptance или полного DoD.

## Остаточные дефекты

Minor либо иной действительно неблокирующий дефект может остаться после согласования только если:

- он не нарушает Acceptance Criteria завершённой задачи;
- зарегистрирован отдельной карточкой;
- severity / impact описаны честно;
- решение о допустимости принято применимыми участниками, включая PO при продуктовом влиянии.

Нельзя снижать severity только ради перевода задачи в Done.

## Повторная проверка после изменений

Если после успешно выполненной проверки код / contract / design / requirement изменился, необходимо повторить все проверки, на которые изменение могло повлиять.

Старое evidence не считается актуальным автоматически.

Примеры:

- изменён API DTO → повторный Code Review, contract check и Frontend ↔ Backend integration;
- изменено BR → повторные затронутые tests, QA и при необходимости Product Acceptance;
- изменена migration → повторная persistence / migration проверка;
- исправлен UI без изменения API → повторная проверка затронутых UI states и QA.

## DoD для разных типов задач

DoD применяется по смыслу, а не механически.

- **Documentation:** consistency, каноничность, ссылки, отсутствие противоречий, review diff.
- **Design:** покрытие сценариев / состояний, Design Review, связь с требованиями.
- **Backend / Frontend code:** применимые tests, review, contracts, integration, QA.
- **Database / migration:** schema integrity, migration, fixtures, persistence tests.
- **QA task:** определённые проверки, reproducible evidence, defects / retest.
- **Process / tooling:** воспроизводимость, документированный usage, отсутствие скрытого изменения product scope.

`N/A` требует причины, но не требует искусственного выполнения нерелевантной работы.

## Parent User Story / Foundation

Done отдельной Technical Task не означает автоматически Done её parent User Story / Foundation.

Parent может считаться завершённым только когда:

- завершены все обязательные дочерние работы;
- интегрирован их совместный результат;
- выполнены parent Acceptance Criteria;
- завершены применимые QA / Product Acceptance;
- отсутствуют блокирующие зависимости / дефекты.

Общие DoR / DoD каноничны в этом документе. Technical Task может добавлять более конкретные проверки, но не может молча ослаблять эти требования.
