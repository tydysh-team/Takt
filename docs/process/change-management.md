# Управление изменениями

[К справочнику](../README.md) · [ADR](../architecture/decisions/README.md)

Изменение обновляет канонический источник и все зависимые артефакты. Его инициатор фиксирует причину и затронутые задачи в Kaiten; владельцы областей определяют impact до реализации. Нельзя вводить новые правила молча в коде, UI или тестах.

| Изменение | Канонический источник / согласование | Зависимые материалы |
| --- | --- | --- |
| Продуктовое требование / BR | Product docs / BR, решение PO | Scope, AC, tasks, API / UI / QA при влиянии |
| API или DTO | Контракт и общие API-правила; Backend + Frontend, PO при изменении поведения | OpenAPI, API-layer types / mocks, UI mapping, тесты |
| DB model | Модель данных, Backend / DB owner; PO для новых доменных данных | Миграционная задача, DTO при влиянии, demo data, persistence-тесты |
| Архитектура | ADR и соответствующая architecture page | Module boundaries, setup / tasks / проверки |
| UX/UI после начала реализации | Утверждённый дизайн и Design Review; PO для поведения | UI task, данные / API при влиянии, AC и QA |
| Scope спринта | Sprint planning / Kaiten и scope page, PO + команда | Оценка, зависимости, задачи и отчётные ссылки |

## Порядок

1. Описать before / after, причину и affected artifacts.
2. Проверить, меняет ли это продукт, сроки, contract compatibility или данные.
3. Получить решение нужных участников; blocker отражать в карточке.
4. Обновить каноническую спецификацию и связанные задачи / критерии.
5. Реализовать согласованные изменения в feature-ветке с PR.
6. Выполнить review, применимые проверки, regression и acceptance; приложить evidence.

Breaking API-change во время параллельной разработки довести до Backend и Frontend до merge: через связанную Kaiten-карточку и явное описание PR, с подтверждением согласованного перехода. Указать, какая редакция контракта используется, очередность обновления и проверку совместимости. Нельзя считать человека уведомлённым только потому, что поле изменилось в OpenAPI.

Совместимость и порядок версионирования определены в [интеграции](../architecture/integration.md#изменения-и-совместимость). История существенных решений остаётся в ADR; устаревшая запись получает ссылку на заменяющую, а не удаляется бесследно.
