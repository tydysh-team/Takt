# QA и Product Acceptance

[К справочнику](../README.md) · [Bug report](../templates/bug-report.md)

## Подготовка и evidence

QA выводит проверки из AC, BR и контрактов. Указать редакцию требований, branch / commit, окружение, данные и ожидаемый результат. Не тестировать неопределённое поведение как будто оно утверждено: Product blocker сначала возвращается на уточнение.

Минимальный набор по применимости:

- Позитивный сценарий и сохранение / получение ожидаемых данных.
- Негативные: неверные поля, аутентификация, роль, чужие ресурсы, HTTP / сетевые ошибки.
- Границы: равенство now, from / to, соседние диапазоны, offsets и DST при локальном календаре.
- API: код, DTO, стабильный error.code, безопасное тело ошибки, пустой список.
- UI: loading / empty / error / success; состояние отправки и повторные действия.
- Интеграция: Teacher создаёт Lesson → запись сохранена → соответствующие выборки Student / Teacher обновляются.
- Регрессия затронутого поведения; не объявлять неподтверждённый будущий контур проверенным.

Для Backend применяется pytest; ручные acceptance / checklists документируются с evidence. Frontend / E2E automation вводится по необходимости. Моковый UI не подтверждает реальный сквозной запрос.

## Severity и priority

| Severity | Значение |
| --- | --- |
| Blocker | Ключевой сценарий / проверка недоступен без обходного пути |
| Critical | Потеря / повреждение данных, нарушение доступа или тяжёлый отказ основного сценария |
| Major | Существенное нарушение AC / поведения, возможен ограниченный обход |
| Minor | Малое визуальное / текстовое отклонение без разрушения основного сценария |

Severity описывает влияние, priority — порядок исправления, согласуемый командой / PO. Не снижать severity только из-за нехватки времени.

## Жизненный цикл дефекта

Зарегистрирован → triage → назначен → исправление → retest → закрыт; если ошибка воспроизводится — reopened. Это логические состояния, не новая обязательная конфигурация Kaiten. Карточка содержит [поля bug template](../templates/bug-report.md), affected task / US, evidence и условия.

QA перепроверяет исправленный сценарий и затронутую регрессию на указанном commit. Автор исправления не заменяет retest обещанием. Дубликат / отклонение закрываются с причиной и ссылкой на решение.

## Product Acceptance

После применимой QA PO проверяет пользовательский результат, границы и известные дефекты. Результат — принято либо возвращено с конкретным несоответствием / новым change request. Новое пожелание не объявляется дефектом старого согласованного AC автоматически.

Критерии завершения — [DoD](definition-of-ready-done.md). Kaiten остаётся источником task / defect workflow. TestRail, если принят командой, хранит подробные переиспользуемые test cases / runs; в карточках и docs — ссылки, без копирования одного набора в несколько систем.
