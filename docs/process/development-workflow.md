# Workflow разработки

[К справочнику](../README.md) · [DoR / DoD](definition-of-ready-done.md)

Логические этапы: Backlog / specification → Ready → Development → Code Review → Integration → QA → Product Acceptance → Done. Это общий flow, а не утверждение о точных названиях колонок существующей Kaiten-доски. Состояние хранится в Kaiten, доказательства — ссылками на документы, PR, проверки и дизайн.

| Этап | Работа и выход | Кто участвует |
| --- | --- | --- |
| Backlog / specification | Уточнить пользовательский результат, BR, AC, scope; разделить реализацию на Technical Tasks | PO / Analyst, владельцы Backend / Frontend, UX/UI по необходимости |
| Ready | Проверить применимые пункты DoR; явные blockers не скрываются | Исполнитель и ревьюер, PO для продуктовых решений |
| Development | Реализовать назначенную задачу в feature-ветке, выполнить локальные проверки, обновить документы | Назначенный исполнитель |
| Code Review | Проверить diff, корректность и договорённости; обработать замечания | Назначенный ревьюер и автор |
| Integration | Проверить реальный обмен и совместный результат, если задача затрагивает границы | Backend / Frontend участники интеграции |
| QA | Проверить AC / BR, ошибки и регрессию; зарегистрировать дефекты и retest | QA; исполнитель помогает воспроизводить |
| Product Acceptance | Подтвердить пользовательский результат и границы, если применимо | Product Owner |
| Done | Зафиксировать evidence по применимому DoD и фактическое состояние | Исполнитель / проверяющий по карточке |

Зоны команды — в [продукте](../product/overview.md#ответственность-команды). Вероника как Scrum Master помогает прозрачности workflow и блокеров, но не заменяет технического ревьюера, QA или PO.

## История и техническая задача

User Story описывает ценность для пользователя: например, Teacher создаёт Lesson. API-handler, DB migration, API-layer function или тестовый набор оформляются Technical Tasks с родительской US / Foundation, а не искусственными US «как разработчик…».

Назначения, SP и зависимости задаются на карточке и в planning, не выводятся автоматически из общих зон владения. Использовать [шаблон](../templates/technical-task.md). Foundation имеет собственный технический результат и не требует выдуманной пользовательской роли.

## Блокеры и переходы

Если обязательное решение отсутствует, задача возвращается на уточнение / получает blocker в Kaiten. Подготовительная работа оформляется отдельным ограниченным scope; нельзя считать всю US Ready потому, что можно создать каркас.

Integration / QA / Product Acceptance неприменимы некоторым документационным или служебным задачам; это отмечается с причиной. Пропуск этапа не означает проверку «passed». Merge PR и Done не тождественны: порядок merge и среды QA указывается в задаче; незавершённая приёмка не скрывается после merge. [PR workflow](branching-and-pr.md) определяет обязательный review перед merge.
