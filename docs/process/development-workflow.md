# Workflow разработки

[К справочнику](../README.md) · [DoR / DoD](definition-of-ready-done.md) · [Ветки и PR](branching-and-pr.md) · [Code Review](code-review.md) · [QA / Acceptance](qa-and-acceptance.md) · [Change Management](change-management.md)

## Назначение

Этот документ описывает логический flow работы над Technical Task / Foundation task / User Story от уточнения до Done.

Канонические источники разделены:

- **Kaiten** — фактическое состояние карточки, owner / reviewer, Story Points, зависимости и blockers;
- **GitHub** — ветка, commits, Pull Request, review и история изменений;
- **`/docs`** — согласованные продуктовые, архитектурные, API и процессные правила;
- **Figma / другой утверждённый design source** — UI/UX-решения после появления соответствующего артефакта.

Логический этап процесса не обязан иметь отдельную колонку на доске. Название колонки Kaiten само по себе не заменяет проверку gate criteria этапа.

## Основной flow

```text
Backlog / Specification
        ↓
Ready
        ↓
Development
        ↓
Code Review
        ↓
Integration
        ↓
QA
        ↓
Product Acceptance
        ↓
Done
```

Для конкретной задачи неприменимый этап допускается пропустить только с явной причиной. Пропущенный этап не считается `passed`.

## Этапы и критерии выхода

| Этап | Что происходит | Критерий выхода | Кто участвует |
| --- | --- | --- | --- |
| Backlog / Specification | Уточняются пользовательский результат, scope / out-of-scope, BR, AC, зависимости; работа декомпозируется на Technical Tasks | Применимые требования и зависимости достаточно определены для проверки DoR | PO / Analyst, применимые Backend / Frontend owners, UX/UI |
| Ready | Проверяется Definition of Ready и отсутствие скрытых блокеров | Все обязательные для старта пункты DoR выполнены либо явно помечены `N/A` с причиной; blocker отсутствует | Исполнитель, reviewer; PO для продуктовых решений |
| Development | Выполняется работа в отдельной ветке, локальные проверки, тесты и обновление зависимых документов | Scope реализован локально; автор выполнил self-review и подготовил evidence | Назначенный исполнитель |
| Code Review | Проверяется diff, архитектурные / API / coding agreements, тесты и документация | Blocking review comments закрыты; значимые изменения после замечаний перепроверены | Автор и назначенный reviewer |
| Integration | Проверяется фактическая работа затронутых границ системы | Реальный интеграционный сценарий проходит; mocks не являются единственным доказательством | Участники затронутых компонентов |
| QA | Проверяются Acceptance Criteria, BR, негативные сценарии и применимая regression | Блокирующие дефекты отсутствуют; исправленные дефекты прошли retest; evidence зафиксирован | QA; исполнитель помогает с воспроизведением |
| Product Acceptance | Проверяется пользовательский результат и соответствие согласованному scope | PO принимает результат либо фиксирует конкретные замечания | Product Owner |
| Done | Выполняется финальная проверка Definition of Done | Все применимые пункты DoD выполнены, evidence и фактический статус зафиксированы | Исполнитель / проверяющий по карточке |

Зоны общей ответственности команды описаны в [product overview](../product/overview.md#ответственность-команды). Они не заменяют конкретные назначения owner / reviewer / QA / Product Review в Sprint Planning и Kaiten.

Вероника как Scrum Master помогает поддерживать прозрачность flow, blockers и договорённостей процесса, но не подменяет технического reviewer, QA или Product Owner.

## User Story, Foundation и Technical Task

User Story описывает ценность для реального пользователя продукта.

Например:

> Teacher создаёт Lesson для связанного Student.

Техническая реализация этой ценности декомпозируется на Technical Tasks, например:

- API endpoint;
- DB migration;
- API-layer function;
- UI state;
- automated test;
- integration task.

Не создавать искусственные User Story вида «как разработчик, я хочу написать API».

Foundation task имеет самостоятельный технический результат и не требует выдуманной пользовательской роли.

Для Technical Task фиксируются применимые:

- parent User Story / Foundation;
- owner;
- reviewer;
- Story Points;
- dependencies;
- scope / out-of-scope;
- Acceptance Criteria;
- ссылки на BR / API / design;
- ожидаемые проверки.

Используется [шаблон Technical Task](../templates/technical-task.md).

Назначения, SP и зависимости берутся из актуального Sprint Planning / Kaiten, а не выводятся автоматически из общей зоны владения компонентом.

## Правило Ready

Карточка не считается Ready только потому, что разработчик технически может начать писать каркас.

Если для выполнения scope отсутствует обязательное продуктовое решение, API-контракт, дизайн или другая критическая зависимость:

1. blocker явно фиксируется;
2. задача не объявляется полностью Ready;
3. допустимая независимая подготовительная работа при необходимости выделяется в отдельный ограниченный scope.

Неблокирующий implementation choice I-* может быть уточнён внутри соответствующей Technical Task, если он не требует неизвестного продуктового решения и не меняет согласованный внешний контракт.

## Работа с blockers

Blocker должен быть видим в Kaiten и связан с конкретной причиной / зависимостью.

Не допускается:

- скрывать blocker внутри комментария без отражения фактического состояния задачи;
- заменять отсутствующее решение предположением исполнителя;
- переводить задачу дальше по flow только ради формального движения карточки;
- считать частично реализованный scope завершённой User Story.

После устранения blocker исполнитель повторно проверяет, не изменились ли:

- требования;
- API-контракт;
- design;
- зависимости;
- оценка / scope задачи.

Если изменились — применяются правила [change management](change-management.md).

## Возврат на доработку

Flow не является однонаправленным.

Если проблема обнаружена на Code Review, Integration, QA или Product Acceptance, задача возвращается на необходимый этап доработки.

После исправления повторно выполняются все проверки, которые могли быть затронуты изменением.

Примеры:

- изменение Backend DTO после review → повторный Code Review и Frontend ↔ Backend integration;
- исправление business rule → повторные применимые API / Service tests и QA;
- UI fix, влияющий только на отображение и не меняющий API → повторный UI review / QA в затронутом scope.

Нельзя считать старый `passed` evidence доказательством после изменения, которое могло сделать его неактуальным.

## Code Review и merge

Обычная разработка выполняется в feature / fix / docs branch согласно [branching-and-pr](branching-and-pr.md).

Pull Request проходит review до merge.

Merge и Done — разные события.

Merge допускается только при выполнении требований PR workflow и отсутствии блокирующих review issues. При этом merge сам по себе не означает, что:

- Integration завершена;
- QA завершена;
- Product Acceptance выполнена;
- задача соответствует DoD.

Конкретный порядок merge относительно Integration / QA зависит от доступного окружения и фиксируется в задаче, но незавершённые этапы не скрываются изменением статуса.

## Integration

Integration требуется, когда задача изменяет границу между компонентами или системами.

Для Frontend ↔ Backend применяется [integration contract](../architecture/integration.md).

Минимальный принцип:

- согласованный contract;
- фактический HTTP exchange;
- корректные success / error DTO;
- authentication / role context;
- применимая time semantics;
- проверка без зависимости только от двух независимых mocks.

Изменение только внутренней реализации компонента не требует искусственного integration evidence, если публичная граница действительно не затронута.

## QA и Product Acceptance

QA проверяет не только happy path, но и применимые:

- Acceptance Criteria;
- BR;
- permissions;
- validation / error cases;
- temporal boundaries;
- regression risks.

QA не заменяет Code Review.

Product Acceptance не заменяет QA: Product Owner подтверждает продуктовый результат и scope, а не выполняет техническое тестирование вместо QA.

Если Product Acceptance неприменима к чисто технической / служебной задаче, это отмечается с причиной. Пользовательская User Story не считается принятой только потому, что её отдельные Technical Tasks смержены.

## Done

Перед переводом в Done применяется [Definition of Done](definition-of-ready-done.md).

Для каждой задачи должны быть понятны:

- фактический реализованный scope;
- результаты применимых проверок;
- ссылки на PR / документы / design / test evidence;
- остаточные известные дефекты;
- причина для каждого неприменимого DoD-пункта.

Blocker / Critical defect и Major defect, нарушающий Acceptance Criteria, несовместимы с Done соответствующей задачи.

Согласованный неблокирующий остаточный дефект не скрывается: он должен иметь отдельную карточку и решение согласно QA / Product Acceptance process.

## Актуальность статуса

Статус карточки в Kaiten должен отражать фактическое состояние работы, а не желаемое.

Если GitHub, документация и Kaiten расходятся, команда сначала выясняет реальное состояние и затем синхронизирует источники. Нельзя использовать устаревшую колонку или старый PR как доказательство готовности.

При изменении process rules обновляется этот документ и связанные process artifacts согласно [change management](change-management.md).
