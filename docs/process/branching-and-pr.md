# Ветки, коммиты и Pull Request

[К справочнику](../README.md) · [Workflow](development-workflow.md) · [DoR / DoD](definition-of-ready-done.md) · [Code Review](code-review.md) · [Change Management](change-management.md)

## Назначение

Этот документ определяет правила работы с Git / GitHub для обычной разработки Takt.

GitHub хранит техническую историю изменений, ветки, commits, Pull Requests и review. Фактическое состояние задачи, owner / reviewer, Story Points, зависимости и blockers ведутся в Kaiten.

`main` — интеграционная / стабильная ветка проекта.

Обычная разработка не выполняется прямыми рабочими коммитами в `main`. Изменения попадают в `main` через Pull Request после применимого review.

## Ветки

Ветка создаётся под конкретную задачу или ограниченный связанный scope.

Примеры:

```text
feature/f-03-backend-init
feature/us01-t03-create-lesson-api
fix/lesson-timezone-validation
docs/api-contracts
```

Имя ветки описывает работу, а не имя исполнителя.

Рекомендуемые категории:

- `feature/` — новая функциональность или Foundation work;
- `fix/` — исправление дефекта;
- `docs/` — изменение документации;
- иная короткая категория допускается, если её смысл однозначен и согласован командой.

Не создавать одну долгоживущую ветку для несвязанных задач.

Если несколько задач зависят друг от друга, зависимости фиксируются в Kaiten / planning, а порядок интеграции согласуется до начала взаимозависимых изменений.

## Работа с чужими ветками

Не переписывать опубликованную историю чужой или совместной ветки без явной договорённости.

Не выполнять force push в совместную ветку, если это может уничтожить чужие commits или invalidate уже выполненный review, без согласования с участниками.

Не переключать / очищать чужой worktree и не удалять незакоммиченные изменения другого участника.

Если необходимо исправить конфликт или историю совместной ветки, сначала определить:

- кто владеет текущей рабочей копией;
- какие commits должны сохраниться;
- какой PR / review уже зависит от текущих SHA;
- кто уведомляется после изменения истории.

## Коммиты

Commit должен описывать законченное логическое изменение настолько, насколько это практично.

Примеры:

```text
docs: complete F-01 project documentation
feat: add lesson creation endpoint
fix: reject lesson start in the past
test: cover teacher calendar boundaries
```

Количество commits само по себе не является показателем качества.

Допускается один commit на небольшое связанное изменение либо несколько логических commits на более крупную задачу.

Не включать в commit:

- секреты / credentials;
- `.env` с реальными значениями;
- локальные IDE / OS artifacts, если они не являются согласованной частью repository;
- временные debug-файлы;
- случайные unrelated changes;
- реальные персональные данные в demo / test data.

Перед push автор проверяет как минимум:

- `git status`;
- состав staged files;
- diff;
- отсутствие случайного удаления / добавления файлов.

## Подготовка Pull Request

Перед открытием PR автор выполняет self-review.

PR должен иметь один понятный основной scope. Если diff содержит несколько независимых изменений, их следует разделить, если совместный review не имеет объективной причины.

PR содержит по применимости:

- краткий summary результата;
- ссылку на Technical Task / Foundation / User Story;
- scope и явно значимый out-of-scope;
- что изменено;
- как результат проверен;
- команды / test results либо иное evidence;
- API impact;
- DB / migration impact;
- UI / UX impact;
- документационные изменения;
- breaking changes;
- известные blockers / ограничения;
- связанные PR / зависимости, если есть.

Для API change PR ссылается на актуальный API contract.

Для изменения schema PR указывает применимую migration и влияние на data / fixtures.

Для UI change PR указывает связанный design / UX source, если он существует и применим.

Документация проходит review по тем же принципам, что и код: каноничность, consistency, ссылки и отсутствие противоречий являются частью качества diff.

## Draft PR

Draft PR допустим для раннего технического обсуждения или visibility незавершённой работы.

Draft PR не означает:

- выполненный Code Review;
- готовность к merge;
- прохождение QA;
- соответствие Definition of Done.

Перед финальным review PR должен содержать актуальный scope и достаточное evidence для проверки.

## Reviewer

Reviewer назначается в Sprint Planning / Kaiten либо явно согласуется для конкретной задачи.

Общая ownership-область не делает человека автоматически единственным допустимым reviewer.

Reviewer должен иметь достаточно контекста, чтобы проверить затронутые границы.

Если изменение затрагивает несколько областей, может потребоваться участие нескольких reviewers / owners, например:

- Backend + Frontend для изменения API contract;
- Backend / DB owner для migration;
- UX/UI + Frontend для значимого интерфейсного изменения;
- PO для изменения продуктового поведения.

Это не означает обязательное количество approvals для каждого PR; применимый состав определяется задачей и риском изменения.

## Review comments

Review comment должен описывать:

- проблему;
- возможное последствие;
- ожидаемый результат или критерий исправления.

Автор:

1. исправляет замечание; либо
2. аргументированно отвечает и согласует альтернативу.

Blocking review comment должен быть разрешён по существу до merge.

Механическое `Resolve conversation` без устранения / согласования проблемы не считается закрытием замечания.

После значимого изменения в ответ на review повторно проверяются затронутые части diff.

Если изменение после review затрагивает API / DB / архитектурную границу, соответствующий reviewer должен увидеть актуальную версию.

## Merge gate

Перед merge проверить применимые пункты:

- scope PR соответствует задаче;
- обязательный review завершён;
- blocking comments закрыты;
- применимые tests / проверки выполнены;
- branch не содержит случайных unrelated changes;
- документация обновлена, если поведение / контракт изменились;
- breaking change согласован и зависимые потребители обновлены;
- применимая Frontend ↔ Backend integration проверена в объёме, требуемом workflow;
- отсутствуют известные дефекты, которые по DoD блокируют завершение соответствующего изменения.

Merge не используется как способ обойти незавершённое review.

Кто физически выполняет merge, определяется командой / карточкой. Этот документ не назначает отдельного постоянного merge-owner.

## Merge и QA / Product Acceptance

Merge и Done — разные события.

В зависимости от доступного окружения часть Integration / QA может выполняться до или после merge.

Если QA / Product Acceptance выполняются после merge:

- их незавершённость остаётся видимой в Kaiten;
- задача не переводится в Done заранее;
- обнаруженный дефект возвращает работу в необходимый этап workflow;
- исправление проходит новый применимый PR / review.

Merge PR не является доказательством прохождения QA или Product Acceptance.

## После merge

После merge:

- убедиться, что целевая ветка содержит ожидаемое изменение;
- обновить фактический статус задачи в Kaiten;
- не помечать незавершённые QA / Product Acceptance как завершённые;
- связанные follow-up defects / changes оформить отдельными карточками;
- удалить рабочую ветку после merge, если она больше не нужна и это безопасно для текущего workflow.

Если merge создал необходимость синхронизации зависимой ветки, владелец зависимой работы обновляет её согласованным способом и повторяет затронутые проверки.

## Конфликты и актуальность ветки

Перед финальным merge PR должен быть совместим с актуальным состоянием target branch.

При разрешении merge conflict нельзя механически выбирать одну сторону без понимания семантики.

После conflict resolution автор повторно проверяет:

- затронутый diff;
- tests;
- contracts / docs;
- integration boundaries, если они могли измениться.

Если target branch изменила базовый API / schema / architecture contract, зависимая задача возвращается к проверке актуальности требований и DoR.

## Breaking changes

Нельзя молча менять в PR уже согласованную публичную границу:

- method / path;
- authentication requirement;
- request / response DTO;
- field type / required / nullable semantics;
- stable `error.code`;
- sorting;
- time semantics;
- database invariant, влияющий на внешний сценарий.

Breaking change проходит [change management](change-management.md), обновляет канонические документы и явно обозначается в PR.

## CI и автоматические проверки

Для текущего проекта этот справочник не объявляет обязательными конкретные:

- GitHub Actions workflows;
- branch protection rules;
- required status checks.

Если такие механизмы будут включены позже, фактическая repository configuration и process docs должны быть синхронизированы.

Отсутствие автоматического enforcement не отменяет обязательные manual / local checks, review и DoD.

Нельзя писать в PR, что CI прошёл, если соответствующего CI фактически нет или он не выполнял нужную проверку.

## Связь с Definition of Done

PR workflow подтверждает только часть DoD.

Даже успешно merged PR не делает Technical Task автоматически Done.

Финальное завершение определяется [Definition of Done](definition-of-ready-done.md), включая применимые Integration, QA, Product Acceptance, docs и evidence.
