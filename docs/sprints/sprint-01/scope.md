## US-01 — Создание занятия

Как Teacher, я хочу создать занятие для связанного со мной Student, чтобы запланировать учебную встречу.

Предусловия: Teacher аутентифицирован; в системе существует связанный с ним Student.

Минимальный сценарий:

1. Teacher выбирает существующего связанного Student.
2. Teacher задаёт дату и время занятия.
3. Frontend отправляет запрос в Backend.
4. Backend проверяет запрос, текущего Teacher и допустимость выбора Student.
5. Backend сохраняет Lesson в PostgreSQL.
6. Пользователь получает результат операции; при ошибке интерфейс сообщает о ней.

**AC-01:** корректный запрос создаёт Lesson для текущего Teacher и выбранного Student; некорректный запрос не создаёт Lesson и возвращает ошибку. Созданное занятие доступно в US-02 и US-03 при выполнении условий их выборки. Проверить отсутствующую аутентификацию, неверную роль, чужого / несуществующего Student, формат даты и подтверждённое сохранение.

Правила: [BR-01–BR-03](../../requirements/business-rules.md). Контракт: [API-05](../../api/contracts/sprint-01.md#api-05--создать-lesson), список учеников — API-04. Минимум Lesson содержит только starts_at, без длительности. Политика прошлой даты — Q-05; auth context — Q-07; подписи участников / зона UI — Q-09 / Q-10. Эти блокеры не подменяются предположениями.

## US-02 — Просмотр предстоящих занятий учеником

Как Student, я хочу видеть свои предстоящие занятия, чтобы знать время встречи и преподавателя.

Минимальный сценарий:

1. Система определяет текущего Student.
2. Backend выбирает его занятия с starts_at >= now, фиксируя now один раз на запрос в UTC; прошедшие занятия исключаются, равная граница включается.
3. Занятия возвращаются по starts_at ASC, id ASC.
4. Frontend отображает дату, время и Teacher каждого занятия.
5. Frontend поддерживает состояния загрузки, пустого списка и ошибки.

**AC-02:** Student видит только свои предстоящие занятия в указанном порядке; прошедшие отсутствуют; загрузка, пустой результат, ошибка и успешное отображение проверяемы. Проверить начало до, ровно на и после замороженного now, одинаковые моменты в разных offsets и чужого Student.

Правила: [BR-04–BR-06](../../requirements/business-rules.md). Контракт: [API-06](../../api/contracts/sprint-01.md#api-06--предстоящие-lesson-ученика). Технические Q-01 / Q-02 решены; человекочитаемый Teacher и локальное время UI — Q-09 / Q-10, доверенный контекст — Q-07.

## US-03 — Календарь преподавателя

Как Teacher, я хочу видеть свои занятия за выбранный период в календаре, чтобы ориентироваться в расписании.

Минимальный сценарий:

1. Система определяет текущего Teacher.
2. Пользователь выбирает календарный период.
3. Frontend преобразует выбранный период в абсолютные from / to по согласованной зоне и отправляет timezone-aware ISO 8601 значения.
4. Backend возвращает занятия текущего Teacher с from <= starts_at < to; from < to обязательно.
5. Frontend отображает занятия в календарном представлении.
6. Frontend поддерживает состояния загрузки, пустого календаря и ошибки.

**AC-03:** календарь показывает только занятия текущего Teacher, соответствующие периоду; изменение периода обновляет выборку без подмены запоздалым ответом; loading / empty / error / success проверяемы. Проверить включённый from, исключённый to, соседние периоды, offsets, неверный диапазон и чужого Teacher.

Правило: [BR-07](../../requirements/business-rules.md#br-07--календарная-выборка). Контракт: [API-07](../../api/contracts/sprint-01.md#api-07--lesson-в-календарном-периоде-teacher). Технические Q-01 / Q-03 решены; виды календаря / локальная зона — Q-10 и дизайн L-04, доверенный контекст — Q-07.

## За пределами Sprint 1

- Проверка конфликтов расписания.

## Ожидаемый результат

Подготовлена техническая основа Takt и проверен сквозной сценарий: аутентифицированный Teacher создаёт Lesson, Backend сохраняет его в PostgreSQL, Student видит его среди предстоящих занятий, а Teacher — в выбранном календарном периоде. Frontend и Backend интегрированы; для списков и календаря предусмотрены загрузка, пустое состояние и ошибка.

Документация отражает целевое поведение, не статус реализации. Блокирующие вопросы из [реестра решений](../../requirements/business-rules.md#открытые-решения) согласуются до реализации зависимых частей. Общепроектные архитектура, процесс и DoR / DoD описаны в [справочнике](../../README.md); они не расширяют scope спринта.
