## US-01 — Создание занятия

Как Teacher, я хочу создать занятие для связанного со мной Student, чтобы запланировать учебную встречу.

Предусловия: Teacher аутентифицирован; в системе существует связанный с ним Student.

Минимальный сценарий:

1. Teacher выбирает существующего связанного Student.
2. Teacher задаёт дату и время занятия.
3. Frontend отправляет запрос в Backend.
4. Backend проверяет запрос, текущего Teacher и допустимость выбора Student.
5. Backend сохраняет Lesson в PostgreSQL.
6. Пользователь получает результат операции; при ошибке интерфейс сообщает о ней.

Критерии приёмки: корректный запрос создаёт Lesson для текущего Teacher и выбранного Student; некорректный запрос не создаёт Lesson и возвращает ошибку. Созданное занятие доступно в US-02 и US-03 при выполнении условий их выборки.

Связанные правила: BR-01–BR-03. Ограничения даты/времени и длительность — Q-01, Q-04, Q-05.

## US-02 — Просмотр предстоящих занятий учеником

Как Student, я хочу видеть свои предстоящие занятия, чтобы знать время встречи и преподавателя.

Минимальный сценарий:

1. Система определяет текущего Student.
2. Backend выбирает только его предстоящие занятия; прошедшие занятия исключаются.
3. Занятия возвращаются по возрастанию даты/времени.
4. Frontend отображает дату, время и Teacher каждого занятия.
5. Frontend поддерживает состояния загрузки, пустого списка и ошибки.

Критерии приёмки: Student видит только свои предстоящие занятия в указанном порядке; прошедшие занятия отсутствуют; все три состояния интерфейса доступны для проверки.

Связанные правила: BR-04–BR-06. Часовой пояс и граница текущего момента — Q-01 и Q-02.

## US-03 — Календарь преподавателя

Как Teacher, я хочу видеть свои занятия за выбранный период в календаре, чтобы ориентироваться в расписании.

Минимальный сценарий:

1. Система определяет текущего Teacher.
2. Пользователь выбирает календарный период.
3. Frontend отправляет выбранный диапазон дат в Backend.
4. Backend возвращает занятия текущего Teacher внутри этого диапазона.
5. Frontend отображает занятия в календарном представлении.
6. Frontend поддерживает состояния загрузки, пустого календаря и ошибки.

Критерии приёмки: календарь показывает только занятия текущего Teacher, соответствующие выбранному периоду; изменение периода обновляет выборку; все три состояния интерфейса доступны для проверки.

Связанные правила: BR-07. Границы периода и часовой пояс — Q-01 и Q-03. Конкретные виды календаря требуют согласования в F-07.

## За пределами Sprint 1

- Проверка конфликтов расписания.
- Перенос и отмена занятий.

Эти возможности не являются критериями приёмки Sprint 1. Их правила и сроки реализации не определены.

## Ожидаемый результат

Подготовлена техническая основа Takt и проверен сквозной сценарий: аутентифицированный Teacher создаёт Lesson, Backend сохраняет его в PostgreSQL, Student видит его среди предстоящих занятий, а Teacher — в выбранном календарном периоде. Frontend и Backend интегрированы; для списков и календаря предусмотрены загрузка, пустое состояние и ошибка.

Документация отражает согласованное поведение. Вопросы из [реестра решений](../../requirements/business-rules.md#открытые-вопросы) должны быть согласованы до реализации зависимых проверок и контрактов.
