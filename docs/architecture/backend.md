# Backend: границы модулей

## Организация FastAPI-приложения

Рекомендуемый layout будущего `backend/app/`:

| Раздел | Ответственность |
| --- | --- |
| `api/` | Роутеры, HTTP-вход/выход, декларация доступа, вызов сервисов |
| `schemas/` | Pydantic DTO запросов/ответов, проверка формы, типов и transport-level ограничений |
| `services/` | Бизнес-сценарии, авторизация над ресурсами, координация use case и транзакционной операции |
| `models/` | SQLAlchemy-модели хранения, согласованные связи и ограничения |
| `repositories/` | Запросы и persistence; без формирования HTTP-ответов |
| `core/` | Конфигурация, аутентификация, общие обработчики ошибок |
| `db/` | Подключение, фабрика и жизненный цикл сессий |

Имена и конкретное разбиение каталогов могут уточняться в F-03 без изменения обязанностей слоёв.

Не создавать отдельный абстрактный repository для каждой таблицы, если он не добавляет ясности или полезной изоляции.

Роутер не содержит SQL или полный бизнес-сценарий.

### Направление зависимостей

Основное направление зависимостей Backend:

`API → Services → Persistence / DB`.

API-layer адаптирует HTTP-запрос к вызову use case и преобразует результат или проектное исключение обратно в HTTP.

Services не зависят от React, структуры UI и HTTP-деталей FastAPI. Бизнес-сценарий не должен использовать `HTTPException` как доменную ошибку.

Repositories и SQLAlchemy-модели не зависят от API-layer и не формируют HTTP-response DTO.

Допустимое уточнение структуры каталогов в F-03 не должно нарушать эти границы.

## Валидация и доступ

Request DTO проверяет форму, типы и transport-level ограничения входных данных.

Authentication dependency определяет доверенный User context. Service на его основе загружает обязательный Profile, определяет текущую роль и соответствующий TeacherProfile / StudentProfile context и выполняет бизнес-проверки и авторизацию над ресурсами.

Клиентский `teacher_id` / `student_id` не используется для определения того, от имени какого пользователя выполняется защищённая операция.

Repository получает от Service уже доверенные доменные идентификаторы и критерии выборки и выполняет необходимые запросы. Repository не самостоятельно определяет текущего пользователя из HTTP-запроса.

Ограничения БД дополняют проверки Service. Ожидаемые нарушения целостности переводятся в согласованные проектные ошибки; SQL, constraint names и внутренние детали БД клиенту не выдаются.

## Транзакционные границы

Service определяет границу атомарной бизнес-операции.

В частности:

- регистрация атомарно создаёт User, Profile и ровно один соответствующий TeacherProfile / StudentProfile;
- создание Lesson выполняет проверку текущего Teacher, доступности Student, допустимости `starts_at` и сохранение Lesson в одной управляемой операции.

Repositories не выполняют независимый `commit`, способный разрушить атомарность use case.

Успешный результат операции возвращается только после успешного commit. При исключении до завершения операции выполняется rollback.

Конкретный механизм управления транзакцией может уточняться реализацией, но транзакционная граница не должна перемещаться внутрь отдельных repository-вызовов.

## Конфигурация и зависимости

Настройки БД, CORS, параметры аутентификации и окружения читаются централизованно из environment через валидируемую конфигурацию.

Секреты не хранятся в Git, не включаются в логи и не задаются небезопасными production-default значениями.

Безопасный пример конфигурации без реальных секретов и фактические команды запуска появляются при реализации F-03 / F-05.

Отсутствие обязательной или некорректная конфигурация должны обнаруживаться при запуске приложения, а не при первом пользовательском запросе.

FastAPI dependencies предоставляют DB session, Services и текущий аутентифицированный context.

DB session имеет ограниченный lifecycle запроса и гарантированно закрывается. Глобальная mutable session для всех запросов не используется.

Sync / async режим выбирается Backend owner согласованно для SQLAlchemy driver, sessions, repositories и handlers согласно I-01. Случайное смешивание sync / async доступа к БД не допускается.

## Ошибки и OpenAPI

Project / domain exceptions преобразуются в HTTP только на API-границе.

Request schema validation, authentication / authorization failures, ожидаемые domain conflicts и unexpected server errors приводятся к [единой модели ошибок](../api/errors.md).

Ожидаемое нарушение ограничения БД может быть преобразовано в конкретную доменную ошибку только если его смысл известен приложению. Неожиданная persistence / database ошибка рассматривается как server error и не раскрывает внутренние детали клиенту.

Response validation или ошибка сериализации server response является `500`, а не клиентской `422`.

OpenAPI генерируется из фактических FastAPI routes и Pydantic DTO и должен соответствовать согласованным [API-контрактам](../api/contracts/sprint-01.md).

Расхождение runtime OpenAPI и утверждённого контракта является несогласованным изменением или дефектом, а не новой версией контракта по умолчанию.

## Границы тестирования

- **Unit / Service:** бизнес-правила, role/resource authorization, управляемый источник `now`, регистрация User + Profile + role profile как один use case, создание Lesson и негативные сценарии без HTTP.
- **API:** реальные HTTP-запросы через test client, request / response DTO, status codes, authentication header, role context и единая модель ошибок.
- **Persistence:** foreign keys, unique constraints, Teacher–Student relation, User ↔ Profile ↔ TeacherProfile / StudentProfile invariants, запросы по доверенным domain IDs и rollback на изолированной PostgreSQL.
- **Integration:** Backend + PostgreSQL и реальный HTTP transport; для интеграционного сценария Sprint 1 — также фактический Frontend ↔ Backend запрос через согласованный API.

pytest является базовым инструментом Backend.

Моки допустимы для изоляции Unit tests, но не доказывают корректность SQL, migrations, constraints или полной HTTP / DB интеграции.
