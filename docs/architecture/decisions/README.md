Эти записи описывают согласованное текущее направление реализации, но не означают наличие отдельного ADR для каждого решения. Формальный ADR создаётся только для существенного решения, требующего фиксации контекста, альтернатив и последствий.

## Когда нужен ADR

ADR создаётся для существенного технического решения, если оно:

- меняет утверждённый архитектурный baseline;
- имеет несколько реалистичных альтернатив с заметно разными последствиями;
- создаёт долгосрочное техническое ограничение или зависимость;
- существенно влияет одновременно на несколько частей системы;
- должно оставаться объяснимым после завершения текущей задачи / Sprint.

Примеры для Takt:

- выбор стратегии access token / authentication implementation;
- существенное изменение границ Backend-модулей;
- переход с текущей persistence / database технологии;
- введение обязательной Frontend state-management architecture;
- изменение стратегии API versioning / compatibility;
- изменение принятой timezone-архитектуры;
- переход от модульного монолита к нескольким сервисам.

ADR не создаётся только ради имени каталога, отдельного DTO-поля, локального refactoring или выбора, который легко заменить и который не создаёт архитектурных последствий.

## Жизненный цикл ADR

Автор ADR — инициатор существенного технического изменения.

Применимые owners выполняют техническое review. PO участвует, если решение меняет продуктовое поведение, BR, Acceptance Criteria или внешний API-смысл.

Используются статусы:

- `предложено` — решение находится на review;
- `принято` — решение согласовано и является действующим;
- `отклонено` — предложение рассмотрено и не принято;
- `заменено` — ранее принятое решение заменено более новым ADR.

Принятый ADR не редактируется так, чтобы задним числом менять смысл принятого решения. Если архитектурный выбор существенно меняется, создаётся новый ADR, а предыдущий получает ссылку на заменяющий документ.

После принятия ADR обновляются канонические architecture / API / BR документы и связанные задачи. ADR объясняет принятое решение и его последствия, но не заменяет API-контракт, бизнес-правило или Technical Task.

Файл ADR именуется `NNNN-краткая-тема.md`. Номер не переиспользуется.

Запись ADR содержит как минимум:

- контекст;
- рассматриваемое решение;
- альтернативы;
- последствия;
- способ проверки;
- затронутые документы и компоненты.

## Текущие нерешённые технические выборы

Отдельные нумерованные ADR пока не созданы.

Неблокирующие implementation choices I-01–I-04 ведутся в [реестре бизнес-правил и открытых решений](../../requirements/business-rules.md#открытые-решения).

Само наличие записи I-* не требует ADR. Если в ходе уточнения выбор оказывается существенным архитектурным решением по критериям выше, он оформляется отдельным ADR до завершения соответствующей реализации.
