# Frontend: границы модулей

[К архитектуре](overview.md) · [Интеграция](integration.md) · [API conventions](../api/conventions.md) · [Authentication](../api/authentication.md) · [Ошибки](../api/errors.md)

## Организация React / TypeScript

Рекомендуемое разделение будущего `frontend/src/`:

| Область | Ответственность |
| --- | --- |
| `pages/` | Композиция страниц, route-level состояния и запуск доступных пользователю сценариев |
| `features/` | UI-логика конкретных пользовательских сценариев: регистрация / вход, создание Lesson, upcoming-занятия Student, календарь Teacher |
| `components/` | Переиспользуемые визуальные элементы и элементы управления без прямой зависимости от Backend transport |
| `api/` | HTTP-клиент, функции API-операций, transport DTO, Bearer header и обработка transport / compatibility errors |
| `shared/` | Общие типы, UI primitives, date/time utilities и другие переиспользуемые элементы без feature-specific бизнес-логики |
| Routing | Сопоставление URL страницам и UX-ограничение недоступных для текущей роли сценариев |
| Environment config | Единая точка получения Backend origin и публичных настроек frontend-сборки |

Точные имена каталогов и конкретные библиотеки закрепляются в F-04. Не вводить отдельную библиотеку состояния, пока простых средств React достаточно; существенный долгосрочный выбор фиксируется через ADR.

Сетевое взаимодействие с Backend централизуется в API-layer. Pages, features и components не формируют Backend URL вручную и не выполняют произвольные `fetch` / HTTP-вызовы в обход этого слоя.

Router guards, скрытие элементов интерфейса и role-based navigation являются UX-мерами и не заменяют Backend authorization.

## Правила границ

Backend origin берётся из Environment config. API-layer добавляет пути и префикс согласно [API conventions](../api/conventions.md), не дублируя `/api/v1`.

Переменные frontend-сборки считаются публичными. В них нельзя хранить секреты БД, private signing keys, пароли или иные данные, раскрытие которых создаёт риск безопасности.

Бизнес-данные не зашиваются в переиспользуемые components. Demo data и contract mocks находятся отдельно от runtime API-layer; использование mock должно быть явно обозначено и не считается интеграцией с Backend.

API DTO описываются TypeScript-типами согласно согласованному API-контракту. TypeScript-типы сами по себе не гарантируют корректность runtime-response.

API-layer должен безопасно обрабатывать несовместимый или неожиданно сформированный response как transport / compatibility error, а не считать его корректным только из-за статической типизации.

Преобразование DTO в представление выполняется явно и не меняет доменную семантику данных.

## Аутентификация, роль и пользовательский контекст

Frontend получает access token как непрозрачную строку и добавляет `Authorization: Bearer <access_token>` централизованно в API-layer.

Claims токена, если выбранный механизм вообще их содержит, не являются самостоятельным источником продуктовых полномочий Frontend.

Текущий User, его роль и соответствующий Teacher / Student context определяются Backend и получаются через согласованный API.

Role-based routing и отображение доступных сценариев строятся на текущем серверном контексте.

В Sprint 1 User имеет одну роль `teacher` или `student`. Переключатель роли после регистрации и одновременный Teacher / Student UI для одного User не требуются.

Клиент не вычисляет `teacher_id` / `student_id` из User ID и не использует произвольные идентификаторы как источник текущей пользовательской identity.

При `401` защищённой операции Frontend прекращает использование недействительной сессии и переводит пользователя к повторной аутентификации.

`403` означает, что аутентифицированному User запрещена конкретная операция из-за роли / полномочий, и не должен автоматически запускать повторный login. Если валидный User не имеет обязательного matching Teacher / Student profile по BR-09, это server-side invariant failure и обрабатывается как `500 internal_error`.

Конкретный способ token storage, routing library и request tooling определяется I-02 до соответствующей реализации.

## Представление доменных данных

Frontend использует UUID как технический идентификатор ресурса, но не как основную пользовательскую подпись.

Когда пользователь должен идентифицировать Teacher или Student, UI отображает `display_name`, полученный из API DTO.

В частности:

- Teacher выбирает доступного Student по человекочитаемому `display_name`;
- Student видит `display_name` Teacher в предстоящем Lesson;
- Teacher видит `display_name` Student в календарном Lesson.

Frontend не подменяет отсутствующее человекочитаемое представление UUID.

Конкретный состав reference DTO и вложение данных участников определяются [API-контрактами Sprint 1](../api/contracts/sprint-01.md).

## Даты и календарь

В Sprint 1 ввод и отображение даты и времени выполняются в локальной временной зоне браузера пользователя.

Преобразование между UI-значением и API date-time централизуется в shared date/time utility.

При создании Lesson локальные дата и время интерпретируются в timezone браузера и преобразуются в timezone-aware ISO 8601 date-time с явным offset или `Z`.

Полученный от Backend UTC / timezone-aware момент преобразуется для отображения обратно в локальную timezone браузера.

Naive date-time, Unix timestamp и локализованные строки не отправляются в API как абсолютные моменты времени.

Календарь Teacher использует недельное представление:

- при первоначальном открытии отображается текущая неделя;
- неделя начинается в понедельник;
- доступны переходы к предыдущей и следующей неделе;
- `from` — понедельник выбранной недели, `00:00:00` в локальной timezone браузера;
- `to` — понедельник следующей недели, `00:00:00` в той же timezone;
- обе границы преобразуются в timezone-aware абсолютные моменты перед отправкой в API.

Границы соседних недель вычисляются как календарные границы локальной timezone, а не прибавлением фиксированных `7 × 24` часов. Это необходимо для корректного поведения при изменении UTC offset / DST.

## Состояния, ошибки и тестирование

Для пользовательских сценариев явно различаются `loading`, `empty`, `error` и `success`.

Во время отправки формы повторная отправка блокируется до получения результата. Это UX-защита и не является обещанием серверной идемпотентности.

После успешной mutation Frontend обновляет затронутые данные из авторитетного Backend-состояния.

При смене календарного периода или другого параметра выборки запоздалый response старого запроса не должен перезаписывать состояние нового запроса.

Frontend validation помогает пользователю, но не заменяет серверную проверку.

Поведение по Backend errors определяется стабильным `error.code`; field errors связываются с полями через `details[].location`.

Неизвестный error code, сетевой сбой, не-JSON response или несовместимый response DTO обрабатываются безопасно как transport / compatibility failure.

Минимальные области проверки Frontend:

- формы регистрации, входа и создания Lesson;
- состояния `loading / empty / error / success`;
- role-based navigation и текущий пользовательский context;
- отображение `display_name`;
- mapping Backend errors;
- преобразование date-time в обе стороны;
- границы недели и поведение при изменении timezone offset / DST;
- защита от отображения stale response после смены периода;
- реальные HTTP-запросы через API-layer.

Конкретный набор инструментов Frontend unit / component / E2E testing определяется при реализации и не считается уже выбранной dependency.

Ручные проверки должны оставаться воспроизводимыми по [QA-процессу](../process/qa-and-acceptance.md).
