# Frontend: границы модулей

[К архитектуре](overview.md) · [Интеграция](integration.md)

## Организация React / TypeScript

Рекомендуемое разделение будущего `frontend/src/`:

| Область | Ответственность |
| --- | --- |
| `pages/` | Сборка страниц и координация доступных пользователю сценариев |
| `features/` | Создание Lesson, список ученика, календарь преподавателя и их UI-логика |
| `components/` | Переиспользуемое отображение и элементы управления, данные приходят через props |
| `api/` | HTTP-клиент, функции операций, API DTO, обработка транспортных ошибок |
| `shared/` | Общие утилиты, преобразование дат, типы и компоненты без доменных привилегий |
| Routing | Сопоставление URL приложения страницам и UX-проверка доступности |
| Environment config | Единственное место получения базового URL Backend и настроек окружения |

Точные имена и библиотеки закрепляются F-04. Не вводить отдельную библиотеку состояния, пока простых средств React недостаточно; существенный выбор фиксируется ADR.

## Правила границ

Компоненты не содержат Backend base URL и не выполняют произвольные сетевые вызовы: они используют API-layer. Базовый URL берётся из environment config и обозначает origin Backend; API-layer добавляет пути с префиксом из [соглашений](../api/conventions.md), не удваивая его. Переменные frontend-сборки публичны: в них нельзя хранить секреты БД или подписи токенов.

Бизнес-данные не зашиваются в переиспользуемые компоненты. Демонстрационные данные и контрактные моки находятся отдельно; использование мока явно обозначается и не считается интеграцией.

API DTO описываются TypeScript-типами по контракту. Типы не гарантируют корректность runtime-ответа сами по себе: API-layer обрабатывает неожиданный ответ как ошибку совместимости. Преобразование DTO в представление выполняется явным mapping, не меняет смысл данных.

## Состояние и валидация

Для применимых сценариев явно различать loading, empty, error и success. При отправке формы показывать выполнение, защищать от повторного нажатия до ответа; это UX-мера, а не обещание серверной идемпотентности. После успешного создания обновлять затронутую выборку; при смене календарного периода не отображать запоздалый ответ старого периода как новый.

Frontend validation помогает пользователю, но серверная проверка обязательна. Скрытая кнопка и router guard не являются авторизацией. Программное поведение по ошибкам основано на `error.code`, field errors — на `details`; правила отображения — в [ошибках](../api/errors.md).

## Даты, сессия и проверка

Преобразование ввода даты/времени в API-значение идёт через shared utility по [семантике времени](../api/conventions.md#даты-и-время). Дата без смещения или локализованная строка не отправляется как момент времени. Выбор отображаемой зоны зависит от Q-10.

Frontend получает токен как непрозрачную строку и добавляет Bearer header в API-layer. Не интерпретировать claims как единственный источник полномочий; доверенный контекст получает Backend. Хранение токена / router / библиотека запросов выбираются в I-02 до соответствующей реализации.

Проверять поля формы, состояния выборок, mapping ошибок и дат, смену периода и реальные HTTP-запросы. Автоматизация Frontend / E2E выбирается по потребности, не является уже установленным инструментом. Ручные проверки остаются воспроизводимыми по [QA-процессу](../process/qa-and-acceptance.md).
