# Sprint 1 — Requirements

Документ фиксирует согласованный функциональный scope, предметные понятия, бизнес-правила и ограничения Sprint 1.

Документ определяет, **что** должно быть обеспечено системой.

Внутренняя архитектура и способ технической реализации определяются ответственными разработчиками.

# 1. Sprint Goal

Создать техническую основу Takt и реализовать первый сквозной сценарий работы с расписанием: преподаватель создаёт занятие, а информация о запланированных занятиях становится доступна пользователям через интерфейс.

## Scope

Sprint 1 включает:

- Foundation `F-01–F-08`;
- пользовательские сценарии `US-01–US-03`.

Текущие owner, reviewer, QA, SP, зависимости и статусы задач ведутся в Kaiten.

# 2. Foundation

## F-01 — Базовая проектная и функциональная документация

Должна существовать минимальная согласованная документационная база, достаточная для постановки последующих задач, разработки, интеграции, тестирования и приёмки Sprint 1.

Каноническая документация Sprint 1 состоит из:

- `README.md`;
- `sprint-01-requirements.md`;
- `sprint-01-contracts.md`;
- `acceptance-criteria.md`.

## F-02 — Структура репозитория и workflow

Должен существовать рабочий repository и согласованный процесс совместной разработки через branches, Pull Requests и Code Review.

Конкретная организация workflow находится в зоне ответственности исполнителей и reviewers задачи.

## F-03 — Backend base

Должна существовать работоспособная Backend-основа, позволяющая реализовывать и предоставлять API пользовательских сценариев Sprint 1.

Внутренняя структура Backend и используемые технические решения определяются ответственными разработчиками.

## F-04 — Frontend base

Должна существовать работоспособная Frontend-основа, позволяющая реализовать пользовательские сценарии Sprint 1 и взаимодействовать с Backend.

Внутренняя структура Frontend и используемые технические решения определяются ответственными разработчиками.

## F-05 — Persistence / local environment

Должен существовать воспроизводимый механизм хранения данных и локального запуска необходимой инфраструктуры Sprint 1.

Конкретная схема, persistence implementation, migrations и infrastructure находятся в зоне ответственности исполнителей соответствующей задачи.

## F-06 — Teacher / Student / Authentication

Система должна обеспечивать минимальную предметную модель `Teacher / Student` и механизм идентификации текущего пользователя, достаточные для пользовательских сценариев Sprint 1.

Необходимо обеспечить:

- существование `Teacher` и `Student` с уникальными идентификаторами;
- возможность связи `Teacher ↔ Student`;
- учётную запись пользователя;
- принадлежность пользователя к одной роли: `TEACHER` или `STUDENT`;
- регистрацию с выбором роли;
- вход зарегистрированного пользователя;
- определение Backend текущего пользователя и его роли;
- безопасное хранение пароля без хранения открытого значения;
- воспроизводимое создание необходимых структур данных;
- demo data: один Teacher и не менее трёх Students;
- demo relations, позволяющие проверить как доступного, так и недоступного текущему Teacher Student.

### Регистрация

Для регистрации используются:

- `email`;
- `password`;
- `role`;
- `first_name`;
- `last_name`;
- опциональный `middle_name`.

Допустимые роли пользователя:

- `TEACHER`;
- `STUDENT`.

Во внешних API-контрактах роль передаётся указанными строковыми кодами.

Один пользователь имеет только одну роль.

Multi-role и изменение роли в Sprint 1 не требуются.

`email` используется как идентификатор входа.

Перед использованием email:

- удаляются внешние пробелы;
- значение приводится к нижнему регистру.

Нормализованный email должен быть уникальным.

`first_name` и `last_name` обязательны и после удаления внешних пробелов не должны быть пустыми.

`middle_name` опционален. Пустое значение после удаления внешних пробелов может рассматриваться как отсутствие значения.

Пароль:

- обязателен;
- имеет длину от 8 до 128 символов включительно;
- не должен автоматически изменяться, обрезаться или нормализоваться;
- не хранится и не возвращается в открытом виде.

Подтверждение email, восстановление пароля, расширенный профиль, multi-role, смена роли и расширенное управление аккаунтом не входят в F-06.

## F-07 — UI/UX base

Для пользовательских сценариев Sprint 1 должна существовать единая UI/UX-основа.

Необходимо определить:

- базовую сетку и layout;
- типографику и основные визуальные правила;
- отступы;
- базовые `button`;
- `input`;
- `select`;
- `date/time input`;
- состояния `normal`;
- `loading`;
- `error`;
- `empty`;
- `success feedback`;
- desktop-first / responsive подход.

UI должен позволять пользователю работать с данными через человекочитаемые представления.

Техническая реализация компонентов определяется Frontend owner.

## F-08 — Frontend ↔ Backend Integration

Frontend и Backend должны иметь рабочий интеграционный контур.

Необходимо обеспечить:

- возможность Frontend выполнять реальные HTTP-запросы к Backend;
- корректный Backend origin / CORS;
- конфигурируемый Backend API base URL;
- согласованный формат API-ошибки;
- обработку успешного ответа;
- обработку ошибочного ответа;
- воспроизводимый реальный flow:

`Frontend → Backend → Response`

Mocks могут использоваться во время разработки, но не являются подтверждением готовой интеграции.

Конкретная внутренняя реализация Frontend и Backend определяется ответственными разработчиками.

# 3. Основные понятия

## User

Учётная запись пользователя Takt, используемая для аутентификации.

В Sprint 1 пользователь имеет одну роль:

- `teacher`;
- `student`.

Способ внутреннего хранения User и связи с предметными сущностями определяется Backend-разработчиками.

## Teacher

Пользователь Takt в роли преподавателя.

Teacher может работать только в рамках разрешённых ему пользовательских сценариев и взаимодействовать с доступными ему Students.

## Student

Пользователь Takt в роли ученика.

Student участвует в связанных с ним учебных сценариях и имеет доступ только к разрешённым ему данным.

## Teacher–Student relation

Связь, определяющая допустимое взаимодействие конкретного Teacher и конкретного Student.

В Sprint 1 Teacher может быть связан с несколькими Students.

Student также может быть связан с несколькими Teachers.

Пользовательское создание, изменение и удаление этих связей в Sprint 1 не требуется.

## Lesson

Запланированное занятие между одним Teacher и одним Student.

Минимально значимыми для Sprint 1 являются:

- Teacher;
- Student;
- момент начала `starts_at`.

Расширенная модель Lesson определяется требованиями соответствующих User Story.

# 4. Общие бизнес-правила Foundation

## BR-F-01 — Роль пользователя

Пользователь имеет ровно одну роль `teacher` или `student`.

Защищённые операции выполняются от имени текущего аутентифицированного пользователя.

Клиент не должен иметь возможность получить права другого пользователя простой подменой идентификатора.

## BR-F-02 — Teacher–Student relation

Если пользовательский сценарий требует доступного Teacher Student, доступность определяется существованием актуальной связи `Teacher ↔ Student`.

Получение Student ранее не отменяет необходимость учитывать актуальное состояние связи при выполнении операции.

## BR-F-03 — Человекочитаемое представление

Когда Teacher или Student отображается пользователю, интерфейс должен предоставлять человекочитаемое представление.

Для Sprint 1 используются:

- `first_name`;
- `last_name`;
- опциональный `middle_name`.

UUID или иной технический идентификатор не должен использоваться как единственная пользовательская подпись.

## BR-F-04 — Идентификация текущего пользователя

Backend является доверенным источником текущего пользовательского контекста для защищённых операций.

Frontend не определяет самостоятельно, от имени какого Teacher или Student Backend должен выполнить защищённую операцию.

Конкретный механизм аутентификации фиксируется во внешнем контракте.

# 5. Общие границы Foundation

Foundation Sprint 1 не требует:

- multi-role;
- изменения роли;
- password recovery / reset;
- email confirmation;
- OAuth;
- расширенного User management;
- расширенных профилей Teacher / Student;
- пользовательского управления Teacher–Student relations;
- поиска Teacher / Student;
- admin panel;
- дополнительной функциональности, не требуемой задачами Sprint 1.

Дополнительная функциональность может быть реализована разработчиками, если она не нарушает обязательные требования и внешние контракты.

Наличие дополнительной функциональности не компенсирует отсутствие обязательной функциональности Sprint 1.

# 6. Граница требований и реализации

- внутреннюю архитектуру Backend;

- способ организации migrations;

Если выбранное техническое решение приводит к невыполнению требования, Acceptance Criterion или согласованного внешнего контракта, это не изменяет требование автоматически.

Изменение требования должно быть согласовано отдельно.
