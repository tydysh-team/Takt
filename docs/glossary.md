# Глоссарий

[К справочнику](README.md)

Русское название и английский идентификатор обозначают одно понятие. DTO и JSON-поля не заменяют определения предметной области.

| Термин | Определение |
| --- | --- |
| Takt | Многопользовательская платформа для организации учебного процесса частных преподавателей и учеников. |
| Пользователь (User) | Пользовательская учётная запись Takt, используемая для аутентификации и получения доступа к функциям системы. В Sprint 1 User имеет одну роль, один общий Profile и один соответствующий TeacherProfile или StudentProfile. |
| Роль (Role) | Пользовательский контекст и связанные с ним полномочия в системе. В Sprint 1 User имеет ровно одну роль: `teacher` или `student`; совмещение и переключение ролей не поддерживаются. Канонические правила определены BR-09. |
| Профиль (Profile) | Общие данные человека, связанные ровно с одним User: `first_name`, `last_name`, опциональный `middle_name`. Имеет собственный внутренний `id`. |
| Профиль преподавателя (TeacherProfile) | Ролевой доменный профиль User с ролью `teacher`. Имеет собственный `id`, используемый как Teacher ID в доменных связях и API. |
| Профиль ученика (StudentProfile) | Ролевой доменный профиль User с ролью `student`. Имеет собственный `id`, используемый как Student ID в доменных связях и API. |
| Преподаватель (Teacher) | Пользователь Takt в роли преподавателя; в модели данных его ролевой доменный контекст представлен TeacherProfile. В текущем контуре планирует Lesson для связанных Student и работает со своим расписанием. |
| Ученик (Student) | Пользователь Takt в роли ученика; в модели данных его ролевой доменный контекст представлен StudentProfile. В текущем контуре просматривает информацию о своих предстоящих Lesson. |
| Связь Teacher–Student | Зафиксированная связь между Teacher и Student, определяющая их допустимое взаимодействие в Takt. В Sprint 1 она используется для определения доступных Teacher учеников при планировании Lesson. |
| Занятие (Lesson) | Запланированная встреча одного Teacher и одного Student с моментом начала `starts_at`. |
| Расписание (Schedule) | Совокупность занятий, относящихся к определённому пользователю и временному периоду. |
| Предстоящее занятие (Upcoming Lesson) | Lesson, которое по действующим бизнес-правилам относится к предстоящим для Student. Точные временные критерии определяются BR-05. |
| Календарный период (Calendar Period) | Временной диапазон, за который выполняется выборка Lesson для календаря. Точные правила границ определяются BR-07 и API-контрактом. |
| Аутентификация (Authentication) | Проверка личности пользователя и получение доверенного контекста User. |
| Авторизация (Authorization) | Проверка того, разрешено ли конкретному User выполнять действие над определённым ресурсом. Аутентификация сама по себе не даёт доступ к чужим данным. |
| Демонстрационные данные (Demo Data) | Воспроизводимые синтетические данные для демонстрации и проверки системы. |
| API Contract | Согласованный метод, путь, DTO, HTTP-коды, ошибки и семантика операции на границе Frontend / Backend. |
| DTO | Структура данных обмена между частями системы. DTO не является автоматической копией ORM-модели. |
| Business Rule (BR) | Проверяемое правило предметной области со стабильным ID и источником требования. |
| Acceptance Criteria (AC) | Проверяемые условия, при выполнении которых результат User Story или Technical Task считается соответствующим требованию. |
| Definition of Ready (DoR) | Условия достаточной определённости задачи для начала активной разработки. |
| Definition of Done (DoD) | Условия, которые должны быть выполнены для признания работы завершённой. |
| Product Acceptance | Подтверждение Product Owner, что результат соответствует согласованному пользовательскому поведению и границам продукта. Если в Sprint Planning / Kaiten используется служебная метка `Product Review`, в рамках этого справочника она обозначает назначение проверки Product Acceptance, а не отдельный этап процесса. |
| Story Point (SP) | Относительная оценка объёма и сложности работы; не является количеством часов. |
| User Story (US) | Описание пользовательской ценности или результата с точки зрения пользователя продукта. Технические действия сами по себе не являются User Story. |
| Technical Task | Конкретная техническая работа, связанная с User Story или Foundation-задачей и имеющая owner, критерии, оценку и проверки. |
| Foundation task | Организационная или техническая основа проекта, необходимая для последующей реализации пользовательских сценариев и обозначаемая F-ID. |
| Sprint | Ограниченный по времени цикл разработки, для которого определяются Sprint Goal и Sprint Backlog. |
| Product Backlog | Упорядоченный перечень продуктовых требований и работ, рассматриваемых для дальнейшего развития Takt. |
| Sprint Backlog | Набор User Story, Foundation и Technical Tasks, выбранных командой для выполнения в текущем Sprint. |
| Increment | Совокупный проверяемый результат разработки, добавляющий работающую часть продукта. |
| Blocker | Нерешённое условие, решение или зависимость, из-за которых соответствующая работа не может быть корректно продолжена или завершена. |
| ADR | Запись существенного архитектурного решения, его контекста, рассмотренных альтернатив и последствий. |

Статусы решений находятся в [реестре бизнес-правил и открытых решений](requirements/business-rules.md#открытые-решения).

Условия DoR / DoD описаны в [процессе разработки](process/definition-of-ready-done.md).
