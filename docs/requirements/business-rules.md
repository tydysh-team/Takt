# Бизнес-правила и открытые решения

[К справочнику](../README.md) · [Scope / AC Sprint 1](../sprints/sprint-01/scope.md) · [API](../api/contracts/sprint-01.md)

## Формат и статус

BR-ID стабилен и не переиспользуется. Для каждого правила фиксируются статус, формулировка, источник и проверка. «Подтверждено для Sprint 1» — требование к результату, не статус реализации. Технические соглашения имеют канонические источники в архитектуре / API, не создают отдельные бизнес-правила без доменного смысла.

## Активные правила

### BR-01 — Автор создания занятия

**Статус:** подтверждено для Sprint 1.

Lesson может создавать только аутентифицированный Teacher.

Созданный Lesson принадлежит Teacher, который выполняет операцию создания. Teacher не может создавать Lesson от имени другого Teacher.

Идентификатор автора Lesson не выбирается пользователем отдельно при создании занятия.

**Источник / проверка:** [US-01 / AC-01](../sprints/sprint-01/scope.md#us-01--создание-занятия), [API-05](../api/contracts/sprint-01.md#api-05--создать-lesson).

Проверить:

- без аутентификации создание Lesson недоступно;
- пользователь без роли Teacher не может создать Lesson;
- Teacher не может указать другого Teacher в качестве автора;
- созданный Lesson связан с Teacher, выполняющим операцию.

Технический способ определения текущего Teacher задаётся правилами аутентификации и API-контрактом.

### BR-02 — Выбор ученика

**Статус:** подтверждено для Sprint 1.

Teacher может создать Lesson только для существующего Student, с которым у него существует связь Teacher–Student.

Student без связи с текущим Teacher не является допустимым участником создаваемого Lesson.

Связь Teacher–Student должна существовать на момент создания Lesson. Получение Student ранее в списке доступных учеников само по себе не гарантирует допустимость последующего создания: при выполнении операции правило проверяется повторно.

**Источник / проверка:** [US-01 / AC-01](../sprints/sprint-01/scope.md#us-01--создание-занятия), [API-04](../api/contracts/sprint-01.md#api-04--доступные-ученики), [API-05](../api/contracts/sprint-01.md#api-05--создать-lesson).

Проверить:

- связанный с текущим Teacher Student доступен для создания Lesson;
- существующий Student без связи с текущим Teacher не позволяет создать Lesson;
- несуществующий Student не позволяет создать Lesson;
- список доступных Student содержит только Student, связанных с текущим Teacher;
- если допустимость Student изменилась между получением списка и созданием Lesson, Backend использует актуальное состояние связи при выполнении операции.

Конкретный HTTP-код и формат ошибки определяются API-контрактом и общей моделью ошибок.

### BR-03 — Данные и результат создания

**Статус:** подтверждено для Sprint 1.

Создаваемый Lesson должен быть связан:

- с Teacher, выполняющим создание;
- с выбранным допустимым Student;
- с моментом начала `starts_at`.

Для Sprint 1 `starts_at` является обязательной временной характеристикой Lesson. Длительность и момент окончания в минимальную модель Sprint 1 не входят.

Lesson создаётся только при успешном прохождении всех применимых проверок.

Если хотя бы одно обязательное условие создания не выполнено, новый Lesson не должен появиться в системе. Частично созданный Lesson не допускается.

**Источник / проверка:** [US-01 / AC-01](../sprints/sprint-01/scope.md#us-01--создание-занятия), [API-05](../api/contracts/sprint-01.md#api-05--создать-lesson).

Проверить:

- успешное создание формирует один Lesson с корректными Teacher, Student и `starts_at`;
- отсутствие или некорректность обязательных данных приводит к отказу в создании;
- нарушение BR-01 или BR-02 приводит к отказу в создании;
- при отклонённой операции новый Lesson не сохраняется;
- успешный результат позволяет клиенту получить данные созданного Lesson.

Конкретный состав request / response DTO, HTTP-коды и формат ошибок задаются API-контрактом.

Правила допустимого значения `starts_at` относительно текущего времени определяются отдельно.

### BR-04 — Принадлежность занятий ученику

**Статус:** подтверждено для Sprint 1.

Student может просматривать только собственные Lesson.

При формировании списка предстоящих занятий система выбирает только Lesson, в которых текущий Student является участником.

Lesson другого Student не должен быть доступен через данный пользовательский сценарий.

Student не выбирает произвольного пользователя, для которого необходимо получить список занятий.

**Источник / проверка:** [US-02 / AC-02](../sprints/sprint-01/scope.md#us-02--просмотр-предстоящих-занятий-учеником), [API-06](../api/contracts/sprint-01.md#api-06--предстоящие-lesson-ученика).

Проверить:

- собственный Lesson текущего Student может попасть в результат при выполнении остальных правил выборки;
- Lesson другого Student не попадает в результат;
- изменение идентификаторов или параметров запроса не позволяет получить занятия другого Student;
- результат определяется текущим пользовательским контекстом, а не переданным клиентом идентификатором Student.

Технический способ определения текущего Student задаётся правилами аутентификации и API-контрактом.

Временной критерий того, какие Lesson считаются предстоящими, определяется отдельно в BR-05.

### BR-05 — Предстоящие занятия

**Статус:** подтверждено для Sprint 1.

Lesson считается предстоящим для Student, если его момент начала удовлетворяет условию:

`starts_at >= now`

где `now` — единый момент текущего времени, зафиксированный системой для выполнения конкретной операции выборки.

Lesson с `starts_at == now` считается предстоящим.

Lesson с `starts_at < now` не относится к предстоящим и не включается в соответствующий список.

В Sprint 1 принадлежность к предстоящим определяется только по моменту начала Lesson. Отдельное состояние «занятие идёт сейчас» не вводится, поскольку длительность и момент окончания не являются частью минимальной модели.

**Источник / проверка:** [US-02 / AC-02](../sprints/sprint-01/scope.md#us-02--просмотр-предстоящих-занятий-учеником), [API-06](../api/contracts/sprint-01.md#api-06--предстоящие-lesson-ученика).

Проверить:

- Lesson с `starts_at < now` исключается;
- Lesson с `starts_at == now` включается;
- Lesson с `starts_at > now` включается;
- все сравнения внутри одной операции используют одно и то же значение `now`;
- эквивалентные моменты времени с различными timezone offsets дают одинаковый результат.

Технические правила передачи, нормализации и сравнения времени определяются API conventions.

### BR-06 — Порядок предстоящих занятий

**Статус:** подтверждено для Sprint 1.

Предстоящие Lesson отображаются в хронологическом порядке по моменту начала:

`starts_at ASC`

Lesson с более ранним `starts_at` должен располагаться перед Lesson с более поздним `starts_at`.

Таким образом, ближайшие предстоящие занятия отображаются пользователю первыми.

Если несколько Lesson имеют одинаковый `starts_at`, их взаимный порядок не имеет отдельного продуктового значения. Техническое правило детерминированной сортировки для таких случаев задаётся API-контрактом.

**Источник / проверка:** [US-02 / AC-02](../sprints/sprint-01/scope.md#us-02--просмотр-предстоящих-занятий-учеником), [API-06](../api/contracts/sprint-01.md#api-06--предстоящие-lesson-ученика).

Проверить:

- Lesson с более ранним `starts_at` располагается раньше Lesson с более поздним `starts_at`;
- список из нескольких предстоящих Lesson отсортирован хронологически по возрастанию времени начала;
- наличие одинакового `starts_at` не нарушает согласованный технический порядок ответа.

### BR-07 — Календарная выборка

**Статус:** подтверждено для Sprint 1.

Teacher получает в календаре только собственные Lesson, относящиеся к выбранному календарному периоду.

Lesson относится к календарному периоду, если его момент начала удовлетворяет условию:

`from <= starts_at < to`

Начальная граница `from` включается, конечная граница `to` исключается.

Для корректного периода должно выполняться:

`from < to`

В Sprint 1 принадлежность Lesson календарному периоду определяется только по `starts_at`.

Длительность Lesson и пересечение интервалов не учитываются, поскольку момент окончания не является частью минимальной модели Sprint 1.

**Источник / проверка:** [US-03 / AC-03](../sprints/sprint-01/scope.md#us-03--календарь-преподавателя), [API-07](../api/contracts/sprint-01.md#api-07--lesson-в-календарном-периоде-teacher).

Проверить:

- Lesson текущего Teacher с `starts_at == from` включается;
- Lesson текущего Teacher с `from < starts_at < to` включается;
- Lesson с `starts_at == to` не включается;
- Lesson вне выбранного периода не включается;
- Lesson другого Teacher не попадает в результат;
- соседние периоды не дублируют Lesson на общей границе;
- диапазон с `from >= to` считается некорректным.

Технический формат `from` / `to`, timezone-aware transport, HTTP-код и формат ошибки задаются API conventions и API-контрактом.

### BR-08 — Допустимый момент начала при создании Lesson

**Статус:** подтверждено для Sprint 1.

При создании Lesson его момент начала должен удовлетворять условию:

`starts_at >= now`

где `now` — единый момент текущего времени, зафиксированный системой для выполнения операции создания.

Lesson с `starts_at < now` создать нельзя.

Lesson с `starts_at == now` допускается.

В Sprint 1 максимальная граница будущего момента для `starts_at` не устанавливается.

**Источник / проверка:** [US-01 / AC-01](../sprints/sprint-01/scope.md#us-01--создание-занятия), [API-05](../api/contracts/sprint-01.md#api-05--создать-lesson).

Проверить:

- `starts_at < now` приводит к отказу в создании;
- `starts_at == now` допускается;
- `starts_at > now` допускается;
- отклонённая операция не создаёт Lesson;
- отсутствие установленного максимума будущей даты не заменяется произвольным техническим ограничением.

Конкретный HTTP-код и формат ошибки задаются API-контрактом и общей моделью ошибок.

### BR-09 — Роль User и доменный контекст

**Статус:** подтверждено для Sprint 1.

Каждый User в Sprint 1 имеет ровно одну доменную роль:

- `teacher`;
- `student`.

Каждый User связан ровно с одним Profile, содержащим общие данные человека.

Для Profile существует ровно один ролевой профиль, соответствующий `User.role`:

- `TeacherProfile` для роли `teacher`;
- `StudentProfile` для роли `student`.

Одновременное наличие TeacherProfile и StudentProfile для одного Profile в Sprint 1 не допускается.

При регистрации пользователь выбирает одну из доступных ролей: `teacher` или `student`.

При успешной регистрации система атомарно создаёт:

- User;
- Profile;
- ровно один соответствующий TeacherProfile или StudentProfile.

После успешной аутентификации Backend определяет роль User и соответствующий ролевой доменный контекст. В пользовательских сценариях Teacher и Student обозначают пользователей соответствующих ролей; их доменные идентификаторы представлены `TeacherProfile.id` и `StudentProfile.id`.

Клиент не выбирает Teacher или Student, от имени которого выполняется защищённая операция.

Изменение выбранной роли после регистрации, переключение ролей и совмещение нескольких ролей одним User не входят в Sprint 1.

**Источник / проверка:** [F-06](../sprints/sprint-01/scope.md#foundation), [API-01](../api/contracts/sprint-01.md#api-01--регистрация), [API-03](../api/contracts/sprint-01.md#api-03--текущий-контекст), [US-01](../sprints/sprint-01/scope.md#us-01--создание-занятия), [US-02](../sprints/sprint-01/scope.md#us-02--просмотр-предстоящих-занятий-учеником), [US-03](../sprints/sprint-01/scope.md#us-03--календарь-преподавателя).

Проверить:

- регистрация с ролью `teacher` создаёт User, Profile и ровно один TeacherProfile;
- регистрация с ролью `student` создаёт User, Profile и ровно один StudentProfile;
- User с ролью `teacher` получает Teacher context на основе TeacherProfile;
- User с ролью `student` получает Student context на основе StudentProfile;
- Teacher-операция недоступна User с ролью `student`;
- Student-операция недоступна User с ролью `teacher`;
- клиент не может подменить текущий доменный контекст произвольным `teacher_id` / `student_id`;
- один Profile не имеет одновременно TeacherProfile и StudentProfile в Sprint 1;
- отсутствие обязательного Profile / соответствующего ролевого профиля рассматривается как нарушение системного инварианта;
- изменение или переключение роли после регистрации в Sprint 1 не поддерживается.

Технический способ хранения роли и связей определяется моделью данных и authentication implementation.

### BR-10 — Регистрация и идентификатор User

**Статус:** подтверждено для Sprint 1.

Для регистрации User пользователь предоставляет:

- `email`;
- `password`;
- `role`;
- `first_name`;
- `last_name`;
- опциональный `middle_name`.

В Sprint 1 `email` является идентификатором User для входа в систему.

Перед проверкой уникальности и сохранением `email` нормализуется:

- удаляются пробельные символы в начале и конце;
- значение приводится к нижнему регистру.

Значение `email` должно иметь корректный формат адреса электронной почты. Подтверждение владения email в Sprint 1 не требуется.

Уникальность User определяется по нормализованному `email`.

Два значения email, различающиеся только регистром или внешними пробелами, не могут использоваться для создания разных User.

Поле `role` обязательно и принимает одно из значений:

- `teacher`;
- `student`.

Создание Profile и соответствующего ролевого профиля определяется BR-09.

`first_name` и `last_name` обязательны. Перед сохранением у них удаляются пробельные символы в начале и конце; после trim значения должны оставаться непустыми.

`middle_name` опционален и может быть `null`. Если строковое значение передано, внешние пробелы удаляются; пустое после trim значение нормализуется в `null`.

В Sprint 1 отдельное составное поле `display_name` не хранится и не является частью регистрационного контракта.

Пароль является обязательным.

Для Sprint 1 допустим пароль длиной от 8 до 128 символов включительно.

Пароль не нормализуется, не приводится к другому регистру и не обрезается автоматически.

В Sprint 1 дополнительные требования к составу пароля не вводятся.

Усиленная парольная политика не входит в Sprint 1 и должна вводиться отдельной технической задачей.

Пароль не хранится и не возвращается в открытом виде. Технический механизм hashing определяется authentication implementation.

**Источник / проверка:** [F-06](../sprints/sprint-01/scope.md#foundation), [API-01](../api/contracts/sprint-01.md#api-01--регистрация), [API-02](../api/contracts/sprint-01.md#api-02--вход).

Проверить:

- корректные обязательные поля позволяют зарегистрировать User;
- зарегистрированный `email` используется для последующего входа;
- email с внешними пробелами нормализуется;
- значение, не соответствующее формату email, отклоняется;
- регистр email не позволяет создать отдельный User;
- повторная регистрация уже используемого нормализованного email отклоняется;
- отсутствие любого обязательного поля регистрации приводит к отказу;
- допускаются только роли `teacher` и `student`;
- `first_name` и `last_name` обязательны;
- внешние пробелы `first_name` / `last_name` удаляются;
- пустой `first_name` или `last_name` после trim отклоняется;
- отсутствие `middle_name` допускается;
- пустой `middle_name` после trim нормализуется в `null`;
- пароль короче 8 символов отклоняется;
- пароль длиннее 128 символов отклоняется;
- пароль длиной 8 и 128 символов допускается;
- пароль не изменяется системой перед проверкой credentials;
- открытый пароль не сохраняется и не возвращается клиенту.

Конкретные request / response DTO, HTTP-коды и коды ошибок задаются API-контрактом и общей моделью ошибок.


### BR-11 — Человекочитаемое представление Teacher и Student

**Статус:** подтверждено для Sprint 1.

Общие персональные данные Teacher и Student в Sprint 1 хранятся в Profile структурированно:

- обязательный `first_name`;
- обязательный `last_name`;
- опциональный nullable `middle_name`.

Минимальное представление Teacher или Student, когда пользователь должен идентифицировать участника учебного процесса, включает:

- уникальный идентификатор ролевого ресурса (`TeacherProfile.id` или `StudentProfile.id`);
- `first_name`;
- `last_name`;
- `middle_name` со значением строки либо `null`.

Frontend формирует человекочитаемую подпись из этих полей и не использует UUID как пользовательское имя. Отдельное persisted-поле `display_name` в Sprint 1 не вводится.

Структурированное хранение имени позволяет в будущих требованиях добавлять поиск / фильтрацию по имени и фамилии без разбора одной составной строки. Сам пользовательский поиск Teacher / Student по ФИО в Sprint 1 не входит.

Для Sprint 1 дополнительные профильные сведения — `bio`, аватар, предметы, контакты, пользовательская timezone и другие расширенные данные — не являются обязательными.

**Источник / проверка:** [F-06](../sprints/sprint-01/scope.md#foundation), [US-01](../sprints/sprint-01/scope.md#us-01--создание-занятия), [US-02](../sprints/sprint-01/scope.md#us-02--просмотр-предстоящих-занятий-учеником), [US-03](../sprints/sprint-01/scope.md#us-03--календарь-преподавателя), [BR-10](#br-10--регистрация-и-идентификатор-user).

Проверить:

- Teacher при регистрации получает обязательные `first_name` и `last_name` в Profile;
- Student при регистрации получает обязательные `first_name` и `last_name` в Profile;
- `middle_name` корректно обрабатывается как опциональное поле;
- Teacher может выбрать связанного Student по человекочитаемой подписи, сформированной из полей имени;
- Student видит человекочитаемое имя Teacher в предстоящем Lesson;
- Teacher видит человекочитаемое имя Student в календарном Lesson;
- UUID участника не используется как единственная пользовательская подпись.

Конкретный состав reference DTO и вложение данных участников в ответы Lesson задаются API-контрактом.

### BR-12 — Зона времени и календарный период UI

**Статус:** подтверждено для Sprint 1.

В Sprint 1 ввод и отображение даты и времени в пользовательском интерфейсе выполняются в локальной временной зоне браузера пользователя.

Отдельная настройка временной зоны пользователя в Sprint 1 не вводится.

При создании Lesson Frontend интерпретирует введённые пользователем дату и время в локальной временной зоне браузера и передаёт Backend timezone-aware date-time с явным offset или `Z`.

Полученные от Backend абсолютные моменты времени Frontend отображает пользователю в локальной временной зоне браузера.

Календарь Teacher в Sprint 1 использует недельное представление.

При первоначальном открытии календаря отображается текущая календарная неделя в локальной временной зоне браузера.

Пользователь может перейти к предыдущей или следующей неделе.

Для Sprint 1 календарная неделя начинается в понедельник.

Для выбранной недели Frontend формирует календарный диапазон:

- `from` — понедельник выбранной недели, `00:00:00` в локальной временной зоне браузера;
- `to` — понедельник следующей недели, `00:00:00` в той же временной зоне.

Границы преобразуются в timezone-aware абсолютные моменты и передаются Backend согласно BR-07 и API conventions.

Дневное и месячное представления календаря, а также пользовательская настройка временной зоны не входят в Sprint 1.

**Источник / проверка:** [US-01](../sprints/sprint-01/scope.md#us-01--создание-занятия), [US-02](../sprints/sprint-01/scope.md#us-02--просмотр-предстоящих-занятий-учеником), [US-03](../sprints/sprint-01/scope.md#us-03--календарь-преподавателя), [API: даты и время](../api/conventions.md#даты-и-время).

Проверить:

- дата и время создания Lesson интерпретируются в локальной зоне браузера;
- returned UTC / offset moment отображается пользователю как соответствующее локальное время;
- календарь первоначально открывается на текущей неделе;
- переход на предыдущую / следующую неделю изменяет `from` / `to`;
- диапазон недели имеет семантику `[from, to)`;
- границы недели корректно формируются при смене offset / DST;
- изменение системной timezone браузера влияет на UI-представление, но не меняет абсолютный момент уже сохранённого Lesson;
- недельный диапазон начинается в понедельник в `00:00:00` локальной временной зоны;
- пользовательская настройка timezone и дополнительные виды календаря не требуются для Sprint 1.
