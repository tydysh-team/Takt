# US-04 — Acceptance Criteria

## User Story

**Я как преподаватель хочу получать предупреждение о пересечении создаваемого занятия с другим занятием, чтобы избежать конфликтов в расписании.**

---

## AC-US04-01 — Создание занятия без конфликта

**Given**
- пользователь аутентифицирован как `Teacher`;
- выбран доступный ему `Student`;
- данные нового `Lesson` валидны;
- временной интервал нового занятия не пересекается с существующими неотменёнными занятиями текущего `Teacher`.

**When**
- `Teacher` инициирует создание занятия.

**Then**
- система выполняет проверку пересечений;
- конфликт не обнаруживается;
- warning не отображается;
- стандартный сценарий создания продолжается;
- `Lesson` успешно создаётся;
- созданное занятие появляется в актуальном расписании.

---

## AC-US04-02 — Частичное пересечение

**Given**
- у текущего `Teacher` существует неотменённый `Lesson` `10:00–11:00`.

**When**
- создаётся новый `Lesson` `10:30–11:30`.

**Then**
- система определяет пересечение;
- новый `Lesson` не создаётся автоматически;
- `Teacher` получает warning о конфликте.

---

## AC-US04-03 — Полное пересечение и совпадающие интервалы

Для существующего неотменённого `Lesson` система должна определять конфликт во всех случаях:

1. новый интервал полностью находится внутри существующего;
2. существующий интервал полностью находится внутри нового;
3. интервалы полностью совпадают;
4. интервалы имеют одинаковое время начала и разное время окончания;
5. интервалы имеют одинаковое время окончания и разное время начала.

Во всех перечисленных случаях:

- возвращается результат `conflict`;
- отображается warning;
- автоматическое создание до решения пользователя не выполняется.

---

## AC-US04-04 — Соприкосновение временных интервалов

**Given**
- существующий неотменённый `Lesson` заканчивается ровно в момент начала нового занятия либо начинается ровно в момент окончания нового.

Пример:

- существующее занятие: `10:00–11:00`;
- новое занятие: `11:00–12:00`.

**Then**
- пересечение отсутствует;
- warning не отображается;
- сценарий создания продолжается как обычное создание без конфликта.

---

## AC-US04-05 — Scope проверки: текущий Teacher и неотменённые Lesson

При проверке пересечений:

- `Teacher` определяется из authentication context;
- учитываются только `Lesson`, принадлежащие текущему `Teacher`;
- `Lesson` со статусом `cancelled` не участвует в conflict-check;
- пересечение нового занятия только с отменённым `Lesson` не считается конфликтом;
- занятие другого `Teacher`, проходящее в тот же временной интервал, не считается конфликтом для текущего пользователя;
- подмена `teacher_id` со стороны клиента не должна позволять проверить либо использовать расписание другого `Teacher`.

---

## AC-US04-06 — Warning содержит данные конфликтующего занятия

При обнаружении пересечения warning должен содержать достаточную человекочитаемую информацию о конфликтующем `Lesson`.

Минимально:

- факт наличия конфликта;
- дату занятия;
- время занятия;
- данные связанного `Student`.

Если доступно название / предмет занятия, оно также может отображаться пользователю.

Отменённые `Lesson` не должны отображаться как конфликтующие.

Warning должен визуально восприниматься как предупреждение, а не как критическая системная ошибка.

---

## AC-US04-07 — Изменение даты или времени после warning

**Given**
- система обнаружила конфликт;
- warning отображён.

**When**
- `Teacher` изменяет дату или время создаваемого `Lesson`.

**Then**
- предыдущий результат проверки считается неактуальным;
- перед созданием выполняется новая проверка пересечений;
- решение о наличии конфликта принимается на основании новых временных параметров.

---

## AC-US04-08 — Отмена создания после warning

**Given**
- обнаружен конфликт;
- `Teacher` получил warning.

**When**
- пользователь отказывается от создания.

**Then**
- новый `Lesson` не создаётся;
- существующие `Lesson` не изменяются;
- интерфейс не отображает ложный success.

---

## AC-US04-09 — Явное подтверждение конфликтующего занятия

**Given**
- обнаружен конфликт;
- warning отображён.

**When**
- `Teacher` явно подтверждает создание занятия несмотря на пересечение.

**Then**
- система разрешает продолжить создание;
- конфликтующий `Lesson` может быть успешно создан;
- после успешного создания расписание содержит новый `Lesson`.

Без явного подтверждения `Teacher` конфликтующий `Lesson` не должен быть создан.

---

## AC-US04-10 — Ошибка проверки пересечений

**Given**
- выполняется проверка конфликтов.

**When**
- Backend / API / transport error не позволяет получить достоверный результат проверки.

**Then**
- ошибка не трактуется как отсутствие конфликта;
- `Lesson` не создаётся автоматически;
- пользователю отображается error-state;
- ложный success отсутствует;
- пользователь может повторить операцию.

---

## AC-US04-11 — Loading-state и защита от повторной операции

Во время выполнения проверки пересечений:

- пользователь видит состояние ожидания;
- система не должна создавать `Lesson` до завершения обязательной проверки;
- повторное действие пользователя во время активного запроса не должно приводить к созданию дублирующихся занятий.

---

## AC-US04-12 — Authentication и Authorization

### Неаутентифицированный пользователь

Попытка выполнить защищённый сценарий проверки / создания должна быть отклонена согласно общим правилам authentication приложения.

### Пользователь без роли Teacher

Не должен получать возможность выполнять Teacher-сценарий создания занятия с проверкой конфликтов.

### Недоступный Student

`Teacher` не должен иметь возможности создать `Lesson` для `Student`, недоступного ему по существующим правилам продукта.

---

## AC-US04-13 — Date / Time / Timezone

Проверка пересечений должна давать одинаковый фактический результат независимо от timezone представления клиента.

Обязательно:

- `starts_at` обрабатывается как timezone-aware значение;
- временные значения сравниваются в едином представлении;
- `ends_at` определяется из `starts_at` и `duration`;
- изменение способа отображения timezone не должно изменять фактический момент занятия;
- окончательное решение о наличии конфликта предоставляет Backend.

---

## AC-US04-14 — Некорректные входные данные

Некорректные данные нового `Lesson` не должны приводить к успешному созданию.

Проверяются как минимум:

- невалидная дата / время;
- невалидная продолжительность;
- недопустимое прошлое время;
- некорректный либо недоступный `Student`.

В ошибочном сценарии:

- новый `Lesson` не создаётся;
- пользователь получает соответствующий validation / error result;
- ложный success отсутствует.

---

## AC-US04-15 — Реальный Frontend ↔ Backend flow

Сценарий должен быть подтверждён на реальной интеграции Frontend и Backend без использования mock-response как источника результата проверки.

Необходимо подтвердить:

1. Frontend передаёт данные нового `Lesson`;
2. Backend выполняет проверку только по учитываемым в conflict-check `Lesson`;
3. Frontend корректно обрабатывает `no conflict`;
4. Frontend корректно отображает `conflict warning`;
5. действия `изменить / отменить / продолжить` работают согласно спецификации;
6. после успешного создания расписание обновляется актуальными Backend-данными.

---

## AC-US04-16 — Regression US-01

После внедрения US-04 существующий сценарий US-01 должен сохранять работоспособность.

При отсутствии временного конфликта:

- `Teacher` по-прежнему может создать `Lesson`;
- существующие обязательные проверки US-01 продолжают работать;
- успешное создание корректно отображается в расписании;
- новый conflict-flow не блокирует обычное создание без конфликта.

Пересечение только с отменённым `Lesson` также должно обрабатываться как отсутствие конфликта.

---

# Обязательные Acceptance Criteria

Для Product Acceptance обязательными являются:

- `AC-US04-01` — создание без конфликта;
- `AC-US04-02` — частичное пересечение;
- `AC-US04-03` — полное пересечение / совпадение;
- `AC-US04-04` — временная граница;
- `AC-US04-05` — scope текущего Teacher / исключение cancelled Lesson;
- `AC-US04-06` — warning;
- `AC-US04-07` — повторная проверка;
- `AC-US04-08` — отмена;
- `AC-US04-09` — явное подтверждение;
- `AC-US04-10` — error-state;
- `AC-US04-11` — loading / duplicate protection;
- `AC-US04-12` — authentication / authorization;
- `AC-US04-13` — date/time/timezone;
- `AC-US04-14` — validation;
- `AC-US04-15` — Frontend ↔ Backend integration;
- `AC-US04-16` — regression US-01.

Если хотя бы один обязательный Acceptance Criterion имеет статус `FAIL`, итоговый статус US-04 не может быть `PASS`.
