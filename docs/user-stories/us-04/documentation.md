# US-04 — Проверка пересечений занятий

## User Story

**Я как преподаватель хочу получать предупреждение о пересечении создаваемого занятия с другим занятием, чтобы избежать конфликтов в расписании.**

---

## 1. Цель

При создании нового `Lesson` система должна проверить, пересекается ли его временной интервал с уже существующими **неотменёнными** занятиями текущего `Teacher`.

Если пересечение обнаружено, `Teacher` получает понятное предупреждение до окончательного создания занятия и самостоятельно принимает решение:

- изменить дату или время;
- отказаться от создания;
- явно подтвердить создание несмотря на конфликт.

Наличие конфликта является **предупреждением**, а не безусловным запретом на создание `Lesson`.

---

## 2. Участники

### Основной пользователь

`Teacher`.

### Связанные сущности

- `Teacher`;
- выбранный `Student`;
- создаваемый `Lesson`;
- существующий конфликтующий `Lesson`.

---

## 3. Предусловия

Для выполнения сценария должны выполняться следующие условия:

- пользователь аутентифицирован;
- текущий пользователь имеет роль `Teacher`;
- `Teacher` создаёт новый `Lesson` через доступный ему сценарий создания занятия;
- выбранный `Student` доступен текущему `Teacher`;
- введённые дата, время и продолжительность занятия прошли базовую валидацию создания `Lesson`.

---

## 4. Временной интервал Lesson

Временной интервал занятия определяется значениями:

- `starts_at` — дата и время начала;
- `duration` — продолжительность занятия;
- `ends_at = starts_at + duration`.

Для проверки пересечений используется интервал:

`[starts_at, ends_at)`

Начало занятия входит в интервал, момент окончания — не входит.

Это позволяет двум занятиям непосредственно следовать друг за другом без конфликта.

### Пример

Первое занятие:

`10:00–11:00`

Второе занятие:

`11:00–12:00`

Такие занятия **не пересекаются**.

---

## 5. Правило определения пересечения

Два временных интервала считаются пересекающимися, если выполняется условие:

`new.starts_at < existing.ends_at`

и одновременно:

`new.ends_at > existing.starts_at`

Таким образом, конфликтом считаются:

- частичное наложение интервалов;
- полное вхождение одного интервала в другой;
- одинаковые интервалы;
- одинаковое время начала при различной продолжительности;
- одинаковое время окончания при различном времени начала.

Соприкосновение только по общей временной границе конфликтом **не считается**.

Правило пересечения применяется только к `Lesson`, которые участвуют в conflict-check согласно области проверки ниже.

---

## 6. Область проверки

При создании `Lesson` система проверяет пересечения только с **неотменёнными занятиями текущего авторизованного Teacher**.

`Teacher` определяется из authentication context.

### Отменённые занятия

`Lesson` со статусом `cancelled` **не участвует в проверке пересечений** и не занимает временной слот с точки зрения conflict-check.

Если новый `Lesson` пересекается только с отменёнными занятиями текущего `Teacher`:

- конфликт не фиксируется;
- warning не отображается;
- стандартный сценарий создания продолжается.

Пользователь не должен иметь возможности:

- передать произвольный `teacher_id`;
- проверить расписание другого `Teacher`;
- повлиять на результат проверки подменой идентификатора Teacher.

Пересечение с занятием другого преподавателя не является конфликтом в рамках US-04.

---

## 7. Основной сценарий без конфликта

1. `Teacher` открывает форму создания занятия.
2. Выбирает `Student`.
3. Указывает дату, время и остальные необходимые параметры.
4. Инициирует создание занятия.
5. Система определяет временной интервал нового `Lesson`.
6. Система проверяет его на пересечение с существующими неотменёнными `Lesson` текущего `Teacher`.
7. Пересечение отсутствует.
8. Система продолжает стандартный сценарий создания занятия.
9. `Lesson` успешно создаётся.
10. Расписание обновляется и отображает созданное занятие.

Сценарий существующего создания занятия без конфликта не должен быть нарушен.

---

## 8. Сценарий при обнаружении конфликта

1. `Teacher` заполняет форму создания `Lesson`.
2. Система выполняет проверку пересечений.
3. Обнаруживается один или несколько конфликтующих неотменённых `Lesson`.
4. Новый `Lesson` ещё не создаётся.
5. Пользователю отображается warning о конфликте расписания.
6. Warning содержит достаточную информацию для понимания причины конфликта.
7. `Teacher` выбирает дальнейшее действие:
   - изменить дату или время;
   - отменить создание;
   - продолжить создание несмотря на конфликт.

---

## 9. Действия после warning

### 9.1. Изменить дату или время

Если `Teacher` изменяет дату или время:

1. пользователь возвращается к редактированию данных создаваемого `Lesson`;
2. после изменения временных параметров выполняется **новая проверка пересечения**;
3. предыдущий результат проверки не считается актуальным.

### 9.2. Отменить создание

Если `Teacher` отказывается от продолжения:

- новый `Lesson` не создаётся;
- существующие занятия не изменяются;
- ложный success не отображается.

### 9.3. Продолжить несмотря на конфликт

Если `Teacher` явно подтверждает продолжение:

- система разрешает создание конфликтующего `Lesson`;
- наличие пересечения не блокирует операцию;
- после успешного создания расписание отображает оба занятия.

Создание конфликтующего `Lesson` без явного подтверждения пользователя не допускается.

---

## 10. Данные в предупреждении

Warning должен позволять пользователю понять, с каким занятием возникает конфликт.

Минимально отображаются:

- факт обнаружения пересечения;
- дата конфликтующего занятия;
- время начала;
- время окончания либо продолжительность;
- человекочитаемые данные связанного `Student`;
- название / предмет занятия — если такие данные доступны.

Если конфликтующих занятий несколько, пользователь должен получить информацию, достаточную для понимания всех обнаруженных пересечений.

Отменённые `Lesson` в список конфликтующих занятий не включаются.

---

## 11. Date / Time / Timezone semantics

Сравнение временных интервалов должно выполняться однозначно независимо от timezone клиента.

Правила:

- Backend является источником истины для проверки пересечений;
- `starts_at` передаётся в timezone-aware формате;
- перед сравнением временные значения приводятся к единому временному представлению;
- отображение пользователю выполняется в согласованной пользовательской timezone;
- изменение timezone представления не должно изменять фактический момент начала `Lesson`;
- `ends_at` рассчитывается на основании нормализованного `starts_at` и `duration`.

Frontend не должен самостоятельно определять окончательный результат наличия или отсутствия конфликта независимо от Backend.

---

## 12. Состояния пользовательского сценария

### Normal

Форма создания доступна для заполнения.

### Loading

Во время проверки пересечения пользователь должен видеть состояние ожидания.

Повторное инициирование той же операции во время активной проверки не должно приводить к дублирующим запросам или созданию нескольких `Lesson`.

### No conflict

Пересечение с учитываемыми в conflict-check занятиями отсутствует, стандартное создание продолжается.

### Warning

Пересечение обнаружено. Пользователь получает информацию о конфликте и доступные действия.

Warning не должен визуально восприниматься как критическая системная ошибка.

### Error

Если проверка не может быть выполнена из-за Backend / API / transport error:

- система не должна трактовать результат как «конфликта нет»;
- `Lesson` не должен автоматически создаваться;
- пользователь получает понятное сообщение об ошибке;
- пользователь может повторить операцию.

### Success

После успешного создания `Lesson` пользователь получает ожидаемый результат сценария создания, а расписание обновляется актуальными данными.

---

## 13. Boundary cases

Обязательной проверке подлежат следующие случаи.

### Частичное пересечение

Существующее неотменённое занятие:

`10:00–11:00`

Новое:

`10:30–11:30`

Результат: **конфликт**.

### Новое занятие полностью внутри существующего

Существующее неотменённое занятие:

`10:00–12:00`

Новое:

`10:30–11:00`

Результат: **конфликт**.

### Существующее занятие полностью внутри нового

Существующее неотменённое занятие:

`10:30–11:00`

Новое:

`10:00–12:00`

Результат: **конфликт**.

### Полностью совпадающие интервалы

Существующее неотменённое занятие:

`10:00–11:00`

Новое:

`10:00–11:00`

Результат: **конфликт**.

### Соприкосновение справа

Существующее неотменённое занятие:

`10:00–11:00`

Новое:

`11:00–12:00`

Результат: **нет конфликта**.

### Соприкосновение слева

Существующее неотменённое занятие:

`11:00–12:00`

Новое:

`10:00–11:00`

Результат: **нет конфликта**.

### Пересечение только с отменённым Lesson

Существующее занятие:

`10:00–11:00`, статус `cancelled`.

Новое:

`10:30–11:30`.

Результат: **нет конфликта**.

Отменённый `Lesson` не участвует в conflict-check.

---

## 14. Negative scenarios

Система должна корректно обрабатывать:

- отсутствие authentication;
- пользователя без роли `Teacher`;
- недоступного текущему Teacher `Student`;
- некорректные дату / время / duration;
- попытку создать занятие в недопустимом прошлом времени;
- ошибку Backend при выполнении проверки;
- transport error;
- некорректный ответ API;
- изменение данных формы после уже выполненной проверки;
- попытку продолжить конфликтное создание без явного подтверждения.

Ошибка проверки не должна восприниматься как отсутствие конфликта.

---

## 15. Business Rules

1. Проверка выполняется до окончательного создания `Lesson`.
2. Проверяются только занятия текущего `Teacher`.
3. `Lesson` со статусом `cancelled` не участвует в conflict-check.
4. Конфликт определяется пересечением временных интервалов учитываемых занятий.
5. Соприкосновение интервалов по границе конфликтом не является.
6. Конфликт создаёт warning, но не абсолютный запрет.
7. Для создания конфликтующего `Lesson` требуется явное подтверждение `Teacher`.
8. После изменения даты или времени проверка выполняется повторно.
9. Backend является источником истины по результату проверки.
10. Ошибка проверки не эквивалентна результату «конфликтов нет».
11. Стандартный сценарий US-01 без конфликта должен продолжать работать без регрессии.

---

## 16. Зависимости

### US-01 — Создание занятия

US-04 расширяет существующий flow создания `Lesson` и не заменяет его.

### US-05 — Перенос занятия

При переносе на другое время должна использоваться та же семантика определения конфликтов.

### US-06 — Отмена занятия

`Lesson`, отменённый согласно US-06, сохраняется в системе, но не участвует в conflict-check US-04.

### US-09 — Регулярные занятия

При создании серии каждый создаваемый экземпляр должен учитывать правила конфликтов US-04 согласно отдельной спецификации US-09.

---

## 17. Out of Scope

В US-04 не входят:

- автоматический перенос конфликтующего `Lesson`;
- автоматическая отмена существующего занятия;
- автоматический поиск свободного времени;
- оптимизация расписания;
- массовое изменение расписания;
- проверка правил регулярной серии занятий;
- автоматическое разрешение конфликтов;
- блокирование создания любого конфликтующего занятия без возможности подтверждения.

---

## 18. Пользовательский результат

После реализации US-04 `Teacher` заранее узнаёт о временном конфликте при создании занятия и может осознанно выбрать дальнейшее действие.

При отсутствии конфликта, в том числе если пересечение существует только с отменёнными `Lesson`, сценарий создания работает как обычно.

При наличии конфликта новый `Lesson` создаётся только после явного решения пользователя, а ошибка проверки никогда не воспринимается системой как успешное отсутствие конфликта.
