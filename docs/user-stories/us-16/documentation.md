# US-16 — Повторная отправка работы

## User Story

**Я как ученик хочу отправить исправленную версию работы после доработки, чтобы преподаватель мог повторно её проверить.**

---

## 1. Цель

Позволить `Student` после `needs_revision` создать новую Submission Attempt, не теряя предыдущую историю.

## 2. Предусловия

- Student аутентифицирован;
- Homework принадлежит текущему Student;
- Homework находится в `needs_revision`;
- существует предыдущая попытка и комментарий о доработке.

## 3. Основные правила

1. Повторная отправка разрешена только из `needs_revision`.
2. Создаётся новая попытка.
3. Предыдущая попытка не изменяется и не удаляется.
4. Номер новой попытки увеличивается последовательно.
5. После успешной отправки Homework → `submitted`.
6. Новая попытка становится актуальной для очереди Teacher.
7. Решение о доработке предыдущей попытки остаётся в истории.

## 4. Основной сценарий

1. Student открывает Homework в `needs_revision`.
2. Видит комментарий Teacher.
3. Выбирает повторную отправку.
4. Прикладывает исправленные материалы и/или комментарий.
5. Подтверждает.
6. Backend проверяет current_user, ownership и lifecycle.
7. Создаётся новая Submission Attempt.
8. Фиксируется новый `submitted_at`.
9. Номер попытки = предыдущий + 1.
10. Homework переходит в `submitted`.
11. Teacher снова видит работу в pending queue.
12. Student видит, что новая версия ожидает проверки.

## 5. Просрочка

Если пересдача выполняется после исходного `due_at`, признак просрочки рассчитывается последовательно с общими правилами Homework.

Исторический late-признак предыдущих попыток не переписывается.

## 6. Внешний контракт

Используется та же операция создания попытки:

```text
POST /api/v1/homework/{homework_id}/submissions
```

Backend по lifecycle определяет, допустима ли текущая отправка.

Response возвращает созданную попытку и актуальный Homework state.

## 7. Ошибочные сценарии

- Homework не в `needs_revision`;
- Student отправляет чужой Homework;
- активная попытка уже `submitted`;
- повторный запрос;
- upload error;
- state изменился конкурентно;
- Backend error.

## 8. Boundary cases

- вторая попытка;
- третья и последующие попытки;
- отсутствие новых файлов при наличии текстового исправления;
- новая попытка сразу после получения `needs_revision`;
- double click;
- несколько вкладок.

## 9. Зависимости

- US-15;
- US-12;
- US-13;
- US-17.

## 10. Out of Scope

- редактирование старой попытки;
- параллельные активные drafts;
- diff содержимого файлов;
- автоматическое объединение файлов попыток.

## 11. Пользовательский результат

Student может исправить работу и отправить новую версию, а Teacher получает её как новую актуальную попытку без потери предыдущей истории.

## 15. Security & authorization

- Backend является финальной точкой контроля доступа; скрытие кнопки/маршрута на Frontend не считается достаточной защитой.
- Идентификаторы из request нельзя использовать для обхода ownership.
- При отказе доступа response не должен раскрывать данные чужого Teacher/Student/Homework/Submission.

## 16. Reliability & concurrency

- Mutating action считается завершённым только после подтверждения Backend.
- Double-click, retry и конкурентная смена lifecycle не должны приводить к двойному применению одного логического действия.
- При конфликте состояния пользователь получает явный conflict/error state и должен перезагрузить актуальные данные.

## 17. Observability & performance

Для ошибок, влияющих на Product Acceptance, должны быть доступны диагностические данные Backend/Frontend (request correlation/лог ошибки или эквивалент в принятом стеке) без вывода чувствительных данных пользователю.

Performance проверяется как Sprint-ориентир, а не production SLA: интерактивные запросы — ориентир p95 ≤ 500 мс, агрегирующие статистические запросы — p95 ≤ 1000 мс на типовом тестовом объёме.
