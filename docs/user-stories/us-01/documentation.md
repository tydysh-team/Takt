# US-01 — Создание занятия

## User Story

> Я как преподаватель хочу создать занятие для конкретного ученика на выбранные дату и время, чтобы запланировать проведение урока.

## 1. Пользовательский результат

Аутентифицированный `Teacher` может создать занятие для доступного ему `Student`.

После успешного создания занятие сохраняется системой и появляется в расписании.

## 2. Основной сценарий

1. Teacher открывает расписание.
2. Выбирает создание нового занятия.
3. Выбирает доступного Student.
4. Указывает:
   - название занятия;
   - опциональное описание;
   - дату;
   - время начала;
   - длительность.
5. Подтверждает создание.
6. Система проверяет данные и доступность Student.
7. При успешном результате создаётся Lesson.
8. Расписание обновляется, пользователь получает подтверждение создания.

## 3. Данные занятия

Для создания обязательны:

- `Student`;
- название;
- дата и время начала;
- длительность.

Описание является опциональным.

Созданное занятие связано с:

- текущим Teacher;
- выбранным Student;
- названием;
- описанием при наличии;
- временем начала;
- длительностью.

## 4. Основные правила

### Teacher

Teacher, от имени которого создаётся Lesson, определяется системой из текущего authentication context.

Frontend не выбирает Teacher передачей произвольного `teacher_id`.

### Student

Для создания занятия Student должен:

- существовать;
- быть доступен текущему Teacher через актуальную связь `Teacher ↔ Student`.

Если Student отсутствует или недоступен текущему Teacher, занятие не создаётся.

### Дата и время

Дата и время интерпретируются в часовом поясе пользователя и передаются Backend как однозначный момент времени.

Создание занятия в прошлом не допускается.

### Длительность

Длительность занятия должна быть положительным значением.

Пользовательский интерфейс предоставляет предусмотренные варианты длительности занятия.

## 5. Внешнее взаимодействие

### Получение доступных Students

```text
GET /api/v1/teachers/me/students
```

Возвращаются Students, доступные текущему Teacher.

Teacher определяется из authentication context.

### Создание Lesson

```text
POST /api/v1/lessons
```

Основные данные запроса:

```json
{
  "student_id": "...",
  "title": "Математика",
  "description": null,
  "starts_at": "2026-10-23T14:00:00+04:00",
  "duration_minutes": 60
}
```

При успешном создании Backend возвращает созданный Lesson.

Общие правила API и ошибок определены в [`../../general/api-conventions.md`](../../general/api-conventions.md).

## 6. Ошибочные сценарии

Создание не должно считаться успешным, если:

- отсутствуют обязательные данные;
- данные имеют некорректный формат;
- Student отсутствует или недоступен Teacher;
- начало занятия находится в прошлом;
- пользователь не аутентифицирован;
- текущему пользователю недоступен Teacher-сценарий.

При ошибке новый Lesson не должен считаться созданным.

## 7. Пользовательские состояния

Интерфейс должен корректно отображать применимые состояния:

- normal;
- loading / submitting;
- validation error;
- Backend / API error;
- success.

Ошибка не должна отображаться как успешное создание.

После успешного создания пользователь получает понятное подтверждение, а расписание актуализируется.

## 8. Out of Scope

US-01 не определяет:

- проверку конфликтов и пересечений расписания;
- перенос занятия;
- отмену занятия;
- статусы занятия;
- посещаемость;
- регулярные занятия.

Эти возможности покрываются отдельными User Story.

Внутренняя архитектура, persistence, структура БД, services, repositories, state management и другие технические решения находятся в зоне ответственности разработчиков и Code Review.
