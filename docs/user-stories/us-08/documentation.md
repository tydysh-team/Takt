# US-08 — Учёт посещаемости

## User Story

**Я как преподаватель хочу отмечать факт посещения занятия учеником, чтобы сохранять историю проведённых занятий.**

---

## 1. Цель

Позволить `Teacher` установить и при необходимости изменить отметку посещаемости `Student` для конкретного `Lesson`.

Отметка должна:

- относиться к конкретному занятию;
- сохраняться Backend;
- повторно отображаться при следующем просмотре;
- быть доступна только в тех состояниях Lesson, где фиксация посещаемости имеет смысл.

---

## 2. Основной пользователь

`Teacher`.

### Связанные сущности

- `Teacher`;
- `Student`;
- `Lesson`;
- attendance-отметка.

---

## 3. Предусловия

Для выполнения сценария:

- пользователь аутентифицирован;
- пользователь имеет роль `Teacher`;
- `Lesson` существует;
- `Lesson` принадлежит текущему `Teacher`;
- `Student` связан с данным `Lesson`;
- состояние занятия допускает установку attendance.

---

## 4. Допустимые значения attendance

Для одного `Lesson` attendance может иметь одно из состояний:

- `not_set` — отметка не установлена;
- `present` — Student присутствовал;
- `absent` — Student отсутствовал.

### Пользовательские значения

В интерфейсе:

- `not_set` → «Не отмечено»;
- `present` → «Присутствовал»;
- `absent` → «Отсутствовал».

`not_set` является отсутствием установленной отметки, а не отдельным фактом посещения.

---

## 5. Связь с Lesson и Student

Attendance относится к конкретному `Lesson`.

Отметка должна быть однозначно связана:

- с конкретным занятием;
- с `Student`, для которого создан этот Lesson;
- с владельцем Lesson — текущим `Teacher`.

Отметка одного Lesson не должна влиять на другие занятия того же Student.

---

## 6. Правила доступа

Изменять attendance может только текущий авторизованный `Teacher`, которому принадлежит `Lesson`.

`Teacher` определяется из authentication context.

Не допускается:

- изменение attendance чужого Lesson;
- подмена `teacher_id`;
- установка attendance для произвольного Student, не связанного с Lesson.

---

## 7. Когда attendance доступен

Установка или изменение attendance допускается, если:

- Lesson не отменён;
- фактическое время начала занятия уже наступило.

То есть:

`now >= starts_at`

### Допустимые случаи

- занятие уже началось;
- занятие завершилось;
- перенесённое занятие, фактическое новое время которого уже наступило.

---

## 8. Когда attendance недоступен

Attendance не должен быть доступен для:

### Planned / будущего Lesson

Если:

`now < starts_at`

то отметить посещаемость нельзя.

### Cancelled Lesson

Если Lesson отменён согласно US-06:

- attendance недоступен;
- новое значение сохранить нельзя.

### Недоступного / чужого Lesson

Teacher не может изменить attendance занятия другого Teacher.

---

## 9. Связь с US-07

Доступность attendance должна быть согласована с актуальным состоянием Lesson.

### Planned

Изменение недоступно.

### In Progress

Изменение доступно.

### Completed

Изменение доступно.

### Cancelled

Изменение недоступно.

### Rescheduled

Сам факт переноса не запрещает attendance.

Для перенесённого Lesson доступность определяется по **актуальным** `starts_at` и состоянию отмены:

- новое время ещё не наступило → attendance недоступен;
- новое время наступило → attendance доступен;
- Lesson отменён → attendance недоступен.

---

## 10. Основной сценарий установки attendance

1. `Teacher` открывает собственный Lesson.
2. Система загружает актуальные данные занятия.
3. Проверяется доступность attendance.
4. Текущая отметка отсутствует.
5. UI отображает состояние «Не отмечено».
6. `Teacher` выбирает:
   - «Присутствовал»;
   - либо «Отсутствовал».
7. Frontend отправляет изменение Backend.
8. Backend проверяет:
   - ownership;
   - допустимость значения;
   - состояние Lesson.
9. Значение сохраняется.
10. Frontend получает актуальное состояние.
11. Сохранённая отметка отображается пользователю.

---

## 11. Изменение ранее установленной отметки

Ранее установленное значение можно изменить.

Пример:

`present → absent`

или:

`absent → present`

После изменения:

- сохраняется новое актуальное значение;
- предыдущее значение больше не считается текущим;
- после refresh отображается последнее сохранённое состояние.

История изменений attendance в рамках US-08 отдельно не ведётся.

---

## 12. Повторное получение

После успешного сохранения attendance должен корректно отображаться при:

- повторном открытии Lesson;
- обновлении страницы;
- повторном получении данных Backend;
- повторном входе пользователя.

Frontend не должен хранить attendance только локально.

---

## 13. Ошибка сохранения

Если Backend не смог сохранить новое значение:

- предыдущее attendance-состояние сохраняется;
- UI не должен показывать новое значение как успешно сохранённое;
- пользователь получает error-state;
- ложный success отсутствует.

После refresh отображается фактическое Backend-состояние.

---

## 14. Атомарность изменения

Изменение attendance является одной логической операцией.

При ошибке:

- значение не должно изменяться частично;
- связанный Lesson не должен повреждаться;
- состояние Frontend не должно противоречить Backend.

---

## 15. Пользовательские состояния

### Not Set

Отметка ещё не установлена.

### Present

Сохранено значение `present`.

### Absent

Сохранено значение `absent`.

### Disabled

Изменение attendance недоступно из-за состояния Lesson или прав пользователя.

### Loading

Выполняется загрузка или сохранение.

### Error

Операция не выполнена.

### Success

Backend подтвердил сохранение нового значения.

---

## 16. Loading-state

Во время активного запроса:

- пользователь видит состояние ожидания;
- повторное сохранение не должно запускать несколько конкурирующих операций;
- новое значение не должно считаться подтверждённым до успешного ответа Backend.

---

## 17. API / Backend error

При Backend / API / transport error:

- существующее сохранённое значение не теряется;
- новое неподтверждённое значение не становится актуальным;
- error не отображается как success;
- пользователь может повторить действие.

---

## 18. Неизвестное attendance-значение

Если Frontend получает неизвестное или неподдерживаемое значение:

- интерфейс не должен падать;
- значение не должно автоматически подменяться на `not_set`, `present` или `absent`;
- ситуация должна обрабатываться безопасно и может считаться integration defect.

---

## 19. Boundary cases

Обязательной проверке подлежат:

### Attendance отсутствует

Результат:

`not_set`.

### Первичная установка Present

`not_set → present`.

### Первичная установка Absent

`not_set → absent`.

### Изменение Present → Absent

Новое значение сохраняется.

### Изменение Absent → Present

Новое значение сохраняется.

### Точная граница начала Lesson

Если:

`now == starts_at`

attendance становится доступен.

### Будущий Lesson

Если:

`now < starts_at`

attendance недоступен.

### Completed Lesson

Attendance доступен.

### Cancelled Lesson

Attendance недоступен.

### Rescheduled Lesson до нового starts_at

Attendance недоступен.

### Rescheduled Lesson после нового starts_at

Attendance доступен.

---

## 20. Negative scenarios

Необходимо корректно обработать:

- отсутствие authentication;
- пользователя без роли `Teacher`;
- чужой Lesson;
- отсутствующий Lesson;
- будущий Lesson;
- cancelled Lesson;
- недопустимое attendance-значение;
- Backend error;
- transport error;
- некорректный API response;
- повторную отправку во время активного запроса.

---

## 21. Business Rules

1. Attendance относится к конкретному Lesson.
2. Attendance устанавливает только Teacher этого Lesson.
3. Допустимые значения: `not_set / present / absent`.
4. `not_set` означает отсутствие сохранённой отметки.
5. Attendance нельзя устанавливать до начала Lesson.
6. Attendance нельзя устанавливать для cancelled Lesson.
7. Для in-progress и completed Lesson attendance доступен.
8. Перенос сам по себе не запрещает attendance — используется актуальное новое время.
9. Ранее установленную отметку можно изменить.
10. Backend является источником истины.
11. Ошибка сохранения не изменяет предыдущее значение.
12. После refresh сохраняется последнее подтверждённое Backend-значение.

---

## 22. Зависимости

### US-01 — Создание занятия

Attendance относится к существующему Lesson.

### US-03 — Календарь Teacher

Точка входа в управление attendance может находиться в карточке Lesson Teacher.

### US-05 — Перенос занятия

После переноса используются актуальные новые временные данные.

### US-06 — Отмена занятия

Cancelled Lesson не допускает изменение attendance.

### US-07 — Статус занятия

Доступность управления attendance зависит от фактического состояния Lesson.

---

## 23. Out of Scope

В US-08 не входят:

- статистика посещаемости;
- агрегированная посещаемость Student;
- отчёты;
- причины отсутствия;
- комментарии к attendance;
- штрафы;
- оплата занятий;
- автоматическое определение присутствия;
- Student-facing управление attendance;
- история изменений отметки;
- массовая установка attendance для нескольких Lesson.

---

## 24. Пользовательский результат

`Teacher` может зафиксировать факт присутствия или отсутствия `Student` для конкретного проведённого либо уже начавшегося `Lesson`.

Сохранённая отметка остаётся доступной при последующих просмотрах и может быть исправлена Teacher.

Для будущих, отменённых и недоступных занятий изменение attendance не разрешается.
