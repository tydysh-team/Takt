# US-15 — Возврат работы на доработку

## User Story

**Я как преподаватель хочу вернуть работу ученику на доработку с комментарием, чтобы он понимал, что необходимо исправить.**

---

## 1. Цель

Позволить `Teacher` вернуть актуальную Submission Attempt Student на доработку вместо принятия работы.

## 2. Предусловия

- Teacher аутентифицирован;
- Submission принадлежит Homework текущего Teacher;
- Submission является актуальной;
- Homework находится в `submitted`.

## 3. Обязательная обратная связь

Возврат на доработку сопровождается комментарием Teacher, объясняющим, что требуется исправить.

Пустой или состоящий только из пробелов комментарий не должен приводить к `needs_revision`.

## 4. Основные правила

1. Возврат применяется к конкретной актуальной попытке.
2. После успешного возврата Homework → `needs_revision`.
3. Решение и комментарий сохраняются Backend.
4. Student видит состояние и комментарий.
5. Отправленная попытка остаётся в истории.
6. Работа исчезает из pending queue до новой попытки Student.

## 5. Основной сценарий

1. Teacher открывает submitted attempt.
2. Выбирает «Вернуть на доработку».
3. Вводит обязательный комментарий.
4. Подтверждает действие.
5. Backend проверяет ownership и state.
6. Сохраняет решение по попытке.
7. Homework получает `needs_revision`.
8. UI Teacher показывает подтверждение.
9. Student видит новое состояние и комментарий.
10. Student может перейти к повторной отправке.

## 6. Внешний контракт

```text
POST /api/v1/teachers/me/homework/submissions/{submission_id}/revision
```

Пример:

```json
{
  "comment": "Исправь вычисления во второй задаче"
}
```

Response возвращает актуальное состояние Homework и результата проверки.

## 7. Ошибочные сценарии

- отсутствует комментарий;
- чужая попытка;
- неактуальная попытка;
- Homework уже `reviewed`;
- Homework уже `needs_revision`;
- Submission отсутствует;
- Backend / transport error.

При ошибке состояние не меняется.

## 8. Boundary cases

- комментарий только из пробелов;
- очень короткий валидный комментарий;
- повторный click;
- состояние изменилось между открытием и подтверждением;
- Student одновременно просматривает Homework.

## 9. Зависимости

- US-12 / US-16;
- US-13;
- US-16;
- общий lifecycle Homework.

## 10. Out of Scope

- автоматическое изменение deadline;
- создание нового Homework вместо доработки;
- чат;
- удаление прошлой попытки;
- редактирование Student-файлов Teacher.

## 11. Пользовательский результат

Teacher возвращает работу с конкретной обратной связью, а Student однозначно понимает, что требуется новая исправленная попытка.

## 15. Security & authorization

- Backend является финальной точкой контроля доступа; скрытие кнопки/маршрута на Frontend не считается достаточной защитой.
- Идентификаторы из request нельзя использовать для обхода ownership.
- При отказе доступа response не должен раскрывать данные чужого Teacher/Student/Homework/Submission.

## 16. Reliability & concurrency

- Mutating action считается завершённым только после подтверждения Backend.
- Double-click, retry и конкурентная смена lifecycle не должны приводить к двойному применению одного логического действия.
- При конфликте состояния пользователь получает явный conflict/error state и должен перезагрузить актуальные данные.

## 17. Observability & performance

Для ошибок, влияющих на Product Acceptance, должны быть доступны диагностические данные Backend/Frontend (request correlation/лог ошибки или эквивалент в принятом стеке) без вывода чувствительных данных пользователю.

Performance проверяется как Sprint-ориентир, а не production SLA: интерактивные запросы — ориентир p95 ≤ 500 мс, агрегирующие статистические запросы — p95 ≤ 1000 мс на типовом тестовом объёме.
