# US-10 — Назначение домашнего задания

## User Story

**Я как преподаватель хочу назначить ученику домашнее задание с описанием, сроком выполнения и материалами, чтобы дать ему самостоятельную работу.**

---

## 1. Цель

Позволить аутентифицированному `Teacher` создать Homework для конкретного доступного `Student`.

После успешного назначения задание сохраняется Backend и становится доступно Teacher и соответствующему Student.

## 2. Основной пользователь и сущности

Основной пользователь — `Teacher`.

Связанные сущности:

- `Teacher`;
- `Student`;
- `Homework`;
- материалы / вложения.

## 3. Предусловия

- пользователь аутентифицирован;
- пользователь имеет доступ к Teacher-сценарию;
- Student существует;
- между текущим Teacher и Student существует допустимая связь;
- заполнены обязательные данные Homework.

## 4. Данные Homework

Обязательные пользовательские данные:

- `student_id`;
- `title`;
- `due_at`.

Дополнительные данные:

- `description`;
- материалы / вложения.

Teacher определяется из authentication context и не выбирается клиентом произвольно.

`due_at` должен быть timezone-aware и однозначно отображаться Student.

## 5. Основные правила

1. Homework назначается одному конкретному Student.
2. Созданное задание принадлежит текущему Teacher.
3. После создания lifecycle-status = `assigned`.
4. Deadline не удаляет задание автоматически.
5. Материалы Teacher доступны Student вместе с заданием.
6. Ошибка сохранения не должна создавать частичное Homework.
7. Homework не считается созданным до подтверждения Backend.

## 6. Основной сценарий

1. Teacher открывает контекст конкретного Student.
2. Выбирает создание Homework.
3. Заполняет название, описание, срок и материалы.
4. Frontend валидирует обязательные поля.
5. Teacher подтверждает назначение.
6. Backend определяет текущего Teacher.
7. Backend проверяет связь Teacher ↔ Student.
8. Backend валидирует данные и `due_at`.
9. Homework сохраняется.
10. UI получает созданный объект.
11. Teacher видит подтверждение.
12. Student получает задание при следующей загрузке списка.

## 7. Внешний контракт

Создание Homework:

```text
POST /api/v1/homework
```

Пример JSON-части запроса без файловой реализации:

```json
{
  "student_id": "...",
  "title": "Решить задачи 1–10",
  "description": "Повторить тему перед выполнением",
  "due_at": "2026-11-08T18:00:00+04:00"
}
```

Если материалы передаются отдельным upload-flow, способ передачи файлов может отличаться, но итоговое Homework должно однозначно ссылаться на доступные вложения.

Успешный response возвращает созданное Homework.

## 8. Ошибочные сценарии

Создание не считается успешным при:

- отсутствии authentication;
- отсутствии Teacher-доступа;
- недоступном Student;
- пустом названии;
- отсутствующем обязательном deadline;
- некорректном date/time;
- ошибке загрузки обязательного вложения;
- Backend / transport error.

## 9. Пользовательские состояния

- form / normal;
- loading student context;
- submitting;
- validation error;
- upload error;
- Backend / API error;
- success.

Во время submitting повторное подтверждение не должно создавать дубликаты из одного пользовательского действия.

## 10. Boundary cases

- описание отсутствует;
- материалов нет;
- несколько материалов;
- deadline находится близко к текущему времени;
- Student перестал быть доступен между открытием формы и отправкой;
- повторный click во время активного запроса.

## 11. Зависимости

- authentication / roles;
- связь `Teacher ↔ Student`;
- [`../../general/homework.md`](../../general/homework.md);
- [`../../foundation/api-conventions.md`](../../foundation/api-conventions.md).

## 12. Out of Scope

- групповое Homework;
- массовое назначение;
- шаблоны;
- уведомления / reminders;
- автоматическая проверка;
- изменение уже отправленной Student попытки.

## 13. Пользовательский результат

Teacher может назначить конкретному Student самостоятельную работу с понятным сроком и материалами, а созданное задание сохраняется и становится доступно Student.

## 15. Security & authorization

- Backend является финальной точкой контроля доступа; скрытие кнопки/маршрута на Frontend не считается достаточной защитой.
- Идентификаторы из request нельзя использовать для обхода ownership.
- При отказе доступа response не должен раскрывать данные чужого Teacher/Student/Homework/Submission.

## 16. Reliability & concurrency

- Mutating action считается завершённым только после подтверждения Backend.
- Double-click, retry и конкурентная смена lifecycle не должны приводить к двойному применению одного логического действия.
- При конфликте состояния пользователь получает явный conflict/error state и должен перезагрузить актуальные данные.

## 17. Observability & performance

Для ошибок, влияющих на Product Acceptance, должны быть доступны диагностические данные Backend/Frontend (request correlation/лог ошибки или эквивалент в принятом стеке) без вывода чувствительных данных пользователю.

Performance проверяется как Sprint-ориентир, а не production SLA: интерактивные запросы — ориентир p95 ≤ 500 мс, агрегирующие статистические запросы — p95 ≤ 1000 мс на типовом тестовом объёме.
