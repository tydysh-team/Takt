# US-14 — Оценка и комментарий к работе

## User Story

**Я как преподаватель хочу выставить оценку и оставить комментарий к работе, чтобы дать ученику обратную связь.**

---

## 1. Цель

Позволить `Teacher` проверить актуальную отправленную попытку и сохранить результат, который затем видит соответствующий `Student`.

## 2. Предусловия

- Teacher аутентифицирован;
- Submission существует;
- Submission относится к Homework текущего Teacher;
- это актуальная попытка Homework;
- Homework находится в `submitted`.

## 3. Результат проверки

Teacher может сохранить:

- оценку;
- текстовый комментарий;
- решение о принятии работы.

Шкала оценки должна быть единой для Backend и Frontend и фиксироваться в контракте реализации до разработки UI и API.

## 4. Основные правила

1. Проверяется конкретная Submission Attempt.
2. Результат привязан именно к этой попытке.
3. После успешного принятия Homework переходит в `reviewed`.
4. Student видит результат только после подтверждённого сохранения Backend.
5. Повторное сохранение не создаёт несколько независимых review results для одной попытки.
6. Чужая работа недоступна.

## 5. Основной сценарий

1. Teacher открывает submitted attempt.
2. Изучает комментарий и вложения Student.
3. Вводит оценку и комментарий.
4. Выбирает действие принятия / сохранения результата.
5. Frontend валидирует форму.
6. Backend проверяет ownership и lifecycle.
7. Review Result сохраняется.
8. Homework становится `reviewed`.
9. Работа исчезает из pending queue.
10. Student видит оценку и комментарий в своём Homework.

## 6. Внешний контракт

```text
POST /api/v1/teachers/me/homework/submissions/{submission_id}/review
```

Пример body:

```json
{
  "grade": 85,
  "comment": "Хорошая работа, проверь пункт 4"
}
```

`grade` приведён как пример числовой модели. Точная шкала должна быть согласована до реализации и одинаково валидироваться Backend и Frontend.

Успешный response возвращает актуальный review/submission state.

## 7. Валидация

- недопустимое значение оценки отклоняется;
- комментарий валидируется по формату;
- review нельзя сохранить для неактуальной / чужой попытки;
- review нельзя применить к Homework, который уже сменил состояние.

## 8. Ошибка сохранения

При ошибке:

- Homework остаётся в предыдущем состоянии;
- попытка остаётся непроверенной;
- UI не показывает оценку как подтверждённую;
- pending queue после reload соответствует Backend.

## 9. Boundary cases

- минимальное допустимое значение оценки;
- максимальное допустимое значение;
- пустой комментарий, если модель допускает его;
- повторное нажатие save;
- состояние изменилось в другой вкладке;
- Student открывает Homework сразу после сохранения.

## 10. Зависимости

- US-12 / US-16;
- US-13;
- US-11;
- [`../../general/homework.md`](../../general/homework.md).

## 11. Out of Scope

- сложные rubric;
- автоматическая проверка;
- AI feedback;
- публичные рейтинги;
- сравнение Students.

## 12. Пользовательский результат

Teacher фиксирует понятную обратную связь по конкретной попытке, а Student видит подтверждённый результат проверки.

## 15. Security & authorization

- Backend является финальной точкой контроля доступа; скрытие кнопки/маршрута на Frontend не считается достаточной защитой.
- Идентификаторы из request нельзя использовать для обхода ownership.
- При отказе доступа response не должен раскрывать данные чужого Teacher/Student/Homework/Submission.

## 16. Reliability & concurrency

- Mutating action считается завершённым только после подтверждения Backend.
- Double-click, retry и конкурентная смена lifecycle не должны приводить к двойному применению одного логического действия.
- При конфликте состояния пользователь получает явный conflict/error state и должен перезагрузить актуальные данные.

## 17. Observability & performance

Для ошибок, влияющих на Product Acceptance, должны быть доступны диагностические данные Backend/Frontend (request correlation/лог ошибки или эквивалент в принятом стеке) без вывода чувствительных данных пользователю.

Performance проверяется как Sprint-ориентир, а не production SLA: интерактивные запросы — ориентир p95 ≤ 500 мс, агрегирующие статистические запросы — p95 ≤ 1000 мс на типовом тестовом объёме.
