# US-21 — Статистика ученика

## User Story

**Я как ученик хочу видеть собственную статистику занятий и домашних заданий, чтобы понимать свой текущий прогресс.**

---

## 1. Цель

Дать `Student` собственное представление прогресса на тех же фактических данных, которые используются в Teacher-статистике.

## 2. Основной пользователь

`Student`.

Backend определяет Student из authentication context.

Произвольный `student_id` не используется для доступа к чужой статистике.

## 3. Состав страницы

Student видит понятные блоки:

- история / показатели занятий и посещаемости;
- выполнение Homework;
- результаты проверок;
- динамика по доступному периоду, если она рассчитана.

Служебные данные Teacher, не предназначенные Student, не попадают в response.

## 4. Согласованность с Teacher view

Для одного Student и одного периода общие фактические показатели совпадают с Teacher view, если обе роли имеют доступ к тем же исходным данным.

Например:

- число назначенных Homework;
- число отправленных;
- attendance;
- сохранённые оценки.

UI может отличаться визуально и по детализации.

## 5. Период

Student должен понимать, за какой период показаны данные.

При смене периода метрики пересчитываются на тех же правилах, что и Teacher view.

## 6. Основной сценарий

1. Student открывает «Мой прогресс».
2. Backend определяет current Student.
3. Загружает доступные progress metrics.
4. UI показывает статистику.
5. Student меняет период, если сценарий это позволяет.
6. Данные обновляются.
7. Student может перейти к своим Homework / занятиям из связанных блоков.

## 7. Внешний контракт

```text
GET /api/v1/students/me/progress
```

Query:

```text
?date_from=...&date_to=...
```

Response имеет те же `student_id`, `date_from`, `date_to`, `attendance`,
`homework` и `reviews`, что и Teacher progress API из US-20. `student_id`
определяется только по auth context; произвольный идентификатор в query
не принимается. Число работ с оценкой и средняя оценка рассчитываются по
последнему применимому принятому Review каждого Homework, без подмены
отсутствующей оценки нулём.

Сводка включает собственные Lesson и Homework Student от всех Teachers,
в том числе исторические записи после деактивации связи. Все проценты
рассчитываются по совокупным числителям и знаменателям, средняя оценка —
по отдельным оценённым работам. Исходные Lesson и Homework содержат
`teacher_id` или сведения о Teacher для однозначного drill-down.

## 8. Privacy / authorization

Не допускается:

- получение статистики другого Student;
- передача произвольного `student_id` для обхода ограничения;
- утечка внутренних заметок Teacher;
- утечка данных других Students.

## 9. Empty / Loading / Error

- отсутствие данных — корректный empty state;
- loading отображается отдельно;
- API error отображается отдельно;
- отсутствие Homework не ломает attendance block;
- отсутствие Lesson не ломает Homework block.

## 10. Boundary cases

- полностью пустой новый аккаунт;
- есть только Lesson;
- есть только Homework;
- часть Homework ещё не проверена;
- часть attendance = `not_set`;
- данные ровно на границе периода;
- несколько Teachers у одного Student.

Если Student связан с несколькими Teachers, источник каждого элемента должен оставаться однозначным.

## 11. Зависимости

- US-18–US-20;
- Student auth;
- US-11 для перехода к Homework;
- [`../../general/progress-statistics.md`](../../general/progress-statistics.md).

## 12. Out of Scope

- статистика других Students;
- внутренние служебные заметки Teacher;
- рейтинги;
- геймификация;
- сравнение с другими учениками.

## 13. Пользовательский результат

Student видит собственный учебный прогресс в одном месте и понимает связь между занятиями, Homework и результатами проверки.

## 15. Security & authorization

- Backend является финальной точкой контроля доступа; скрытие кнопки/маршрута на Frontend не считается достаточной защитой.
- Идентификаторы из request нельзя использовать для обхода ownership.
- При отказе доступа response не должен раскрывать данные чужого Teacher/Student/Homework/Submission.

## 16. Reliability & concurrency

- Mutating action считается завершённым только после подтверждения Backend.
- Double-click, retry и конкурентная смена lifecycle не должны приводить к двойному применению одного логического действия.
- При конфликте состояния пользователь получает явный conflict/error state и должен перезагрузить актуальные данные.

## 17. Observability & performance

Для ошибок, влияющих на Product Acceptance, должны быть доступны диагностические данные Backend/Frontend (request correlation/лог ошибки или эквивалент в принятом стеке) без вывода чувствительных данных пользователю.

Performance проверяется как Sprint-ориентир, а не production SLA: интерактивные запросы — ориентир p95 ≤ 500 мс, агрегирующие статистические запросы — p95 ≤ 1000 мс на типовом тестовом объёме.
