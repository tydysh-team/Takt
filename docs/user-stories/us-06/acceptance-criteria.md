# US-06 — Acceptance Criteria

## User Story

**Я как преподаватель хочу отменить занятие, чтобы ученик видел, что оно больше не состоится.**

---

## AC-US06-01 — Успешная отмена собственного Lesson

**Given**
- пользователь аутентифицирован как `Teacher`;
- существует собственный доступный `Lesson`;
- `Lesson` ещё не отменён.

**When**
- `Teacher` инициирует отмену;
- подтверждает действие.

**Then**
- Backend переводит `Lesson` в cancelled-state;
- запись `Lesson` сохраняется;
- hard delete не выполняется;
- Frontend отображает актуальное отменённое состояние.

---

## AC-US06-02 — Обязательное подтверждение

**When**
- `Teacher` инициирует отмену занятия.

**Then**
- до выполнения операции отображается confirmation;
- пользователь понимает, какой `Lesson` будет отменён;
- доступны действия подтверждения и отказа;
- до подтверждения состояние `Lesson` не изменяется.

---

## AC-US06-03 — Отказ пользователя от отмены

**Given**
- confirmation отображён.

**When**
- `Teacher` отменяет действие либо закрывает confirmation.

**Then**
- Backend-состояние `Lesson` не изменяется;
- cancelled-state не появляется;
- расписание остаётся в исходном состоянии;
- success-state отсутствует.

---

## AC-US06-04 — Отсутствие hard delete

После успешной отмены:

- запись `Lesson` продолжает существовать;
- сохраняется идентификатор `Lesson`;
- сохраняются связи с `Teacher` и `Student`;
- занятие доступно для последующего чтения;
- отмена не реализуется физическим удалением записи.

---

## AC-US06-05 — Cancelled-state для Teacher

После успешной отмены `Teacher` должен видеть:

- тот же `Lesson`;
- актуальный cancelled-status;
- визуальное отличие отменённого занятия от активного предстоящего;
- сохранение состояния после повторной загрузки данных.

Отменённый `Lesson` не должен выглядеть как обычное запланированное занятие.

---

## AC-US06-06 — Cancelled-state для Student

После успешной отмены соответствующий `Student` должен видеть:

- отменённый `Lesson`;
- актуальный cancelled-status;
- состояние, согласованное с отображением Teacher.

Student не должен видеть отменённый Lesson как обычное предстоящее занятие.

---

## AC-US06-07 — Отмена только собственного Lesson

Отмену может выполнять только текущий авторизованный `Teacher` для собственного `Lesson`.

`Teacher` определяется из authentication context.

Клиент не должен получать право на отмену через подмену `teacher_id`.

---

## AC-US06-08 — Попытка отменить чужой Lesson

**Given**
- `Lesson` принадлежит другому `Teacher` либо недоступен текущему пользователю.

**When**
- выполняется попытка отмены.

**Then**
- операция отклоняется;
- состояние `Lesson` не изменяется;
- cancelled-state не устанавливается;
- ложный success отсутствует.

---

## AC-US06-09 — Отсутствующий Lesson

**When**
- пользователь пытается отменить несуществующий `Lesson`.

**Then**
- операция завершается корректным not-found result;
- другие записи не изменяются;
- success-state не отображается.

---

## AC-US06-10 — Повторная отмена

**Given**
- `Lesson` уже находится в cancelled-state.

**When**
- выполняется повторная попытка отмены.

**Then**
- состояние обрабатывается предсказуемо;
- данные не повреждаются;
- новая дополнительная отмена не создаётся;
- `Lesson` не восстанавливается;
- hard delete не выполняется.

Допустимо:

- вернуть текущее cancelled-state;

или

- сообщить, что `Lesson` уже отменён.

Поведение должно быть единым для API и UI.

---

## AC-US06-11 — Backend / API error

**Given**
- пользователь подтвердил отмену.

**When**
- Backend / API / transport error не позволяет успешно завершить операцию.

**Then**
- исходное состояние `Lesson` сохраняется;
- cancelled-state не устанавливается;
- UI не отображает ложную отмену;
- пользователь получает error-state;
- после refresh отображается фактическое Backend-состояние.

---

## AC-US06-12 — Loading-state и защита от повторной операции

Во время выполнения запроса отмены:

- отображается loading-state;
- повторное подтверждение не должно инициировать несколько конкурентных операций;
- success не отображается до подтверждённого ответа Backend.

---

## AC-US06-13 — Сохранение состояния после refresh

**Given**
- `Lesson` успешно отменён.

**When**
- пользователь обновляет страницу либо повторно загружает данные.

**Then**
- cancelled-state сохраняется;
- `Lesson` не возвращается в active/planned состояние;
- Frontend отображает состояние, полученное от Backend.

---

## AC-US06-14 — Authentication

Неаутентифицированный пользователь не должен иметь возможности выполнить защищённый сценарий отмены.

Пользователь без роли `Teacher` не должен получать доступ к Teacher-action отмены.

---

## AC-US06-15 — Реальный Frontend ↔ Backend flow

Необходимо подтвердить сценарий без mock-response:

1. `Teacher` открывает собственный `Lesson`;
2. инициирует отмену;
3. получает confirmation;
4. подтверждает действие;
5. Frontend отправляет запрос в Backend;
6. Backend проверяет ownership;
7. Backend сохраняет cancelled-state без hard delete;
8. Frontend получает актуальный результат;
9. расписание Teacher обновляется;
10. Student получает то же актуальное состояние;
11. после refresh cancelled-state сохраняется.

---

## AC-US06-16 — Cancel / Error не создают ложного состояния

Во всех сценариях, где отмена фактически не состоялась:

- отказ пользователя;
- Backend error;
- transport error;
- authorization error;
- not-found;

UI не должен:

- показывать `Lesson` как отменённый;
- удалять его из расписания;
- отображать success.

---

## AC-US06-17 — Regression связанных сценариев

После внедрения US-06 должны сохранять работоспособность:

- `US-01` — создание занятия;
- `US-02` — расписание Student;
- `US-03` — календарь Teacher;
- `US-04` — conflict-flow;
- `US-05` — перенос занятия.

Отмена не должна нарушать существующие сценарии создания, просмотра и переноса `Lesson`.

---

# Обязательные Acceptance Criteria

Для Product Acceptance обязательными являются:

- `AC-US06-01` — успешная отмена;
- `AC-US06-02` — confirmation;
- `AC-US06-03` — отказ от отмены;
- `AC-US06-04` — отсутствие hard delete;
- `AC-US06-05` — Teacher cancelled-state;
- `AC-US06-06` — Student cancelled-state;
- `AC-US06-07` — ownership;
- `AC-US06-08` — чужой Lesson;
- `AC-US06-09` — not found;
- `AC-US06-10` — повторная отмена;
- `AC-US06-11` — Backend / API error;
- `AC-US06-12` — loading / duplicate protection;
- `AC-US06-13` — persistence after refresh;
- `AC-US06-14` — authentication / authorization;
- `AC-US06-15` — Frontend ↔ Backend E2E;
- `AC-US06-16` — отсутствие ложного состояния;
- `AC-US06-17` — regression.

Если хотя бы один обязательный Acceptance Criterion имеет статус `FAIL`, итоговый статус US-06 не может быть `PASS`.
