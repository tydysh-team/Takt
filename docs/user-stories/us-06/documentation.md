# US-06 — Отмена занятия

## User Story

**Я как преподаватель хочу отменить занятие, чтобы ученик видел, что оно больше не состоится.**

---

## 1. Цель

Позволить `Teacher` отменить собственный `Lesson` без физического удаления записи из системы.

После успешной отмены занятие должно сохраняться в системе в отменённом состоянии и отображаться с актуальным статусом как `Teacher`, так и соответствующему `Student`.

---

## 2. Основной пользователь

`Teacher`.

### Связанные сущности

- `Teacher`;
- `Student`;
- существующий `Lesson`.

---

## 3. Предусловия

Для выполнения сценария:

- пользователь аутентифицирован;
- пользователь имеет роль `Teacher`;
- `Lesson` существует;
- `Lesson` принадлежит текущему `Teacher`;
- занятие доступно для выполнения действия отмены.

---

## 4. Основной сценарий отмены

1. `Teacher` открывает собственный `Lesson`.
2. Выбирает действие отмены.
3. Система отображает confirmation-dialog.
4. Пользователь видит, какое занятие будет отменено.
5. `Teacher` подтверждает действие.
6. Backend изменяет состояние `Lesson` на отменённое.
7. Запись `Lesson` сохраняется в системе.
8. Frontend получает актуальное состояние.
9. `Teacher` видит отменённый Lesson.
10. Соответствующий `Student` видит отменённый Lesson с актуальным статусом.

---

## 5. Confirmation

Отмена является явным пользовательским действием и требует подтверждения.

До подтверждения:

- Backend не должен изменять состояние `Lesson`;
- UI не должен отображать Lesson как отменённый.

Пользователь должен иметь минимум два действия:

- подтвердить отмену;
- отказаться от отмены.

---

## 6. Отказ от отмены

Если пользователь закрывает confirmation-dialog или выбирает отмену действия:

- состояние `Lesson` не меняется;
- Backend не получает успешную операцию отмены;
- расписание остаётся в исходном состоянии;
- success-state не отображается.

---

## 7. Модель отменённого Lesson

Отмена не является физическим удалением.

После успешной операции:

- запись `Lesson` сохраняется в системе;
- занятие получает состояние `cancelled` либо согласованный эквивалент;
- идентификатор `Lesson` сохраняется;
- связанные данные `Teacher` / `Student` сохраняются;
- историческая запись о занятии не теряется.

`Hard delete` в рамках US-06 запрещён.

---

## 8. Правила доступа

Отменить `Lesson` может только текущий авторизованный `Teacher`, которому принадлежит занятие.

`Teacher` определяется из authentication context.

Не допускается:

- отмена чужого `Lesson`;
- подмена `teacher_id`;
- получение доступа к отмене через произвольный идентификатор пользователя.

При попытке отменить чужое или недоступное занятие:

- операция отклоняется;
- состояние `Lesson` не изменяется;
- пользователю возвращается корректный authorization / not-found result;
- ложный success отсутствует.

---

## 9. Повторная отмена

Повторная попытка отменить уже отменённый `Lesson` должна обрабатываться предсказуемо.

Система не должна:

- создавать новое дополнительное состояние отмены;
- повреждать существующие данные;
- восстанавливать занятие;
- удалять запись;
- приводить к противоречивому UI.

Допустимое поведение:

- операция считается идемпотентной и возвращает актуальное cancelled-state;

либо

- система сообщает, что занятие уже отменено.

Выбранное API-поведение должно быть единым и не изменять данные повторно.

---

## 10. Отображение для Teacher

После успешной отмены:

- `Lesson` остаётся доступным в согласованном представлении;
- визуально отличается от обычного предстоящего занятия;
- отображается cancelled-status;
- не воспринимается как активное запланированное занятие;
- после refresh состояние сохраняется.

---

## 11. Отображение для Student

Соответствующий `Student` должен видеть:

- тот же `Lesson`;
- актуальный cancelled-status;
- отсутствие представления занятия как обычного предстоящего.

Teacher и Student должны получать согласованное состояние одного `Lesson`.

---

## 12. Поведение в расписании

Отменённый `Lesson` не должен:

- отображаться как обычное активное предстоящее занятие;
- исчезать так, будто запись была удалена.

Конкретное визуальное представление определяется UX/UI, но пользователь должен однозначно понимать, что занятие **отменено**.

---

## 13. Сохранение состояния

Cancelled-state должен сохраняться Backend.

После:

- повторной загрузки данных;
- обновления страницы;
- повторного входа пользователя;

занятие должно оставаться отменённым.

Frontend не должен использовать только локальное состояние для определения отмены.

---

## 14. Backend / API error

Если операция отмены не завершилась успешно:

- исходное состояние `Lesson` сохраняется;
- cancelled-state не устанавливается;
- UI не должен показывать занятие как отменённое;
- пользователь получает error-state;
- ложный success отсутствует.

После refresh интерфейс должен отображать фактическое Backend-состояние.

---

## 15. Атомарность

Отмена является одной логической операцией.

При ошибке:

- состояние `Lesson` не изменяется частично;
- связанные данные не повреждаются;
- UI и Backend не должны оставаться в противоречивом состоянии.

---

## 16. Пользовательские состояния

### Normal

Teacher видит Lesson и доступное действие отмены.

### Confirmation

Пользователь подтверждает либо отменяет действие.

### Loading

Во время выполнения запроса:

- отображается состояние ожидания;
- повторное подтверждение не должно приводить к нескольким конкурентным операциям.

### Error

При ошибке:

- Lesson сохраняет исходное состояние;
- пользователь получает понятное сообщение;
- ложный cancelled-state отсутствует.

### Success

После подтверждённого успешного ответа:

- Lesson получает cancelled-state;
- UI обновляется актуальными данными.

---

## 17. Boundary cases

Обязательной проверке подлежат:

### Успешная отмена

Собственный Lesson успешно переводится в cancelled-state.

### Отказ в confirmation

Состояние не изменяется.

### Повторная отмена

Система обрабатывает уже отменённый Lesson предсказуемо и без изменения данных.

### Чужой Lesson

Операция запрещена.

### Не существующий Lesson

Операция не выполняется.

### Ошибка Backend

Исходное состояние сохраняется.

### Refresh после отмены

Cancelled-state сохраняется и отображается повторно.

---

## 18. Negative scenarios

Необходимо обработать:

- отсутствие authentication;
- пользователя без роли `Teacher`;
- чужой `Lesson`;
- отсутствующий `Lesson`;
- повторную отмену;
- отказ пользователя от confirmation;
- Backend error;
- transport error;
- некорректный API response;
- повторное подтверждение во время активного запроса.

Во всех неуспешных сценариях исходное состояние `Lesson` должно сохраняться.

---

## 19. Business Rules

1. Отменять Lesson может только его `Teacher`.
2. Отмена требует явного confirmation.
3. Отмена не приводит к hard delete.
4. Отменённый Lesson сохраняется в системе.
5. Teacher и Student должны видеть согласованный cancelled-state.
6. При отказе пользователя состояние не меняется.
7. При ошибке состояние не меняется.
8. Повторная отмена должна быть предсказуемой.
9. Backend является источником истины по состоянию Lesson.
10. После refresh cancelled-state сохраняется.

---

## 20. Зависимости

### US-02 — Расписание Student

Student должен видеть актуальный cancelled-state.

### US-03 — Календарь Teacher

Teacher должен видеть отменённый Lesson в согласованном представлении.

### US-05 — Перенос занятия

Отмена является отдельным сценарием и не должна автоматически выполнять перенос.

### US-07 — Статус занятия

US-07 определяет общую модель статусов Lesson. Cancelled-state US-06 должен быть согласован с этой моделью.

---

## 21. Out of Scope

В US-06 не входят:

- физическое удаление `Lesson`;
- перенос занятия;
- массовая отмена нескольких занятий;
- отмена всей серии регулярных занятий;
- внешние уведомления Student;
- восстановление отменённого Lesson;
- причины отмены;
- финансовые последствия отмены.

---

## 22. Пользовательский результат

После успешной отмены `Teacher` и `Student` видят, что конкретный `Lesson` больше не состоится.

При этом запись о занятии сохраняется в системе и не теряется.

Если пользователь отказывается от отмены либо операция завершается ошибкой, состояние `Lesson` остаётся без изменений.
