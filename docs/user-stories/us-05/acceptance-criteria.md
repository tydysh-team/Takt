# US-05 — Acceptance Criteria

## User Story

**Я как преподаватель хочу перенести занятие на другую дату или время, чтобы актуализировать расписание при изменении договорённостей с учеником.**

---

## AC-US05-01 — Перенос только даты

**Given**
- пользователь аутентифицирован как `Teacher`;
- существует собственный доступный `Lesson`;
- исходные дата и время валидны.

**When**
- `Teacher` изменяет только дату занятия;
- время оставляет без изменений;
- подтверждает перенос.

**Then**
- дата `Lesson` обновляется;
- время сохраняется без изменений;
- остальные данные `Lesson` не изменяются;
- актуальное состояние сохраняется Backend.

---

## AC-US05-02 — Перенос только времени

**Given**
- существует собственный `Lesson`.

**When**
- `Teacher` изменяет только время занятия.

**Then**
- время `Lesson` обновляется;
- дата сохраняется;
- остальные данные `Lesson` остаются неизменными;
- результат сохраняется Backend.

---

## AC-US05-03 — Одновременное изменение даты и времени

**When**
- `Teacher` изменяет дату и время одного `Lesson`;
- новые значения валидны.

**Then**
- оба значения обновляются одной логической операцией;
- сохраняется одно актуальное состояние `Lesson`;
- частичное обновление не допускается.

---

## AC-US05-04 — Сохранение остальных данных Lesson

После успешного переноса должны сохраняться без изменения данные, не относящиеся к сценарию US-05.

В частности:

- связанный `Student`;
- принадлежность `Teacher`;
- предмет / содержание;
- продолжительность, если её изменение не предусмотрено отдельным сценарием;
- другие данные `Lesson`, не входящие в scope переноса.

---

## AC-US05-05 — Перенос собственного Lesson

Перенос доступен только для `Lesson`, принадлежащего текущему авторизованному `Teacher`.

`Teacher` определяется из authentication context.

Успешный перенос не должен зависеть от переданного клиентом произвольного `teacher_id`.

---

## AC-US05-06 — Попытка переноса чужого или недоступного Lesson

**Given**
- `Lesson` не принадлежит текущему `Teacher` либо недоступен пользователю.

**When**
- выполняется попытка его переноса.

**Then**
- операция отклоняется;
- исходный `Lesson` не изменяется;
- пользователю возвращается корректный authorization / not-found result согласно общим правилам API;
- ложный success отсутствует.

---

## AC-US05-07 — Недопустимая дата или время

Перенос не должен успешно выполняться при:

- некорректной дате;
- некорректном времени;
- недопустимом прошлом времени;
- других нарушениях обязательных временных ограничений.

В ошибочном сценарии:

- исходные дата и время сохраняются;
- пользователь получает validation / error result;
- ложный success отсутствует.

---

## AC-US05-08 — Перенос без конфликта расписания

**Given**
- новое время не пересекается с другими `Lesson` текущего `Teacher`.

**When**
- пользователь подтверждает перенос.

**Then**
- conflict-warning не отображается;
- перенос успешно выполняется;
- новое время сохраняется;
- расписание обновляется актуальными данными.

---

## AC-US05-09 — Конфликт при переносе

**Given**
- новое время пересекается с другим `Lesson` текущего `Teacher`.

**When**
- выполняется проверка согласно US-04.

**Then**
- отображается warning о конфликте;
- перенос не применяется автоматически;
- пользователю доступны действия согласно conflict-flow US-04.

---

## AC-US05-10 — Изменение времени после conflict-warning

**Given**
- при переносе обнаружен конфликт.

**When**
- `Teacher` изменяет новую дату или время.

**Then**
- предыдущий результат проверки считается неактуальным;
- выполняется новая проверка пересечений;
- решение принимается по новым временным данным.

---

## AC-US05-11 — Явное подтверждение конфликтного переноса

**Given**
- обнаружен конфликт.

**When**
- `Teacher` явно подтверждает перенос несмотря на warning.

**Then**
- система разрешает выполнить перенос;
- новые дата / время сохраняются;
- расписание отображает актуальный конфликтующий `Lesson`.

Без явного подтверждения конфликтный перенос не применяется.

---

## AC-US05-12 — Отмена переноса пользователем

**Given**
- `Teacher` открыл сценарий переноса.

**When**
- пользователь отменяет изменения.

**Then**
- исходные дата и время сохраняются;
- Backend не изменяет `Lesson`;
- расписание не отображает ложное изменение;
- success-state отсутствует.

---

## AC-US05-13 — Backend / API error при сохранении

**Given**
- пользователь подтвердил перенос.

**When**
- Backend / API / transport error не позволяет успешно завершить операцию.

**Then**
- исходные данные `Lesson` сохраняются;
- частичное обновление отсутствует;
- UI не фиксирует новые значения как успешно сохранённые;
- пользователь получает error-state;
- после refresh отображается фактическое состояние Backend.

---

## AC-US05-14 — Loading-state и защита от повторной отправки

Во время активного сохранения:

- пользователь видит loading-state;
- повторное подтверждение не должно создавать конкурирующие операции;
- UI не должен показывать success до подтверждённого ответа Backend.

---

## AC-US05-15 — Обновление расписания Teacher

После успешного переноса:

- `Lesson` больше не отображается в старом временном слоте;
- появляется в новом временном слоте;
- актуальные дата и время отображаются в `Calendar` и `List`;
- ручной `F5` не требуется для получения нового состояния.

---

## AC-US05-16 — Обновление расписания Student

После успешного переноса:

- соответствующий `Student` получает актуальные дату и время того же `Lesson`;
- старые временные данные больше не считаются актуальными;
- расписание Student не противоречит расписанию Teacher.

---

## AC-US05-17 — Перенос между периодами

Система должна корректно поддерживать перенос:

- внутри одного дня;
- между разными днями;
- между разными неделями;
- между разными отображаемыми диапазонами расписания.

После success `Lesson` отображается только в актуальном периоде.

---

## AC-US05-18 — Date / Time / Timezone

При переносе:

- временные значения обрабатываются в timezone-aware формате;
- Backend является источником истины для сохранённого времени;
- проверка конфликтов выполняется в едином временном представлении;
- timezone отображения не должна изменять фактический момент занятия.

---

## AC-US05-19 — Authentication

Неаутентифицированный пользователь не должен иметь возможности выполнить защищённый сценарий переноса.

Пользователь без роли `Teacher` не должен получать доступ к Teacher-сценарию изменения `Lesson`.

---

## AC-US05-20 — Реальный Frontend ↔ Backend flow

Необходимо подтвердить end-to-end сценарий без mock-response:

1. `Teacher` открывает существующий `Lesson`;
2. текущие дата и время загружаются в форму;
3. пользователь меняет дату и/или время;
4. Frontend отправляет изменение в Backend;
5. Backend валидирует доступ и новые значения;
6. при необходимости применяется US-04;
7. Backend сохраняет результат;
8. Frontend получает актуальное состояние;
9. расписание Teacher обновляется;
10. Student получает те же актуальные временные данные.

---

## AC-US05-21 — Regression связанных сценариев

После внедрения US-05 должны сохранять работоспособность связанные сценарии:

- `US-01` — создание занятия;
- `US-02` — просмотр расписания Student;
- `US-03` — календарь Teacher;
- `US-04` — проверка временных конфликтов.

Перенос не должен нарушать существующее создание и отображение `Lesson`.

---

# Обязательные Acceptance Criteria

Для Product Acceptance обязательными являются:

- `AC-US05-01` — перенос даты;
- `AC-US05-02` — перенос времени;
- `AC-US05-03` — перенос даты и времени;
- `AC-US05-04` — сохранение остальных данных;
- `AC-US05-05` — собственный Lesson;
- `AC-US05-06` — чужой Lesson;
- `AC-US05-07` — invalid date/time;
- `AC-US05-08` — перенос без конфликта;
- `AC-US05-09` — conflict-flow;
- `AC-US05-10` — повторная проверка;
- `AC-US05-11` — подтверждение конфликта;
- `AC-US05-12` — cancel;
- `AC-US05-13` — API error;
- `AC-US05-14` — loading / duplicate protection;
- `AC-US05-15` — актуализация Teacher;
- `AC-US05-16` — актуализация Student;
- `AC-US05-17` — перенос между периодами;
- `AC-US05-18` — timezone;
- `AC-US05-19` — authentication / authorization;
- `AC-US05-20` — Frontend ↔ Backend E2E;
- `AC-US05-21` — regression.

Если хотя бы один обязательный Acceptance Criterion имеет статус `FAIL`, итоговый статус US-05 не может быть `PASS`.
