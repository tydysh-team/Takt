# US-17 — История попыток сдачи

## User Story

**Я как преподаватель хочу видеть историю попыток сдачи домашнего задания, чтобы понимать, как ученик исправлял работу.**

---

## 1. Цель

Позволить `Teacher` просмотреть последовательность Submission Attempt конкретного Homework и понять развитие работы Student.

## 2. Основной пользователь

`Teacher`.

Student-facing история может использовать те же данные, но обязательный пользователь US-17 — Teacher.

## 3. Состав истории

Для каждой попытки отображается минимум:

- номер попытки;
- `submitted_at`;
- комментарий Student;
- вложения;
- late-признак;
- результат проверки;
- комментарий Teacher;
- состояние решения по попытке.

## 4. Порядок

История имеет стабильный хронологический порядок.

Номер попытки и порядок отображения не должны противоречить друг другу.

Историческая попытка после новой пересдачи не перезаписывается.

## 5. Правила доступа

Teacher видит историю только Homework, принадлежащих его Teacher-контексту и связанному Student.

Произвольный `homework_id` не должен раскрывать историю другого Teacher.

## 6. Основной сценарий

1. Teacher открывает Homework / актуальную работу.
2. Переходит к истории попыток.
3. Backend загружает все доступные attempts.
4. UI показывает их последовательно.
5. Teacher раскрывает конкретную попытку.
6. Видит Student-файлы, комментарий и результат проверки именно этой попытки.
7. Актуальная попытка визуально отличима от исторических.

## 7. Внешний контракт

```text
GET /api/v1/teachers/me/homework/{homework_id}/submissions
```

Response — массив attempts в стабильном порядке.

Пустая коллекция допустима только для Homework без отправок.

## 8. Согласованность данных

Review Result конкретной попытки не должен отображаться на другой попытке.

После `needs_revision → resubmit`:

- старая попытка сохраняет своё решение;
- новая попытка имеет собственное состояние;
- история отражает обе.

## 9. Empty / Loading / Error

- отсутствие попыток — отдельный empty state;
- loading не отображается как empty;
- API error не отображается как отсутствие истории.

## 10. Boundary cases

- 0 попыток;
- 1 попытка;
- много попыток;
- попытка без файлов;
- попытка без Student-комментария;
- несколько review cycles;
- недоступное вложение;
- неизвестное историческое состояние.

## 11. Зависимости

- US-12;
- US-14;
- US-15;
- US-16.

## 12. Out of Scope

- визуальный diff;
- экспорт истории;
- аналитика качества исправлений;
- восстановление удалённых файлов за пределами политики хранения.

## 13. Пользовательский результат

Teacher видит последовательность сдач и обратной связи и может понять, как Student дорабатывал одно и то же Homework.

## 15. Security & authorization

- Backend является финальной точкой контроля доступа; скрытие кнопки/маршрута на Frontend не считается достаточной защитой.
- Идентификаторы из request нельзя использовать для обхода ownership.
- При отказе доступа response не должен раскрывать данные чужого Teacher/Student/Homework/Submission.

## 16. Reliability & concurrency

- Mutating action считается завершённым только после подтверждения Backend.
- Double-click, retry и конкурентная смена lifecycle не должны приводить к двойному применению одного логического действия.
- При конфликте состояния пользователь получает явный conflict/error state и должен перезагрузить актуальные данные.

## 17. Observability & performance

Для ошибок, влияющих на Product Acceptance, должны быть доступны диагностические данные Backend/Frontend (request correlation/лог ошибки или эквивалент в принятом стеке) без вывода чувствительных данных пользователю.

Performance проверяется как Sprint-ориентир, а не production SLA: интерактивные запросы — ориентир p95 ≤ 500 мс, агрегирующие статистические запросы — p95 ≤ 1000 мс на типовом тестовом объёме.
