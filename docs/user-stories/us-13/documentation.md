# US-13 — Очередь работ на проверку

## User Story

**Я как преподаватель хочу видеть работы учеников, ожидающие проверки, чтобы понимать, какие задания требуют моего внимания.**

---

## 1. Цель

Дать `Teacher` единый список актуальных Submission Attempt, которые ожидают его проверки.

## 2. Что попадает в очередь

В очередь входят только актуальные попытки Homework текущего Teacher, для которых lifecycle Homework = `submitted`.

Это включает:

- первую отправку;
- повторную отправку после доработки.

Старые исторические попытки не дублируются в очереди, если существует более новая актуальная попытка.

## 3. Отображаемые данные

Для элемента очереди показывается минимум:

- Student;
- Homework;
- номер попытки;
- `submitted_at`;
- `due_at`;
- late-признак;
- информация о наличии файлов / комментария.

Student и Homework должны быть различимы без использования только технических ID.

## 4. Сортировка

Базовая сортировка должна быть стабильной и понятной пользователю.

Основной порядок — по времени фактической отправки.

Конкретное направление сортировки должно быть единообразно в UI и API.

## 5. Основной сценарий

1. Teacher открывает очередь проверки.
2. Backend определяет текущего Teacher.
3. Загружает актуальные `submitted` attempts его Homework.
4. UI отображает список.
5. Teacher открывает выбранную работу.
6. Видит Homework, комментарий Student и вложения.
7. После принятия работы элемент исчезает из очереди.
8. После возврата на доработку элемент также исчезает до следующей пересдачи.

## 6. Внешний контракт

Очередь:

```text
GET /api/v1/teachers/me/homework/submissions/pending
```

Конкретная попытка:

```text
GET /api/v1/teachers/me/homework/submissions/{submission_id}
```

Backend проверяет ownership через Homework → Teacher.

## 7. Empty / Loading / Error

- пустая очередь — корректный empty state;
- loading отличается от empty;
- API error отличается от empty;
- повторная загрузка не создаёт визуальные дубликаты.

## 8. Конкурентные изменения

Если работа проверена в другой вкладке / сессии до открытия карточки:

- UI получает актуальное состояние;
- недопустимое повторное действие не применяется;
- пользователь получает понятное сообщение о смене состояния.

## 9. Boundary cases

- одна работа;
- много работ одного Student;
- несколько attempts одного Homework, где только последняя актуальна;
- late и non-late submissions;
- работа уже проверена между list и detail request.

## 10. Зависимости

- US-12;
- US-16;
- US-14;
- US-15.

## 11. Out of Scope

- SLA проверки;
- автоматическая приоритизация;
- массовая проверка;
- назначение другого reviewer;
- сравнение Students.

## 12. Пользовательский результат

Teacher сразу видит, какие актуальные работы требуют проверки, и может перейти из очереди к конкретной попытке.

## 15. Security & authorization

- Backend является финальной точкой контроля доступа; скрытие кнопки/маршрута на Frontend не считается достаточной защитой.
- Идентификаторы из request нельзя использовать для обхода ownership.
- При отказе доступа response не должен раскрывать данные чужого Teacher/Student/Homework/Submission.

## 16. Reliability & concurrency

- Mutating action считается завершённым только после подтверждения Backend.
- Double-click, retry и конкурентная смена lifecycle не должны приводить к двойному применению одного логического действия.
- При конфликте состояния пользователь получает явный conflict/error state и должен перезагрузить актуальные данные.

## 17. Observability & performance

Для ошибок, влияющих на Product Acceptance, должны быть доступны диагностические данные Backend/Frontend (request correlation/лог ошибки или эквивалент в принятом стеке) без вывода чувствительных данных пользователю.

Performance проверяется как Sprint-ориентир, а не production SLA: интерактивные запросы — ориентир p95 ≤ 500 мс, агрегирующие статистические запросы — p95 ≤ 1000 мс на типовом тестовом объёме.
