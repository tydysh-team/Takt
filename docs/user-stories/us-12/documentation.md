# US-12 — Отправка выполненного задания

## User Story

**Я как ученик хочу отправить выполненное домашнее задание и приложить необходимые файлы, чтобы преподаватель мог проверить мою работу.**

---

## 1. Цель

Позволить `Student` создать первую Submission Attempt по собственному Homework и передать Teacher результат самостоятельной работы.

## 2. Предусловия

- пользователь аутентифицирован как Student;
- Homework существует и принадлежит текущему Student;
- Homework допускает первичную отправку;
- нет уже активной отправленной попытки, ожидающей проверки.

## 3. Данные попытки

Попытка содержит:

- ссылку на Homework;
- порядковый номер;
- `submitted_at`;
- комментарий Student при наличии;
- вложения при наличии;
- вычисленный признак поздней сдачи.

Для первой отправки номер попытки = `1`.

## 4. Правила сдачи

1. Student отправляет только собственное Homework.
2. Сдача после deadline допускается, но должна отражать просрочку.
3. Отправка создаёт новую неизменяемую историческую попытку.
4. После успешной отправки Homework переходит в `submitted`.
5. Пока актуальная попытка ожидает проверки, повторная первичная сдача не создаёт ещё одну попытку.
6. Ошибка upload или Backend не должна создавать ложную успешную попытку.

## 5. Основной сценарий

1. Student открывает Homework в `assigned`.
2. Выбирает отправку работы.
3. Добавляет комментарий и/или файлы.
4. Frontend проверяет локальные ограничения формы.
5. Student подтверждает отправку.
6. Backend проверяет current_user и ownership.
7. Создаётся Submission Attempt №1.
8. Backend фиксирует `submitted_at`.
9. Система определяет late-признак относительно `due_at`.
10. Homework переходит в `submitted`.
11. UI показывает подтверждённый результат.
12. Попытка становится доступна Teacher в очереди проверки.

## 6. Внешний контракт

```text
POST /api/v1/homework/{homework_id}/submissions
```

Пример JSON-части:

```json
{
  "comment": "Решение приложил файлом"
}
```

При наличии файлов transport может быть multipart или отдельным upload-flow.

Успешный response возвращает созданную попытку и актуальное состояние Homework.

## 7. Double submit

Во время активной отправки submit блокируется.

Backend должен предотвращать появление нескольких активных попыток из одного и того же допустимого состояния Homework.

Конкретный механизм idempotency является техническим решением.

## 8. Ошибочные сценарии

- чужой Homework;
- отсутствующий Homework;
- Homework уже `submitted`;
- Homework уже `reviewed`;
- lifecycle не допускает первичную сдачу;
- ошибка файла;
- Backend error;
- transport interruption;
- invalid request.

## 9. Boundary cases

- сдача без файлов, только с комментарием;
- сдача с файлами без комментария;
- сдача точно на границе deadline;
- сдача после deadline;
- двойной click;
- Student потерял доступ к Homework до подтверждения.

## 10. Зависимости

- US-10;
- US-11;
- [`../../general/homework.md`](../../general/homework.md).

## 11. Out of Scope

- редактирование уже отправленной попытки;
- пересдача после `needs_revision` — US-16;
- проверка работы — US-14/US-15;
- визуальный diff файлов.

## 12. Пользовательский результат

Student отправляет работу одним подтверждённым действием, после чего видит, что она принята системой и ожидает проверки Teacher.

## 15. Security & authorization

- Backend является финальной точкой контроля доступа; скрытие кнопки/маршрута на Frontend не считается достаточной защитой.
- Идентификаторы из request нельзя использовать для обхода ownership.
- При отказе доступа response не должен раскрывать данные чужого Teacher/Student/Homework/Submission.

## 16. Reliability & concurrency

- Mutating action считается завершённым только после подтверждения Backend.
- Double-click, retry и конкурентная смена lifecycle не должны приводить к двойному применению одного логического действия.
- При конфликте состояния пользователь получает явный conflict/error state и должен перезагрузить актуальные данные.

## 17. Observability & performance

Для ошибок, влияющих на Product Acceptance, должны быть доступны диагностические данные Backend/Frontend (request correlation/лог ошибки или эквивалент в принятом стеке) без вывода чувствительных данных пользователю.

Performance проверяется как Sprint-ориентир, а не production SLA: интерактивные запросы — ориентир p95 ≤ 500 мс, агрегирующие статистические запросы — p95 ≤ 1000 мс на типовом тестовом объёме.
