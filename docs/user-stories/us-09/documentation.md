# US-09 — Регулярные занятия

## User Story

**Я как преподаватель хочу создавать повторяющиеся занятия, чтобы не добавлять вручную каждое регулярное занятие.**

---

## 1. Цель

Позволить `Teacher` один раз задать параметры регулярного занятия и создать серию отдельных `Lesson` для выбранного `Student`.

Каждый экземпляр серии:

- является самостоятельным `Lesson`;
- имеет собственный идентификатор;
- сохраняется Backend;
- отображается в расписании `Teacher`;
- отображается в расписании соответствующего `Student`;
- подчиняется общим правилам создания Lesson;
- участвует в conflict-check согласно US-04.

---

## 2. Основной пользователь

`Teacher`.

### Связанные сущности

- `Teacher`;
- `Student`;
- `Lesson`;
- серия регулярных занятий.

---

## 3. Предусловия

Для создания серии:

- пользователь аутентифицирован;
- пользователь имеет роль `Teacher`;
- выбран доступный `Student`;
- указаны обязательные данные Lesson;
- базовая дата и время валидны;
- параметры повторения валидны.

---

## 4. Поддерживаемая модель повторения

В рамках Sprint 2 поддерживается один тип повторения:

**weekly — один раз в неделю.**

Каждый следующий Lesson создаётся через одну календарную неделю после предыдущего.

Пример:

- 02.11.2026 18:00;
- 09.11.2026 18:00;
- 16.11.2026 18:00;
- 23.11.2026 18:00.

Сложные recurrence rules в US-09 не поддерживаются.

---

## 5. Обязательные параметры серии

Для создания регулярной серии задаются:

- `Student`;
- базовая дата;
- базовое время;
- `duration`;
- остальные обязательные данные обычного Lesson;
- тип повторения `weekly`;
- количество занятий в серии.

`Teacher` определяется из authentication context и не задаётся пользователем как произвольный владелец серии.

---

## 6. Граница серии

Граница серии определяется **количеством Lesson**.

В рамках Sprint 2:

- минимальный размер серии — **2 Lesson**;
- максимальный размер серии — **52 Lesson**.

Количество включает первый Lesson.

Пример:

`count = 4`

означает создание четырёх отдельных Lesson:

1. базовая дата;
2. +1 неделя;
3. +2 недели;
4. +3 недели.

Бесконечные серии не допускаются.

---

## 7. Алгоритм формирования дат

Для weekly-серии:

`lesson[i].starts_at = base_starts_at + i calendar weeks`

где:

`i = 0 ... count - 1`

Первый экземпляр:

`lesson[0].starts_at = base_starts_at`

Для каждого экземпляра сохраняются:

- согласованное локальное время;
- продолжительность;
- связанный Student;
- остальные данные базового Lesson.

---

## 8. Date / Time / Timezone semantics

Все временные значения должны быть timezone-aware.

При weekly-повторении пользователь ожидает сохранение выбранного **локального времени занятия**.

Например, если занятие задано на:

`понедельник, 18:00`

то последующие занятия серии также должны соответствовать:

`понедельник, 18:00`

в согласованной timezone пользователя.

Backend является источником истины для сформированных временных значений.

Изменение UTC offset из-за timezone rules не должно самостоятельно сдвигать пользовательское локальное время серии.

---

## 9. Занятия в прошлом

Создание серии не допускается, если базовый `starts_at` находится в прошлом.

Если в результате некорректных параметров хотя бы один экземпляр серии должен попасть в недопустимое временное состояние, серия не создаётся.

Пользователь получает validation error.

---

## 10. Основной flow

1. `Teacher` открывает форму создания Lesson.
2. Выбирает `Student`.
3. Заполняет данные занятия.
4. Включает режим повторения.
5. Система показывает настройки серии.
6. `Teacher` выбирает weekly-повторение.
7. Указывает количество Lesson.
8. Frontend валидирует обязательные параметры.
9. Пользователю отображается summary серии.
10. Пользователь подтверждает создание.
11. Backend формирует все даты серии.
12. Backend валидирует каждый экземпляр.
13. Для каждого экземпляра выполняется conflict-check.
14. Если конфликтов нет — серия создаётся.
15. Каждый экземпляр сохраняется как отдельный Lesson.
16. Frontend получает результат.
17. Расписание обновляется без ручного `F5`.
18. Все экземпляры отображаются `Teacher` и соответствующему `Student`.

---

## 11. Summary перед созданием

Перед окончательным подтверждением `Teacher` должен понимать параметры создаваемой серии.

Summary должно отражать минимум:

- Student;
- дату и время первого занятия;
- weekly-повторение;
- количество занятий;
- дату и время последнего занятия либо иной однозначный результат выбранной границы.

Пользователь должен иметь возможность отменить создание до отправки операции.

---

## 12. Conflict-check

Каждый экземпляр серии проверяется на пересечения согласно US-04.

Проверяются конфликты только с Lesson текущего `Teacher`.

Для конфликтов используется то же правило пересечения временных интервалов, что и в US-04.

---

## 13. Серия без конфликтов

Если ни один экземпляр серии не конфликтует с существующим расписанием:

- warning не отображается;
- Teacher подтверждает создание;
- создаётся вся серия.

---

## 14. Один конфликт внутри серии

Если конфликтует один экземпляр:

- система не создаёт серию автоматически;
- пользователю показывается conflict-warning;
- пользователь должен понимать, какой экземпляр серии конфликтует;
- отображаются дата и время конфликтующего Lesson.

Teacher может:

- изменить параметры серии;
- отменить создание;
- явно подтвердить создание серии с конфликтом.

---

## 15. Несколько конфликтов

Если конфликтуют несколько экземпляров:

- warning должен отражать наличие нескольких конфликтов;
- пользователь должен иметь возможность определить конфликтующие даты;
- серия не создаётся автоматически.

Teacher может:

- изменить параметры;
- отменить операцию;
- явно подтвердить создание всей серии с конфликтами.

---

## 16. Явное подтверждение конфликтной серии

Conflict является **предупреждением**, а не безусловным запретом, согласно US-04.

Если `Teacher` явно подтверждает создание:

- создаётся вся серия;
- конфликтующие экземпляры также создаются;
- каждый экземпляр остаётся самостоятельным Lesson.

Без явного подтверждения конфликтная серия не создаётся.

---

## 17. Изменение параметров после warning

Если после conflict-warning пользователь изменяет:

- базовую дату;
- базовое время;
- количество занятий;
- Student;
- duration;
- другие параметры, влияющие на расписание,

предыдущий conflict-result считается неактуальным.

Перед созданием выполняется новая проверка всей серии.

---

## 18. Atomicity

Создание серии является **атомарной операцией**.

Допустимы только два итоговых состояния:

### Success

Созданы **все** Lesson серии.

### Failure / Cancel

Не создан **ни один** Lesson серии.

Частичное создание, при котором часть серии успешно появилась, а часть отсутствует из-за ошибки операции, не допускается.

---

## 19. Validation error

Если параметры серии некорректны:

- запрос не должен приводить к созданию части серии;
- пользователь получает validation error;
- уже существующие Lesson не изменяются.

Некорректными являются, в частности:

- отсутствующий Student;
- некорректная дата;
- некорректное время;
- дата в прошлом;
- недопустимая duration;
- `count < 2`;
- `count > 52`;
- неподдерживаемый recurrence type.

---

## 20. Backend / API error

Если при создании серии возникает Backend / API / transport error:

- серия считается не созданной;
- частичный результат не должен оставаться как успешная серия;
- UI не показывает ложный success;
- пользователь получает error-state.

После повторного получения расписания отображается фактическое Backend-состояние.

---

## 21. Права доступа

Создать серию может только авторизованный `Teacher`.

Backend определяет Teacher из authentication context.

Не допускается:

- создание серии от имени другого Teacher;
- подмена `teacher_id`;
- создание Lesson для недоступного Student.

---

## 22. Каждый экземпляр — отдельный Lesson

После успешного создания:

- каждый экземпляр имеет отдельный идентификатор;
- каждый экземпляр является обычным Lesson;
- каждый экземпляр участвует в календаре;
- каждый экземпляр может использоваться связанными сценариями продукта.

После создания отдельные Lesson могут обрабатываться существующими сценариями:

- US-05 — перенос;
- US-06 — отмена;
- US-07 — статус;
- US-08 — attendance.

US-09 не вводит отдельную обязательную сущность для дальнейшего массового управления всей серией.

---

## 23. Отображение для Teacher

После success:

- все Lesson серии отображаются в календаре `Teacher`;
- занятия находятся в корректных временных слотах;
- серия, переходящая между неделями / отображаемыми периодами, отображается полностью;
- ручной `F5` для появления созданных Lesson не требуется.

---

## 24. Отображение для Student

Соответствующий `Student` видит все созданные для него Lesson серии.

Расписание Student должно быть согласовано с расписанием Teacher:

- одинаковые даты;
- одинаковое время;
- одинаковая duration;
- отсутствие пропавших или дополнительных экземпляров.

---

## 25. Серия между несколькими периодами

Серия может охватывать:

- несколько дней;
- несколько недель;
- несколько отображаемых календарных периодов;
- несколько месяцев.

Переключение периода календаря должно показывать соответствующие экземпляры без их потери или дублирования.

---

## 26. Отсутствие дублей

Повторное:

- получение данных;
- обновление календаря;
- refresh страницы

не должно создавать дополнительные Lesson.

Один созданный экземпляр серии должен отображаться как один Lesson.

Повторная загрузка данных не является повторным созданием серии.

---

## 27. Persistence after refresh

После успешного создания и обновления страницы:

- все созданные Lesson сохраняются;
- количество экземпляров соответствует созданной серии;
- даты и время сохраняются;
- Teacher и Student получают согласованный результат.

---

## 28. Пользовательские состояния

### Normal

Форма работает как обычное создание Lesson.

### Repeat Enabled

Доступны параметры weekly-серии.

### Validation Error

Параметры серии некорректны.

### Loading

Backend выполняет проверку и создание серии.

Повторная отправка должна быть заблокирована.

### Conflict Warning

Обнаружен один или несколько конфликтов.

### Error

Операция не завершена успешно.

### Success

Вся серия успешно создана.

---

## 29. Защита от повторной отправки

Во время активного запроса:

- повторное подтверждение недоступно;
- Frontend не должен инициировать несколько одинаковых операций;
- success отображается только после подтверждённого результата Backend.

---

## 30. Boundary cases

Обязательной проверке подлежат:

### Минимальная серия

`count = 2`

Результат: создаются два Lesson.

### Обычная серия

Например:

`count = 4`

Результат: четыре еженедельных Lesson.

### Максимальная серия

`count = 52`

Результат: создаются 52 Lesson при валидных остальных параметрах.

### Ниже минимальной границы

`count = 1`

Результат: validation error.

### Выше максимальной границы

`count = 53`

Результат: validation error.

### Один конфликт

Conflict-warning до создания.

### Несколько конфликтов

Пользователь получает информацию о нескольких конфликтующих экземплярах.

### Серия без конфликтов

Стандартное создание всей серии.

### Серия через несколько недель / месяцев

Все Lesson формируются и отображаются корректно.

### Weekly при изменении timezone offset

Сохраняется согласованное локальное время занятия.

---

## 31. Negative scenarios

Необходимо корректно обработать:

- отсутствие authentication;
- пользователя без роли Teacher;
- недоступного Student;
- отсутствующего Student;
- базовую дату в прошлом;
- некорректное время;
- некорректную duration;
- неподдерживаемую periodicity;
- количество меньше 2;
- количество больше 52;
- один конфликт;
- несколько конфликтов;
- Backend error;
- transport error;
- повторную отправку;
- некорректный API response.

---

## 32. Business Rules

1. Sprint 2 поддерживает weekly recurrence.
2. Серия содержит от 2 до 52 Lesson включительно.
3. Количество включает первый Lesson.
4. Первый Lesson создаётся на базовую дату и время.
5. Каждый следующий Lesson создаётся через одну календарную неделю.
6. Каждый экземпляр является отдельным Lesson.
7. Teacher определяется из authentication context.
8. Student должен быть доступен текущему Teacher.
9. Базовый Lesson не может начинаться в прошлом.
10. Каждый экземпляр проверяется согласно US-04.
11. Conflict является warning, а не hard block.
12. Конфликтная серия требует явного подтверждения.
13. После изменения параметров conflict-check выполняется заново.
14. Серия создаётся атомарно: all-or-nothing.
15. Backend является источником истины.
16. После success Teacher и Student получают одинаковый набор Lesson.
17. Refresh не создаёт дубли.
18. Локальное weekly-время должно сохранять пользовательский смысл с учётом timezone.

---

## 33. Зависимости

### US-01 — Создание Lesson

Каждый экземпляр серии соответствует общим правилам обычного Lesson.

### US-02 — Расписание Student

Все экземпляры отображаются соответствующему Student.

### US-03 — Календарь Teacher

Все экземпляры отображаются Teacher.

### US-04 — Conflict Check

Каждый сгенерированный Lesson проходит conflict-check.

### US-05 — Перенос

После создания отдельный экземпляр может быть перенесён.

### US-06 — Отмена

После создания отдельный экземпляр может быть отменён.

### US-07 — Статус

Каждый экземпляр получает собственное актуальное состояние.

### US-08 — Attendance

Attendance применяется к каждому отдельному Lesson.

---

## 34. Out of Scope

В US-09 не входят:

- бесконечные серии;
- daily recurrence;
- monthly recurrence;
- выбор нескольких дней недели;
- правила типа «каждый второй понедельник»;
- сложные recurrence rules;
- автоматический поиск свободного времени;
- автоматический перенос конфликтующих Lesson;
- автоматический пропуск конфликтующих экземпляров;
- частичное создание серии;
- массовое редактирование всей созданной серии;
- массовый перенос серии;
- массовая отмена серии;
- изменение recurrence rule уже созданной серии.

---

## 35. Пользовательский результат

`Teacher` один раз задаёт параметры weekly-занятия и получает полный набор отдельных Lesson без необходимости вручную создавать каждую неделю.

До создания пользователь понимает границы серии и получает предупреждения о конфликтах.

После успешного создания вся серия отображается в расписании Teacher и соответствующего Student, сохраняется после refresh и не содержит дублей.
