# Takt — продукт и общие границы

Takt — система для организации взаимодействия преподавателя и ученика вокруг учебных занятий и расписания.

Документ фиксирует общие продуктовые понятия и правила, применимые к нескольким User Story.

## 1. Основные роли

### Teacher

Преподаватель.

В зависимости от реализованных User Story может:

- работать со своими Students;
- создавать и просматривать занятия;
- выполнять другие действия, связанные с учебным процессом.

### Student

Ученик.

В зависимости от реализованных User Story может:

- взаимодействовать со связанными Teachers;
- просматривать свои занятия;
- выполнять другие доступные ему учебные сценарии.

`TEACHER` и `STUDENT` являются основными пользовательскими ролями продукта.

Дополнительные системные роли могут существовать как часть реализации, если они не меняют согласованное пользовательское поведение.

## 2. Основные понятия

### User

Учётная запись пользователя Takt.

Используется для аутентификации и определения текущего пользовательского контекста.

### Teacher ↔ Student relation

Связь между Teacher и Student, определяющая возможность их взаимодействия в сценариях, где такая связь требуется.

Один Teacher может быть связан с несколькими Students.

Один Student может быть связан с несколькими Teachers.

### Lesson

Учебное занятие между Teacher и Student.

Конкретный состав данных Lesson и доступные действия определяются соответствующими User Story.

## 3. Общие продуктовые правила

### Trusted user context

Для защищённых операций Backend самостоятельно определяет текущего пользователя из authentication context.

Клиент не должен получать права другого пользователя простой подменой идентификатора.

### Актуальность связей

Если User Story требует существующей связи Teacher ↔ Student, при выполнении операции учитывается её актуальное состояние.

### Человекочитаемое представление

Teacher и Student должны отображаться пользователю человекочитаемо.

Технический идентификатор не используется как единственная пользовательская подпись.

### Дополнительная функциональность

Реализация может содержать функциональность сверх обязательного scope.

Она допустима, если:

- не нарушает обязательные пользовательские сценарии;
- не изменяет согласованное внешнее поведение без необходимости;
- не используется как замена отсутствующей обязательной функциональности.

## 4. Граница документации

Продуктовая документация определяет:

- ожидаемый пользовательский результат;
- бизнес-правила;
- обязательные ограничения;
- внешнее поведение системы;
- Acceptance Criteria.

Продуктовая документация не определяет без необходимости:

- внутреннюю архитектуру;
- структуру кода;
- структуру БД;
- ORM;
- библиотеки;
- внутренние алгоритмы;
- способ технической реализации.

Эти решения находятся в зоне ответственности разработчиков и Code Review.
