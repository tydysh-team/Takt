# Takt — QA / Product Acceptance process

Документ фиксирует общий порядок QA / Product Acceptance для Foundation и User Story.

## 1. Граница ответственности

Product Owner / Analyst определяет:

- ожидаемый пользовательский результат;
- бизнес-правила и обязательные ограничения;
- внешнее поведение системы;
- Acceptance Criteria.

QA проверяет фактическое поведение относительно согласованной документации и Acceptance Criteria.

Product Acceptance подтверждает соответствие результата согласованному продуктовому scope.

Разработчики и Code Review отвечают за:

- внутреннюю архитектуру;
- структуру кода;
- БД и ORM;
- migrations;
- библиотеки;
- внутренние алгоритмы;
- другие implementation details.

QA / Product Acceptance не заменяет Code Review.

## 2. Статусы проверки

Результат проверки фиксируется одним из статусов:

- `PASS` — все применимые обязательные Acceptance Criteria выполнены;
- `FAIL` — хотя бы один обязательный Acceptance Criterion не выполнен;
- `BLOCKED` — проверку невозможно завершить из-за внешнего blocker, отсутствующего окружения, данных или противоречия в требованиях.

## 3. Передача на проверку

Для QA / Product Acceptance должны быть доступны по применимости:

- проверяемая версия / commit / build;
- воспроизводимый способ запуска;
- необходимые demo / test data;
- результаты применимых automated tests;
- известные ограничения;
- evidence по обязательным Acceptance Criteria.

Evidence может включать:

- automated test results;
- API request / response;
- screenshots / video;
- manual check results;
- integration evidence;
- другой воспроизводимый результат.

Формат evidence не фиксируется жёстко.

## 4. Проверка

QA выполняет собственную проверку обязательных пользовательских сценариев и Acceptance Criteria.

Если результат невозможно воспроизвести или однозначно проверить, проверка может получить `BLOCKED`.

Дополнительная функциональность не компенсирует отсутствие обязательного поведения.

## 5. Retest

После исправления дефекта выполняется повторная проверка затронутых Acceptance Criteria.

Если изменение не затрагивает наблюдаемое поведение или внешний контракт, отдельный повторный Product Acceptance может не требоваться.

## 6. Дефект и изменение требования

Отклонение считается дефектом, если фактическое поведение не соответствует уже согласованному:

- requirement;
- business rule;
- external contract;
- Acceptance Criterion.

Новое пожелание, отсутствующее в согласованном scope, не считается дефектом автоматически и оформляется как изменение или новая задача.

Если требование оказалось неоднозначным, противоречивым или невыполнимым, оно выносится на уточнение.

## 7. Итоговое правило

```text
Implemented ≠ Accepted
Code Review passed ≠ QA passed
QA passed ≠ Code Review
```

Задача считается принятой только тогда, когда обязательный результат соответствует согласованной документации и всем применимым Acceptance Criteria.
