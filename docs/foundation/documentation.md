# Takt — Foundation

Foundation определяет минимальную основу Takt, необходимую для реализации пользовательских сценариев.

Документ фиксирует **ожидаемый результат**, но не определяет внутреннюю архитектуру и способ технической реализации.

## 1. Состав Foundation

| ID | Результат |
| --- | --- |
| `F-01` | существует актуальная проектная и функциональная документация |
| `F-02` | существует рабочий GitHub-репозиторий и процесс разработки через branches, Pull Requests и Code Review |
| `F-03` | существует работоспособная Backend-основа |
| `F-04` | существует работоспособная Frontend-основа |
| `F-05` | существует воспроизводимое хранение данных и локальное окружение |
| `F-06` | реализованы пользователи, роли, аутентификация и связи Teacher ↔ Student |
| `F-07` | существует единая UI/UX-основа продукта |
| `F-08` | Frontend и Backend работают в едином интеграционном контуре |

## 2. Пользователи и роли

Основные пользовательские роли Takt:

- `TEACHER` — преподаватель;
- `STUDENT` — ученик.

Пользователь имеет учётную запись и профиль с человекочитаемыми данными.

Для регистрации используются:

- `email`;
- `password`;
- `role`;
- `first_name`;
- `last_name`;
- опциональный `middle_name`.

Email используется для входа и должен быть уникальным после нормализации.

Пароль:

- обязателен;
- имеет длину от 8 до 128 символов;
- не хранится и не возвращается в открытом виде.

Реализация может содержать дополнительные системные роли и возможности, если они не нарушают обязательные пользовательские сценарии.

## 3. Teacher ↔ Student

Система поддерживает связь между преподавателем и учеником.

Один Teacher может быть связан с несколькими Students, а Student — с несколькими Teachers.

Если пользовательский сценарий требует доступного ученика, должна учитываться актуальная связь `Teacher ↔ Student`.

Технический способ хранения и управления этой связью определяется разработчиками.

## 4. Аутентификация

Система обеспечивает:

- регистрацию Teacher и Student;
- вход зарегистрированного пользователя;
- определение текущего аутентифицированного пользователя;
- определение его роли;
- защиту операций, требующих аутентификации.

Backend является доверенным источником текущего пользовательского контекста.

Клиент не должен получать права другого пользователя простой подменой идентификатора.

Дополнительные механизмы управления сессией могут реализовываться без отдельного изменения Foundation, если обязательное внешнее поведение сохраняется.

## 5. UI/UX base

Пользовательские сценарии должны использовать единую UI/UX-основу.

Минимально должны быть предусмотрены:

- общая структура интерфейса;
- типографика и базовые визуальные правила;
- `button`;
- `input`;
- `select`;
- элементы выбора даты и времени;
- состояния `loading`, `error`, `empty` и `success`.

Teacher и Student отображаются пользователю человекочитаемо, а не только техническим идентификатором.

Конкретная реализация компонентов и визуальные технические решения определяются Frontend-разработчиками и согласованными UI/UX-материалами.

## 6. Frontend ↔ Backend

Frontend и Backend должны работать через реальный интеграционный контур.

Обязательно:

- Frontend выполняет реальные запросы к Backend;
- защищённые операции используют текущий аутентифицированный контекст;
- Frontend корректно обрабатывает успешные и ошибочные ответы;
- конфигурация позволяет воспроизводимо запускать систему;
- mock-данные не используются как подтверждение готовой интеграции.

Минимальный Foundation flow:

```text
Пользователь входит в систему
→ Backend аутентифицирует пользователя
→ Frontend получает текущий пользовательский контекст
→ пользователь работает в интерфейсе в соответствии со своей ролью
```

Общие правила API вынесены в [`../general/api-conventions.md`](../general/api-conventions.md).

## 7. Demo / test data

Для воспроизводимой проверки пользовательских сценариев должны быть доступны данные, позволяющие проверить минимум:

- Teacher;
- несколько Students;
- связь Teacher ↔ Student;
- Student, недоступного конкретному Teacher.

Конкретный способ создания и хранения этих данных определяется разработчиками.

## 8. Граница Foundation

Foundation не определяет:

- внутреннюю архитектуру Backend и Frontend;
- структуру классов, services, repositories и компонентов;
- структуру таблиц БД и ORM-моделей;
- способ реализации migrations;
- конкретные библиотеки;
- внутренние алгоритмы;
- способ реализации authentication и persistence;
- иные технические решения, не влияющие на согласованное внешнее поведение.

Эти решения находятся в зоне ответственности разработчиков и Code Review.

Дополнительная функциональность допустима, если она не нарушает обязательное поведение системы.

Foundation считается базой для последующих User Story и не должен повторно описывать требования конкретных пользовательских сценариев.
